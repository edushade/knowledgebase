# Tenants

A **tenant** is a branded, URL-addressable workspace on the EduShade platform. Every piece of data in every microservice — users, courses, categories, files, sessions — carries a `tenant_id` that resolves back to exactly one `tenants` row. The tenant row owns:

- The **subdomain** at `{subdomain}.<saas-base>` (for example `acme.edushade.com`)
- An optional **custom domain** (for example `learn.acme.com`) — see [Domains](/docs/knowledgebase/tenant-module/domains)
- The parent **organization** (FK → `organizations.id`)
- The **status** (`active`, `inactive`, `suspended`) — lifecycle is covered separately in [Tenant Lifecycle](/docs/knowledgebase/tenant-module/tenant-lifecycle)
- Branding pointers: `logo_dark`, `logo_light`, `favicon`

A tenant is **always** attached to exactly one organization. An organization can own zero or more tenants.

## Data Shape

**Table:** `tenants` (defined in `backend/common/pkg/tenant/tenant.go`)

| Field | Type | Description |
|-------|------|-------------|
| `id` | UUID | Primary key |
| `organization_id` | UUID | FK → `organizations.id` (required) |
| `name` | string (1–255) | Display name |
| `subdomain` | string (1–100) | **Unique**, normalized to lowercase. Pattern `^[a-z][a-z0-9-]*[a-z0-9]$` or a single `[a-z]` |
| `domain` | string, nullable | **Unique** when set. Custom domain verified by [Caddy on-demand TLS](/docs/knowledgebase/tenant-module/domains#caddy-on-demand-tls-verification) |
| `status` | string | One of `active`, `inactive`, `suspended` (create/list) or `active`, `inactive`, `suspended`, `deleted` (update) |
| `logo_dark` / `logo_light` / `favicon` | string, nullable | Asset URLs |
| `created_at` / `updated_at` | timestamp | Auto-managed by the `BeforeAppendModel` hook |
| `deleted_at` | timestamp, nullable | Soft-delete marker |

### Helpers

The tenant model exposes:

- `GetBaseURL()` — returns the tenant's public URL, preferring `domain` and falling back to `https://{subdomain}.edushade.com` when no domain is set.
- `MakeURL(path)` — joins `GetBaseURL()` with a path for building links in emails, invitation tokens, and server-rendered pages.

## Route Tiers

Tenant endpoints are exposed on three of the four tiers described in the [module overview](/docs/knowledgebase/tenant-module/index#route-tiers):

- **Sysadmin** (`/api/v1/sysadmin/tenants/…`) — full CRUD across all tenants
- **Org-admin** (`/api/v1/orgadmin/organizations/:organization_id/tenants/…`) — CRUD restricted to tenants under one organization
- **Admin** (`/api/v1/admin/tenants` / `/api/v1/admin/tenant/info`) — read-only, scoped to the signed-in user's tenants
- **Public** (`/api/v1/public/tenant/…`) — unauthenticated lookups by subdomain or domain

### Sysadmin Authentication

The sysadmin tier is guarded by `SysAdminAuthMiddleware`, which compares a caller-supplied token against `cfg.SystemAPI.AuthToken`. Obtain or validate the token with:

- **Endpoint:** `POST /api/v1/sysadmin/login`
- **Auth:** None — this is the only sysadmin route that is *not* behind the middleware (since the caller is proving they know the token).
- **Request:**

  ```json
  { "token": "<system-api-token>" }
  ```

- **Validation:** `token` is required (`SysAdminLoginRequest.Validate` uses `validation.Required`).
- **Behaviour:**
  - Token matches `SystemAPI.AuthToken` → `200 OK` with `{ "message": "Login successful" }`. Nothing is stored, and no JWT is minted. The endpoint is a pure validation probe.
  - Token does not match → `401 Unauthorized` with `{ "error": "Invalid token" }`.
- **How to call subsequent sysadmin routes:** send the same raw token as a `Bearer` header (`Authorization: Bearer <system-api-token>`). The middleware accepts the header verbatim — there is no session or refresh.

Because the token is static and platform-wide, treat it like a root key: rotate it through the config layer, keep it out of client-side code, and prefer calling sysadmin routes from a server-side job / CLI rather than a browser.

## Create a Tenant

- **Sysadmin endpoint:** `POST /api/v1/sysadmin/tenants`
- **Org-admin endpoint:** `POST /api/v1/orgadmin/organizations/:organization_id/tenants`
- **Permissions (org-admin):** `tenant.create` or `organization.manage`

### Request

```json
{
  "organization_id": "…",
  "name": "Acme Learning",
  "subdomain": "acme",
  "domain": "learn.acme.com",
  "status": "active"
}
```

| Field | Rules |
|-------|-------|
| `organization_id` | Required. Must reference an existing `organizations` row |
| `name` | Required, 1–255 chars, trimmed |
| `subdomain` | Required, 1–100 chars, lowercased before validation, must match `^[a-z][a-z0-9-]*[a-z0-9]$` or a single `[a-z]` |
| `domain` | Optional, 0–255 chars, validated with `is.Domain` |
| `status` | Optional, one of `active`, `inactive`, `suspended`. Defaults to `active` |

### What Happens

1. `organization_id` is parsed and resolved — a missing organization fails with `"organization not found"`.
2. `subdomain` is lower-cased + trimmed.
3. `IsSubdomainAvailable` checks uniqueness → `409 Conflict` with message `tenant with subdomain '<x>' already exists`.
4. If `domain` is set, `IsDomainAvailable` runs the same check → `409 Conflict` on collision.
5. The tenant row is inserted.
6. **Role seeding runs** — [role seeding](/docs/knowledgebase/tenant-module/role-seeding) reads `auth-service/data/roles.json` and `permissions.json` and creates the tenant's RBAC rows. If seeding fails, the freshly-inserted tenant is **deleted** so that state stays consistent.
7. `AuditEvent` (`action="created"`, `resource_type="tenant"`, `module="tenant"`) is published.

> There is no default settings row created on tenant creation — the `settings` row is lazy-created on the first `GET /tenant/settings` call. See [Settings → Lazy creation](/docs/knowledgebase/tenant-module/settings#lazy-creation).

## Retrieve a Tenant

| Scope | Endpoint |
|-------|----------|
| Sysadmin | `GET /api/v1/sysadmin/tenants/:id` |
| Org-admin | `GET /api/v1/orgadmin/organizations/:organization_id/tenants/:id` |
| Admin (current tenant) | `GET /api/v1/admin/tenant/info` |
| Public (by host / header) | `GET /api/v1/public/tenant/info` |
| Public by subdomain | `GET /api/v1/public/tenant/subdomain/:subdomain` |
| Public by domain | `GET /api/v1/public/tenant/domain/:domain` |

The admin `GET /tenant/info` and public `GET /public/tenant/info` paths both rely on `TenantMiddleware` to resolve the caller's tenant ID from the request's `Host` header, `X-Tenant-ID` header, or subdomain — you do not pass the ID as a path parameter. Use `/public/tenant/info` for unauthenticated branding reads (tenant-facing frontends) and `/admin/tenant/info` for authenticated admin reads. The sysadmin `GET /:id` path accepts any tenant ID and requires a sysadmin token.

Public lookups are intentionally unauthenticated because the tenant-facing frontend needs to know which workspace a request maps to **before** it can render a login page. They return the same tenant shape — no filtering on status — so a public caller can distinguish `active`, `inactive`, and `suspended` tenants for UX purposes.

### Single-Tenant Fallback

If the service is configured in single-tenant mode and the requested ID is either the configured default ID or `uuid.Nil`, a tenant row that does not exist in the database is substituted with a **synthetic default tenant** built from the configured slug. In multi-tenant mode a missing tenant always returns `404 Not Found`.

## List Tenants

| Scope | Endpoint |
|-------|----------|
| Sysadmin — all tenants | `GET /api/v1/sysadmin/tenants` |
| Org-admin — org's tenants | `GET /api/v1/orgadmin/organizations/:organization_id/tenants` |
| Admin — current user's tenants | `GET /api/v1/admin/tenants` |

### Query params

| Param | Description |
|-------|-------------|
| `organization_id` | UUID, filters by owning organization |
| `status` | One of `active`, `inactive`, `suspended` (blank allowed) |
| `search` | Case-insensitive `LIKE` on `name` and `subdomain` |
| `page`, `per_page`, sort params | Standard pagination from `PaginationRequestFromGinContext` |

### Admin — "my tenants"

`GET /api/v1/admin/tenants` returns **only** the tenants whose owning organization the signed-in user is a member of. The backend resolves this with an `EXISTS` subquery against `organization_members` (`om.user_id = ? AND om.organization_id = t.organization_id`) — so a user who is a member of two organizations will see every tenant under both.

## Update a Tenant

- **Sysadmin endpoint:** `PUT /api/v1/sysadmin/tenants/:id`
- **Org-admin endpoint:** `PUT /api/v1/orgadmin/organizations/:organization_id/tenants/:id`
- **Permissions (org-admin):** `tenant.update` or `organization.manage`

### Request

```json
{
  "name": "Acme Learning",
  "subdomain": "acme",
  "domain": "learn.acme.com",
  "status": "active"
}
```

Every field is optional. Only provided fields are changed.

- `subdomain` is lowercased and trimmed. If it differs from the current value, uniqueness is re-checked → `409 Conflict` on collision.
- `domain` is lowercased and trimmed. A non-empty new value is checked for uniqueness → `409 Conflict` on collision. Passing an empty string clears the domain back to `NULL`.
- `status` on update additionally accepts `"deleted"`, but soft-deletion is normally done via `DELETE /tenants/:id` (see below) — using `status = "deleted"` here is a direct-state override and skips the soft-delete sweep.

### Branding fields via settings

`logo_dark`, `logo_light`, and `favicon` are **not** modifiable through this endpoint. Update them via the [Settings → Platform block](/docs/knowledgebase/tenant-module/settings#platform-block) so the change is applied in the settings deep-merge path and accompanied by an audit event tied to `resource_type="settings"`.

## Delete a Tenant

- **Sysadmin endpoint:** `DELETE /api/v1/sysadmin/tenants/:id`
- **Org-admin endpoint:** `DELETE /api/v1/orgadmin/organizations/:organization_id/tenants/:id`
- **Permissions (org-admin):** `tenant.delete` or `organization.manage`

Performs a **soft delete** — sets `deleted_at` on the `tenants` row. The tenant disappears from every subsequent list/get, but the row (and its related data) is preserved.

To wipe data — not just hide the tenant — use the [Reset Tenant](/docs/knowledgebase/tenant-module/tenant-lifecycle#reset-a-tenant) flow, which deletes tenant-scoped rows across every service database.

## Tenant Statistics

- **Endpoint:** `GET /api/v1/sysadmin/tenants/stats`
- **Auth:** Sysadmin

Returns a platform-wide roll-up used on the sysadmin dashboard:

| Field | Meaning |
|-------|---------|
| `total_tenants` | All non-deleted tenants |
| `active_tenants` / `inactive_tenants` / `suspended_tenants` | Count by `status` |
| `new_tenants_last_30_days` | `created_at >= now() - 30d` |
| `new_tenants_prev_30_days` | `created_at` in `[now-60d, now-30d)` — lets the UI show a trend comparison |
| `tenants_with_domain` | `domain IS NOT NULL AND domain != ''` |
| `tenants_without_domain` | `total_tenants - tenants_with_domain` |

## Tenant Summary

- **Endpoint:** `GET /api/v1/sysadmin/tenants/:id/summary`
- **Auth:** Sysadmin

Returns a **comprehensive aggregated snapshot** of a single tenant, used for the sysadmin drill-down page. The response combines data from the tenant DB, auth DB, and learning DB in a single call.

### Response shape

| Block | Source | Always present |
|-------|--------|----------------|
| `tenant` | `tenants` row — id, name, subdomain, domain, status, created_at, updated_at | ✅ |
| `organization` | Parent `organizations` row — id, name, code, type, status, description | ✅ |
| `members` | Counts from `organization_members` — `total_members`, `active_members` | ✅ |
| `invitations` | Counts from `invitations` — total, pending, accepted, expired | ✅ |
| `settings` | From the tenant's `settings` row (if present) — `organization_name`, `has_logo` (any of `logo_dark` / `logo_light` / `favicon` set on tenant), `has_custom_theme` (always `false` — theme was removed from settings) | Only when a settings row exists |
| `users` | Counts from `auth.users` — total, active, pending_verification, email_verified, phone_verified, new in last 30 / previous 30 days | Only when `auth_db` is wired |
| `contents` | Counts from `learning.*` — total courses, published courses, total lessons, total quizzes, total assignments, total / active / completed enrollments (`program_type = "course"`) | Only when `learning_db` is wired |

Cross-service count failures are swallowed silently — the tenant, organization, members, and invitations blocks always populate, but `users` and `contents` are omitted if their DB is unreachable. This keeps the summary endpoint available even when another microservice is down.

## Events & Audit

Every mutating tenant endpoint publishes an `AuditEvent`:

| Action | `resource_type` | Triggered by |
|--------|-----------------|--------------|
| `"created"` | `"tenant"` | `POST /tenants` |
| `"updated"` | `"tenant"` | `PUT /tenants/:id`, `PATCH .../activate`, `PATCH .../deactivate`, `POST .../reset` |
| `"deleted"` | `"tenant"` | `DELETE /tenants/:id` |

All events carry `module = "tenant"`, the acting user's UUID, and an `after_value` map containing the tenant's post-change name / subdomain / status. Sysadmin calls log the acting user's UUID from the request context — pass it through your sysadmin proxy so audits don't collapse to `uuid.Nil`.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| `subdomain already exists` on create | Pick a different subdomain. Soft-deleted rows **still** hold the unique constraint slot until hard-deleted |
| `organization not found` | Parent organization ID is wrong or the org is soft-deleted — resurrect or recreate the organization first |
| `domain already exists` | The custom domain is attached to another tenant. Detach it there, or pick a different domain |
| Tenant created but users see a 500 on first login | Role seeding failed silently before the cleanup landed — confirm `auth-service/data/roles.json` and `permissions.json` are reachable from tenant-service's working directory (see [Role Seeding](/docs/knowledgebase/tenant-module/role-seeding)) |
| `GET /tenant/info` returns the wrong tenant | `TenantMiddleware` resolves by subdomain / custom domain / header. The caller is coming in through a URL that maps to a different tenant — check the `Host` header and DNS |
| Admin sees zero tenants in `GET /admin/tenants` | The signed-in user has no row in `organization_members` for any organization that owns a tenant. Add them via [Members](/docs/knowledgebase/tenant-module/members) first |
