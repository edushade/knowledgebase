# Impersonation

Impersonation is the sysadmin's escape hatch for operating inside a tenant. One endpoint — `POST /sysadmin/tenants/:id/impersonate` — returns a real access token + refresh token pair tied to an actual tenant user, so the sysadmin can drive the tenant-facing UI as if they signed in normally.

What makes this flow special is that it is **self-healing**:

- If the tenant has a `super_admin` role and at least one active user with that role, the endpoint logs in as the oldest such user.
- If no user has `super_admin` but the role exists, it creates a dedicated `System Super Admin` user, assigns the role, and issues the token.
- If the `super_admin` role itself does not exist (e.g. a tenant that predates role seeding, or whose seeding failed), it **runs role seeding on demand** and retries.

The net effect: pointing an impersonation call at any tenant in the platform, regardless of its provisioning state, will land the sysadmin inside the tenant within one request.

## Route

- **Endpoint:** `POST /api/v1/sysadmin/tenants/:id/impersonate`
- **Auth:** Sysadmin (static system token)

### Request body (optional)

```json
{ "user_id": "…" }
```

| Field | Rules |
|-------|-------|
| `user_id` | Optional UUID. If provided, impersonate **this specific user** (must have the `super_admin` role in this tenant). If omitted or empty, impersonate the **oldest active user with `super_admin`** |

### Path param

| Param | Meaning |
|-------|---------|
| `id` | Tenant ID to log into |

### Response

```json
{
  "user": { "id": "…", "tenant_id": "…", "email": "…", "name": "…", "is_admin": true, "…": "…" },
  "access_token": "<JWT>",
  "refresh_token": "<64-char random>",
  "expires_in": 3600,
  "email_verification_required": false,
  "phone_verification_required": false,
  "password_set": true
}
```

This is the same shape auth-service returns for a normal login, so any client that knows how to handle a login response handles this.

## User selection

The handler runs a single JOIN query against the auth DB:

```
users
  JOIN user_roles  ON user_roles.user_id  = users.id
  JOIN roles       ON roles.id            = user_roles.role_id
WHERE users.tenant_id = :id
  AND roles.name      = 'super_admin'
  AND users.status    = 'active'
  AND users.deleted_at IS NULL
  AND roles.deleted_at IS NULL
ORDER BY users.created_at ASC
```

- **Default behaviour** (no `user_id` in body): returns the **oldest** match. Stable across repeated impersonations — the same user is always picked unless they're deleted or deactivated.
- **With `user_id`**: the query is narrowed by `users.id = ?`. If the specified user doesn't match *all* the other filters, the endpoint returns `400 user does not have super_admin role`.

### Fallback: create the super admin

If the default query returns no rows (and no `user_id` was specified), `createSuperAdminUser` kicks in:

1. Look up the `super_admin` role for this tenant.
2. **If the role is missing**, run `roleSeedingService.SeedRolesForTenant(tenantID)` to seed roles + permissions from `data/roles.json` and `data/permissions.json`. Retry the role lookup.
3. If a user already exists with email `system-super-admin@tenant-<tenantID>.local`:
   - Attach the `super_admin` role if it isn't already attached.
   - Set `is_admin = true` on the user row.
   - Return that user.
4. Otherwise, create a fresh user:
   - `email = system-super-admin@tenant-<tenantID>.local`
   - `name = "System Super Admin"`
   - `password = <two concatenated UUIDs>` (hashed)
   - `status = active`, `email_verified = true`, `is_admin = true`
   - Timezone `UTC`, locale `en`
   - Insert the user, then insert the `user_roles` pivot row for `super_admin`.

The randomly generated password is **discarded** — no one can sign in as `system-super-admin@...` using a password. The only way into that user is through this impersonation endpoint (which mints tokens without ever checking the password).

## The masquerade JWT

The access token is generated through the common `jwt.GenerateJWTWithImpersonation` helper with:

| Claim | Value |
|-------|-------|
| `jti` | A freshly-generated UUID (per-request) |
| `tenant_id` | The target tenant's UUID |
| `sub` (user) | The impersonated tenant user's UUID |
| `impersonated_by` | `00000000-0000-0000-0000-000000000000` — a well-known sysadmin UUID |
| `purpose` | `"masquerade"` |

Downstream middleware (`AuthMiddleware`) accepts this exactly like a normal user JWT — `Can(permission)` checks still run against the impersonated user's roles, `TenantMiddleware` still scopes to the tenant_id claim. The `impersonated_by` and `purpose` claims let any service that wants to distinguish "real login" from "sysadmin login" do so; they don't change authorization by themselves.

## The session row

A real session is inserted into auth-service's `user_sessions` table so the access token can be refreshed and so device / IP metadata is recorded:

| Column | Value |
|--------|-------|
| `user_id` | The impersonated user's UUID |
| `tenant_id` | The target tenant's UUID |
| `refresh_token` | 64 random alphanumeric chars |
| `access_token_jti` | The JTI on the issued access token — lets revocation flow through |
| `user_agent` | From the inbound request header |
| `expires_at` | `now + auth.jwt.refresh_duration` |

`PopulateDeviceInfo` parses the User-Agent, and `PopulateIPInfo` looks up geo data through the configured MaxMind service — so the session's device + IP fields look exactly like a normal login. Watch for this when auditing: an impersonation session visually resembles a legitimate login, and the only definitive signal is the `impersonated_by` claim on the JWT plus the audit event.

### Logging out

There is **no** `POST /impersonate/stop` endpoint. To end an impersonation session:

- Client-side: drop the access / refresh tokens.
- Server-side: hit the normal auth-service logout endpoint with the refresh token, which deletes the session row the impersonation created.

Until the session row is deleted, the refresh token is valid and a client could mint new access tokens — treat the access token like any other credential.

## Events & Audit

Every successful impersonation publishes:

```
AuditEvent {
  action:        "created",
  resource_type: "impersonation",
  module:        "tenant",
  tenant_id:     <target tenant>,
  resource_id:   <target tenant id>,
  actor_id:      <sysadmin user ID from JWT, or uuid.Nil for pure static-token calls>,
  description:   "Impersonated tenant admin",
  after_value:   { "tenant_id": "<target tenant>" },
  ip_address:    <caller IP>,
  user_agent:    <caller UA>
}
```

This is the only audit trail for impersonation. `actor_id` will be `uuid.Nil` if the caller hit the endpoint using **only** the static sysadmin token (common for CLI / ops tooling) — in that case, correlate via IP / UA, or route ops tools through a real sysadmin user so the actor is recorded.

## Relationship to role seeding

The on-demand seeding path triggered inside `createSuperAdminUser` is the **only** non-create-tenant surface that kicks off `SeedRolesForTenant`. It exists so that:

- A tenant whose roles were never seeded (e.g. reset-tenant run without the tenant ever being bootstrapped, or a data-migration that skipped role seeding) can still be logged into.
- The on-demand path is idempotent: if roles already exist, `SeedRolesForTenant` detects them and is a no-op.

See [Role Seeding](/docs/knowledgebase/tenant-module/role-seeding) for how the seed files are structured and what gets inserted.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| `user does not have super_admin role` | The `user_id` in the request exists but lacks the role. Either grant the role through auth-service or drop `user_id` from the body to fall back to the default-user logic |
| `user does not belong to the specified tenant` | Rare — the selected user's `tenant_id` does not match the path param. Indicates cross-tenant data leakage; investigate how the user got mis-assigned before retrying |
| `super_admin role not found, failed to auto-seed roles` | `RoleSeedingService` is either unwired (check service construction) or the `roles.json` / `permissions.json` seed files are missing / malformed. See [Role Seeding](/docs/knowledgebase/tenant-module/role-seeding) |
| Session shows up as a normal login in admin dashboards | Expected — the session row is indistinguishable from a real login. Filter by the audit event (`resource_type = "impersonation"`) or by the JWT's `impersonated_by` claim to isolate masquerade activity |
| Impersonation token rejected by other services with `tenant mismatch` | The issued JWT's `tenant_id` matches the target tenant, but `X-Tenant-ID` on the request doesn't. Keep the two in sync when the caller controls `X-Tenant-ID` (e.g. in single-tenant-override mode) |
| Want to impersonate a non-super-admin user for testing | Not supported — the endpoint is hardcoded to `super_admin`. Assign the role to the test user temporarily, or use the standard auth-service login endpoint |
