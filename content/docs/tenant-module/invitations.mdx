# Invitations

An **invitation** is the standard way a tenant or org admin onboards a new user without already knowing their auth-service `user_id`. The flow is token-based:

1. Admin calls `POST /invitations` with an email, target org, target tenant, and the roles / permissions the invitee should land on.
2. Backend generates a secure token, stores the row, and returns it.
3. The token is delivered out-of-band (email / link). The invitee hits `GET /public/tenant/invitation/token/:token` to preview, then `POST /invitations/:id/accept` (authenticated) to claim it.
4. Accept triggers a full provisioning cycle: create (or fetch) the auth-service user, create an `organization_members` row, assign the pre-attached roles, assign the pre-attached permissions, mark the invitation `accepted`.

Invitations are the only flow in the tenant module that publishes both an **`AuditEvent`** *and* a user-scoped **`ActivityEvent`** (`action = "invitation.accepted"`) — acceptance counts as the user's own activity, not just an admin action.

## Data Shape

**Table:** `invitations`

| Field | Type | Description |
|-------|------|-------------|
| `id` | UUID | Primary key |
| `organization_id` | UUID | FK → `organizations.id` |
| `tenant_id` | UUID | FK → `tenants.id`. Must belong to the same organization |
| `email` | string | Lowercased and trimmed on write |
| `token` | string, **unique** | 32 random bytes → base64 URL-encoded. Rotated by resend |
| `role_ids` | `[]uuid` JSONB | Roles that will be assigned on accept (may be empty) |
| `permission_ids` | `[]uuid` JSONB | Extra direct permissions assigned on accept (may be empty) |
| `invited_by` | UUID | User who created the invitation |
| `status` | string | `pending`, `accepted`, `expired`, `cancelled`. Defaults to `pending` |
| `expires_at` | timestamp | Default now + 7 days; override via `expires_in_days` (1–90) |
| `accepted_at` | timestamp, nullable | Set on accept |
| `accepted_by` | UUID, nullable | Auth-service user ID of the accepter (may differ from `invited_by`) |
| `message` | string, nullable | Optional 0–1000 char note shown to the invitee |
| `created_at` / `updated_at` / `deleted_at` | timestamp | Bookkeeping + soft-delete |

### Pending uniqueness

Only one **pending** invitation can exist per `(tenant_id, email)` pair at a time. Creating a second while the first is still `pending` returns `409 Conflict` with `pending invitation already exists for this email`. Cancelling or accepting the first frees the slot.

## Route Tiers

Invitations are exposed on **every** route tier — the semantics are identical but the auth is different:

| Tier | Base | Auth | Typical caller |
|------|------|------|----------------|
| **Sysadmin** | `/api/v1/sysadmin/invitations` | Static system token | Platform-wide tooling |
| **Org-admin** | `/api/v1/orgadmin/organizations/:organization_id/invitations` | JWT + `CanAnyWithOrganization` | Org admin inviting users into tenants under their org |
| **Admin** | `/api/v1/admin/tenant/invitations` | JWT + `TenantMiddleware` + `Can(...)` | A tenant admin inviting users into their own tenant |
| **Public** | `GET /api/v1/public/tenant/invitation/token/:token` | None (only the token acts as a capability) | Invitee preview page |

### Permissions on the admin tiers

| Operation | Permission (admin) | Permission (org-admin) |
|-----------|-------------------|------------------------|
| Create | `invitation.create` | `invitation.create` or `organization.manage` |
| List / Get | `invitation.view` | `invitation.view` or `organization.manage` |
| Cancel | `invitation.delete` | `invitation.delete` or `organization.manage` |
| Resend | `invitation.update` | `invitation.update` or `organization.manage` |
| Accept | `invitation.accept` | `invitation.accept` or `organization.manage` |

> Accept is additionally exposed as `POST /invitations/:id/accept` on the admin / org-admin / sysadmin tiers — but the **primary** acceptance path for a human invitee is the public preview + authenticated `POST` once they've signed in. The authenticated `POST` uses the token in the body, not `:id`.

## Create an Invitation

- **Endpoint (admin):** `POST /api/v1/admin/tenant/invitations`
- **Endpoint (orgadmin):** `POST /api/v1/orgadmin/organizations/:organization_id/invitations`
- **Endpoint (sysadmin):** `POST /api/v1/sysadmin/invitations`

### Request

```json
{
  "organization_id": "…",
  "tenant_id": "…",
  "email": "new.user@acme.com",
  "role_ids": ["…", "…"],
  "permission_ids": ["…"],
  "expires_in_days": 14,
  "message": "Welcome to Acme — this link expires in two weeks."
}
```

| Field | Rules |
|-------|-------|
| `organization_id` | Required UUID. Must exist |
| `tenant_id` | Required UUID. Must exist **and** its `organization_id` must match the above |
| `email` | Required, valid email. Stored lowercased + trimmed |
| `role_ids` | Optional list of role UUIDs. Invalid UUIDs are silently dropped |
| `permission_ids` | Optional list of permission UUIDs. Invalid UUIDs are silently dropped |
| `expires_in_days` | Optional integer, 1–90. Defaults to `7` |
| `message` | Optional string, 0–1000 chars |

### What happens

1. Organization is resolved → `404 organization not found` if missing.
2. Tenant is resolved under that organization → `404 tenant not found or does not belong to organization` if the tenant exists but is under a different org.
3. A lookup for an existing `pending` invitation on `(tenant_id, email)` returns `409 Conflict` — `pending invitation already exists for this email`.
4. A 32-byte cryptographically random token is generated and base64 URL-encoded.
5. `role_ids` and `permission_ids` are parsed; any non-UUID entries are dropped.
6. `expires_at` is computed from `now() + expires_in_days` (default 7).
7. Row is inserted with `status = pending`.
8. `AuditEvent { action: "created", resource_type: "invitation" }` is published.

Response is `201 Created` with the full invitation, **including the token** — callers are expected to embed it in the email they send.

## Preview an Invitation (Public)

- **Endpoint:** `GET /api/v1/public/tenant/invitation/token/:token`
- **Auth:** None — the token itself is the capability

Returns the invitation with all fields (including `role_ids`, `permission_ids`, `message`, `expires_at`). Intended to drive an invitation landing page so the invitee can see what they're being invited to before signing up or signing in.

### Auto-expire on read

If `status = pending` but `expires_at` has passed, the fetch **flips status to `expired`** and returns the updated row. This means:

- You don't need a cron to age out unread invitations — the next preview / accept does it.
- There is also an `ExpireOldInvitations` sweep available as a service method, but the HTTP surface does not expose it today; the self-healing preview is the canonical story.

## Accept an Invitation

- **Endpoint (admin):** `POST /api/v1/admin/tenant/invitations/:id/accept`
- **Endpoint (orgadmin):** `POST /api/v1/orgadmin/organizations/:organization_id/invitations/:id/accept`
- **Endpoint (sysadmin):** `POST /api/v1/sysadmin/invitations/:id/accept`
- **Auth:** JWT — the signed-in user becomes the accepter

### Request

```json
{ "token": "…" }
```

> Note: the path contains `:id` but the **body** carries the token. The handler looks the invitation up **by token**, not by path ID — the path ID is required by the route but functionally ignored during accept. This matches how an invitation-link landing page works: the landing page knows the token (from the query string), not the invitation UUID.

### What happens

1. Invitation is loaded by token. If `status != pending` → `400 invitation is not pending`. If expired → `400 invitation has expired` (and the status is flipped to `expired` as a side-effect of the same GET).
2. `AuthClient.GetOrCreateUser(tenantID, email, nil, nil, nil, verifyEmail=nil)` — auth-service returns an existing user with this email in the tenant or creates a new one. Email is **not** auto-verified; the user verifies via whatever signup / password flow auth-service drives.
3. `memberService.CreateMember(organizationID, tenantID, userID, nil)` — creates the `organization_members` row with default `active` status.
4. If `role_ids` is non-empty, `AuthClient.AssignRoles(userID, tenantID, role_ids)` links the user to each role.
5. If `permission_ids` is non-empty, `AuthClient.AssignPermissions(userID, tenantID, permission_ids)` links the user to each direct permission (in addition to whatever the roles grant).
6. The invitation is updated to `status = accepted`, `accepted_at = now()`, `accepted_by = <userID>` (the auth-service user ID returned above — **not** the JWT user ID of the caller).
7. `AuditEvent { action: "updated", resource_type: "invitation", description: "Accepted invitation" }` is published.
8. `ActivityEvent { action: "invitation.accepted", module: "tenant", metadata: { invitation_id, email } }` is published for the accepter's activity feed.

### Why `accepted_by` can differ from the JWT user

Auth-service may return an **existing** user row (matched by email) rather than the caller's user. If an admin is clicking "accept" on behalf of an invitee from an admin tool, `accepted_by` reflects the invitee's user ID, not the admin's. The `AuditEvent.ActorID`, meanwhile, does come from the JWT — so the audit trail still captures the admin, while the invitation's `accepted_by` captures the provisioned user.

## Resend an Invitation

- **Endpoint (admin):** `POST /api/v1/admin/tenant/invitations/:id/resend`
- **Endpoint (orgadmin):** `POST /api/v1/orgadmin/organizations/:organization_id/invitations/:id/resend`
- **Endpoint (sysadmin):** `POST /api/v1/sysadmin/invitations/:id/resend`

### Request

```json
{ "expires_in_days": 14 }
```

| Field | Rules |
|-------|-------|
| `expires_in_days` | Optional, 1–90. Defaults to `7` (fresh window, not an extension of the existing one) |

### What happens

Only `pending` invitations can be resent — anything else returns `400 only pending invitations can be resent`.

- A brand-new token is generated, **replacing** the old one — the old token stops working immediately, even if the invitee still has the old email.
- `expires_at` is replaced with `now() + expires_in_days`.
- `status` remains `pending` (it is re-set defensively).
- `AuditEvent { action: "updated", resource_type: "invitation", description: "Resent invitation" }` is published.

> Resend is the right tool when the invitee lost the email or the token expired. For anything else, cancel + create a fresh invitation.

## Cancel an Invitation

- **Endpoint (admin):** `DELETE /api/v1/admin/tenant/invitations/:id`
- **Endpoint (orgadmin):** `DELETE /api/v1/orgadmin/organizations/:organization_id/invitations/:id`
- **Endpoint (sysadmin):** `DELETE /api/v1/sysadmin/invitations/:id`

Only `pending` invitations can be cancelled — `400 only pending invitations can be cancelled` otherwise.

- Sets `status = cancelled`. The row is **not** soft-deleted — it stays in the table so audit history remains queryable.
- The token is not rotated, but the pending-accept check on GetInvitationByToken / AcceptInvitation rejects cancelled rows (`invitation is not pending`).
- `AuditEvent { action: "updated", resource_type: "invitation", description: "Cancelled invitation" }` is published.

To re-invite the same email after a cancel, call `POST /invitations` again — the uniqueness check only blocks against *pending*, so a cancelled row does not interfere.

## List / Get Invitations

| Scope | Endpoint |
|-------|----------|
| Sysadmin list | `GET /api/v1/sysadmin/invitations` |
| Org-admin list | `GET /api/v1/orgadmin/organizations/:organization_id/invitations` |
| Admin list | `GET /api/v1/admin/tenant/invitations` |
| Get one (any tier) | `GET /.../invitations/:id` |

### Query params

| Param | Description |
|-------|-------------|
| `organization_id` | Filter to one organization (mostly useful on the sysadmin tier) |
| `tenant_id` | Filter to one tenant |
| `status` | One of `pending`, `accepted`, `expired`, `cancelled` |
| `email` | Case-insensitive `LIKE '%<email>%'` match |
| `page`, `per_page`, sort params | Standard pagination |

The list endpoint does **not** auto-expire on read — only the public token GET does. If you want accurate `pending` vs `expired` filtering in a dashboard, call `ExpireOldInvitations` on a schedule or filter client-side by `expires_at < now`.

## Events & Audit

| Action | `resource_type` | Triggered by |
|--------|-----------------|--------------|
| `"created"` | `"invitation"` | `POST /invitations` |
| `"updated"` | `"invitation"` (description `Accepted invitation`) | `POST /invitations/:id/accept` |
| `"updated"` | `"invitation"` (description `Resent invitation`) | `POST /invitations/:id/resend` |
| `"updated"` | `"invitation"` (description `Cancelled invitation`) | `DELETE /invitations/:id` |

All events carry `module = "tenant"`. Acceptance additionally publishes an `ActivityEvent` with `action = "invitation.accepted"` keyed to the **accepter's** user ID, so it surfaces in their own activity feed.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| `pending invitation already exists for this email` | A `pending` invitation is live. Resend it (to rotate the token) or cancel it first if you need to change the role set |
| `invitation has expired` | Resend — resend rotates the token and grants a fresh window. If the invitee is long-gone, cancel + re-invite |
| `invitation is not pending` on accept | The invitation was already accepted, cancelled, or expired. Check `status` before hitting accept |
| Accept succeeded but user has no roles | `role_ids` was empty on create, or auth-service returned an error on `AssignRoles` that the caller didn't surface. Re-run accept on a fresh invitation with the right `role_ids` |
| Public preview returns `status = expired` after a first visit | Expected — the GET flips `pending` → `expired` on read. Resend to rotate |
| `tenant not found or does not belong to organization` | The `organization_id` / `tenant_id` pair is mismatched. Invitations always go through the parent org; pick a tenant that lives under that org |
| Resend returns the same token | Only happens if the PUT failed silently — check service logs. Fresh resends always return a **new** token |
