# Comm Module

The **Comm Module** is the platform's broadcast and announcement system. Admins author notices — rich-text messages with attachments, thumbnails, and a priority — and target them at the whole tenant, a role, a course, a quiz, an event, a cohort, a learning path, or a hand-picked list of users. Every signed-in user has a notice board in their sidebar that shows the notices they can access, with unread badges, "mark all as read", and a dedicated detail page.

## Architecture Overview

The comm system is a standalone microservice (`comm-service`) that sits behind the platform gateway and exposes two logical surface areas — admin and user — each with its own endpoint prefix. Learner access is gated by the learning-service calendar rather than by RBAC.

### Key Components

- **Backend**: Go (Gin framework) with Bun ORM on PostgreSQL
- **Frontend (Learner)**: Next.js with a notice board dropdown, a sheet panel, a detail route at `/dashboard/notices/{id}`, and an unread badge in the sidebar
- **Frontend (Admin)**: Next.js admin pages at `/admin/communication/notices` for list, create, and edit
- **Multi-Tenancy**: Every notice and read-receipt row is tenant-scoped; cross-tenant delivery is impossible by construction
- **Integrations**:
  - `learning-service → CalendarService` — decides which notices a given user can see
  - `filemanager → AttachmentService` — manages file attachments on notices
  - `auth-service → UserAssociationService` — loads creator and target-user profiles
  - `EntityAssociationService` — loads the audience entity (course, event, cohort, etc.) for display
  - `edushade-common/pkg/events` — publishes `AuditEvent` and `ActivityEvent` asynchronously

### Endpoint Surfaces

| Prefix | Audience | Auth |
|--------|----------|------|
| `/api/v1/admin/notices/*` | Admins with `notice.*` permissions | User JWT + RBAC |
| `/api/v1/user/notices/*` | Any signed-in user | User JWT (access filtered by calendar service) |

### Notice Statuses

Notices move freely between four statuses. The backend does not enforce a state machine — any status can transition to any other.

| Status | Description |
|--------|-------------|
| `draft` | Being authored; not visible to users |
| `scheduled` | Scheduled for a future `published_at`; not visible until that time |
| `published` | Visible to its target audience |
| `archived` | Retained but **not visible to users** — only `published` notices are returned by the user surface; archived notices appear only in the admin list |

### Audience Types

| Audience Type | Value | Meaning |
|---------------|-------|---------|
| All | `` (empty string) | Broadcast to every user in the tenant |
| Role | `role` | Users who have any of the listed roles |
| Course | `course` | Learners enrolled in the listed courses |
| Quiz | `quiz` | Users attached to the listed quizzes |
| Event | `event` | Registrants on the listed events |
| Cohort | `cohort` | Members of the listed cohorts |
| Learning Path | `learning_path` | Learners on the listed learning paths |
| User Individual | `user_individual` | Hand-picked list of user IDs |

See [Audience Targeting](/docs/knowledgebase/comm-module/audience-targeting) for the full matrix.

## How a Notice Reaches a User (High-Level Flow)

```
1. Admin opens the notice form → writes title, body (rich text), chooses audience, priority, status
2. Admin optionally attaches files and uploads a thumbnail
3. On submit → POST /admin/notices → row inserted → attachments linked via AttachmentService.Sync
4. If status=scheduled, the notice stays hidden until published_at is reached (no auto-publish job today)
5. When a user opens the notice board → GET /user/notices
6. CalendarService returns the subset of notices the user can access based on audience_type + audience_ids (only `status = 'published'` notices are considered)
7. The service preloads per-notice read-state from notice_reads and stamps is_read on each response
8. The user clicks a notice → detail page loads, markAsRead inserts a notice_reads row (idempotent per user)
9. AuditEvent is published for create/update/delete and every mark-as-read; ActivityEvent is published on the user-surface mark-as-read path only
```

## User Types & Scope

| Surface | Who can use it |
|---------|----------------|
| **Notice Board + detail page** | Every authenticated learner, instructor, or admin |
| **Create/edit/delete notices, bulk export, bulk delete** | Admins with the relevant `notice.*` permissions |

User type flags (`is_admin`, `is_instructor`, `is_learner`) do not affect notice *visibility*. Access is gated by calendar rules (via the learning service). Admin-surface access is gated by [Roles & Permissions](/docs/knowledgebase/auth-module/roles-and-permissions).

## Permissions

| Permission | Grants |
|------------|--------|
| `notice.list` | List notices in the admin table |
| `notice.view` | View a single notice; export to CSV |
| `notice.create` | Create a notice |
| `notice.update` | Edit any notice |
| `notice.delete` | Delete a notice or bulk delete |

Learner endpoints are **not** gated by RBAC — they rely on business-layer filtering through the calendar service. See [Audience Targeting](/docs/knowledgebase/comm-module/audience-targeting) for details.
