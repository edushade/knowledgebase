# Notice Board (User)

The notice board is the signed-in user's view into every notice they can access. It lives in the sidebar as a bell icon with an unread badge, opens either as a compact dropdown or a full-height sheet panel, and routes to a detail page at `/dashboard/notices/{id}` when a notice is clicked. Every user — learner, instructor, or admin — has a notice board.

## Where the Notice Board Appears

| Surface | Shortcut | Notes |
|---------|----------|-------|
| Sidebar bell icon | Unread badge shows up to "9+" | Clicking opens the dropdown or sheet |
| Dropdown menu | Lists the first 5 notices | Compact view; scrollable inside its container |
| Sheet panel | Slide-out panel (right side) | Shows all accessible notices; responsive (full-width on mobile, `max-w-md` on desktop) |
| Detail page | `/dashboard/notices/{notice_id}` | Full rich-text body, attachments, creator block |

Both the dropdown and the sheet surface the same data — they differ only in layout.

## Unread Badge

The bell icon shows the number of notices where `is_read = false`. The value caps at "9+" to keep the badge compact. The badge updates as soon as the frontend refetches after a mark-as-read — there is no websocket or push path today.

## Priority Icons

Each notice row renders an icon based on its priority:

| Priority | Icon | Colour |
|----------|------|--------|
| `urgent` | AlertCircle | Red |
| `high` | Megaphone | Orange |
| `normal` | Bell | Blue |
| `low` | FileText | Grey |

Unread notices also get a subtle background highlight in the dropdown/sheet row.

## User Workflows

### Opening the Notice Board

1. The user clicks the bell icon.
2. The frontend calls `useNoticeBoard()`:
   - `GET /api/v1/user/notices` with cursor pagination.
   - The service calls `CalendarService.GetNoticeboardEvents()` and returns only notices the user can access **and** whose `status = 'published'` (see [Audience Targeting](/docs/knowledgebase/comm-module/audience-targeting)).
   - Read status is batch-loaded from `notice_reads` so every notice in the response has `is_read` and an optional `read_at`.
3. The backend does **not** apply a sort order to the returned slice today — the SQL query has no `ORDER BY`, and the cursor helper does not re-sort. Any "pinned first" or "unread first" rendering is done on the frontend.

### Opening a Notice Detail

1. The user clicks a notice row.
2. The frontend navigates to `/dashboard/notices/{notice_id}`.
3. `GET /api/v1/user/notices/{notice_id}` returns the full notice:
   - title, body (rich HTML), thumbnail,
   - attachments (with filename, size, and a signed download URL),
   - creator profile (avatar, name, and timestamp).
4. At the same time, the frontend fires `markAsRead(noticeId)` → `POST /api/v1/user/notices/{notice_id}/read`. The backend `GET` does **not** auto-mark-as-read; the frontend is responsible for issuing the `POST`. This is idempotent — the second call for the same user is a silent no-op.
5. Every successful call to the user-surface `POST .../read` publishes an `AuditEvent` and an `ActivityEvent` ("Marked a notice as read").

> **Note:** The service rejects `GET /user/notices/{id}` with `sql.ErrNoRows` → `404` if the user cannot access the notice according to the calendar service, even if the notice is `published`. This is a hard security boundary: access is computed server-side, not in the UI.

### Marking a Single Notice as Read

Clicking a notice automatically marks it as read. There is no separate "mark as read" button inside the detail page.

If you want to mark as read without navigating away, the API is:

```
POST /api/v1/user/notices/{notice_id}/read
```

Response:

```json
{ "message": "Notice marked as read successfully" }
```

### Marking All as Read

1. The **Mark All As Read** button appears in the dropdown footer and the sheet footer **only when `unreadCount > 0`**.
2. Clicking it calls `POST /api/v1/user/notices/mark-as-read-all`.
3. The service:
   - fetches every accessible notice for the user,
   - compares against existing `notice_reads` rows,
   - bulk-inserts one `notice_reads` row per unread notice, all sharing the same `read_at` timestamp.
4. The response is `{ "message": "Successfully marked N notice(s) as read", "data": { "marked_count": N } }` — `marked_count` is the number of newly-marked notices.
5. The frontend shows a toast ("Marked N notice(s) as read") and refetches.

## Notice Detail Page Layout

The `/dashboard/notices/{id}` route renders:

1. **Header**
   - Title (centred, large)
   - Thumbnail image at ~50% width when present
2. **Body**
   - Rich HTML body rendered via `RichTextContent` with prose styling
   - Attachments section (only when files are attached):
     - file icon, filename, file size, Download button
3. **Footer**
   - Creator avatar + name
   - Published date

Loading and error states render inline — a spinner while fetching, "Notice not found" if the ID does not resolve.

## Dropdown vs Sheet

The two implementations share the same hook (`useNoticeBoard()`) and the same data; they differ only in presentation.

| Trait | Dropdown | Sheet |
|-------|----------|-------|
| Opens from | Bell icon in the sidebar | Bell icon in the sidebar |
| Height | Fixed (popover) | Full viewport height |
| Shows | First 5 notices | All accessible notices |
| Responsive | Desktop-first | Responsive — full width on mobile |
| Typical use | Quick glance | Triaging a long backlog |

## Hooks

The frontend exposes two canonical hooks for notice-board integrations:

| Hook | Returns | Backing endpoint |
|------|---------|------------------|
| `useNoticeBoard()` | `{ notices, unreadCount, markAsRead, markAllAsRead, isLoading, error, refetch }` | `GET /v1/user/notices`, `POST /v1/user/notices/{id}/read`, `POST /v1/user/notices/mark-as-read-all` |
| `useNoticeDetails(noticeId)` | Single notice with attachments and creator; only fires when `noticeId` is truthy | `GET /v1/user/notices/{id}` |

Utilities used inside these hooks:

- `getNoticeIconByPriority(priority)` — returns an icon config matching the priority
- `isNoticeUnread(notice)` — returns `!notice.is_read`

## API Reference

| Method | Path | Purpose |
|--------|------|---------|
| `GET` | `/api/v1/user/notices` | List notices the user can access (cursor-paginated, `is_read` stamped) |
| `GET` | `/api/v1/user/notices/{id}` | Get a single notice (returns 404 if the user can't access it) |
| `POST` | `/api/v1/user/notices/{id}/read` | Mark one notice as read (idempotent per user) |
| `POST` | `/api/v1/user/notices/mark-as-read-all` | Bulk mark every accessible unread notice as read |

User endpoints are gated by **authentication only** — no `notice.*` permission is required. Access is filtered by business logic (the calendar service) rather than RBAC.

## Events Emitted

| Action | Audit action | Activity title |
|--------|--------------|----------------|
| `POST /user/notices/{id}/read` | `updated` (notice_read row created) | "Marked a notice as read" |
| `POST /user/notices/mark-as-read-all` | `updated` (N rows) | "Marked N notice(s) as read" |

All mutations publish an `AuditEvent` with `module=comm`, `resource_type=notice`. The handlers always publish events on a successful request, even if the target notice was already read — the database-level "already marked" short-circuit happens inside the service, but the handler does not distinguish that case.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| Bell badge shows the wrong number | Badge is computed from `unreadCount` in the response. Force a refetch; if it persists, verify the frontend cache and confirm `/user/notices` is returning fresh data |
| Opening a notice does not mark it as read | Navigation happens before `markAsRead` resolves. Check the network tab for a failed `POST /user/notices/{id}/read` and investigate the error response |
| Notice I expect to see is missing | Access is filtered server-side by the calendar service. Check that the audience resolves to you — see [Audience Targeting](/docs/knowledgebase/comm-module/audience-targeting) |
| "Notice not found" (404) on a notice that is `published` | The calendar service returns no-access for you. Confirm your enrollment, cohort membership, role, or individual audience entry |
| "Mark all as read" does nothing | The button only appears when `unreadCount > 0`. If it is visible but has no effect, check the API response for `{ "data": { "marked_count": 0 } }` — a count of 0 means nothing was unread according to the calendar service filter |
| Attachments on detail page lack a filename or size | Attachment metadata is fetched from `AttachmentService`. If the file was removed from the file manager but not un-linked, the response may be partial |
