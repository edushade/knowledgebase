# Notification Preferences

Users control what, how, and when they are contacted from a single settings page. Preferences cover three independent axes: **channels** (where), **notification types** (what), and **frequency + quiet hours** (when).

## Accessing Notification Preferences

Learners reach their preferences from the profile settings area:

1. Sign in as any user type.
2. Navigate to **Dashboard → Profile → Settings → Notifications** (`/dashboard/profile/settings/notifications`).
3. Every signed-in user has this page — no special permission required.

Admins who are also learners see the same page from the same route; the admin area does not have a separate admin-only copy of personal preferences.

## What You Can Configure

The page is organised into three cards, each saving to the same `NotificationPreference` record for the user.

### 1. Channel Preferences

Global on/off switches for every channel. If a channel is off, the user will not receive any notification on that channel, regardless of what the sender chose.

| Field | Description |
|-------|-------------|
| `email_enabled` | Email notifications to the user's verified email address |
| `sms_enabled` | SMS notifications to the user's verified phone number |
| `push_enabled` | Browser / mobile push via FCM (see [Push Notifications](/docs/knowledgebase/notification-module/push-notifications)) |
| `whatsapp_enabled` | WhatsApp messages via WhatsApp Cloud API |
| `telegram_enabled` | Telegram messages via Bot API |
| `slack_enabled` | Slack messages via the user's linked workspace |
| `discord_enabled` | Discord messages via the user's linked account |

> The learner UI today renders toggles for **Email, SMS, and Push**; the remaining four channels are supported by the backend `NotificationPreference` model and respected server-side, but their toggles are not yet surfaced in the profile UI. Admin-sent campaigns targeting those channels therefore skip users whose tenant has disabled the channel at a higher level. See [Channels](/docs/knowledgebase/notification-module/channels) for the full matrix.

### 2. Notification Type Preferences

Granular per-type opt-out stored in the `notification_type_preferences` map. Each entry is a boolean: `true` = receive this type, `false` = suppress it across *all* channels.

The learner UI exposes ten controllable types:

| Type | Label |
|------|-------|
| `COURSE_UPDATE` | Course updates |
| `ENROLLMENT` | Enrollment confirmations |
| `ASSIGNMENT_UPDATE` | Assignment feedback |
| `QUIZ_REMINDER` | Quiz reminders |
| `PAYMENT_CONFIRMATION` | Payment confirmations |
| `DISCUSSION` | Discussion posts |
| `CERTIFICATE` | Certificate awards |
| `CLASS_ALERT` | Class alerts |
| `MARKETING` | Marketing messages |
| `SYSTEM_ANNOUNCEMENT` | System announcements |

Transactional, security-critical types (`WELCOME_MESSAGE`, `ACCOUNT_VERIFICATION`, `PASSWORD_RESET`, `ACCOUNT_UPDATE`) are **not** user-suppressible — they always reach the user on at least the email channel. See [Notification Types](/docs/knowledgebase/notification-module/notification-types) for the complete catalogue and which are user-controllable.

### 3. Frequency & Quiet Hours

Controls for *when* notifications reach the user.

| Field | Description |
|-------|-------------|
| `frequency_preference` | `IMMEDIATE`, `DAILY`, or `WEEKLY`. Non-immediate values roll eligible notifications into a digest at a deterministic cadence |
| `quiet_hours_start` | `HH:MM` — start of the do-not-disturb window in the user's timezone |
| `quiet_hours_end` | `HH:MM` — end of the do-not-disturb window |

See [Quiet Hours](/docs/knowledgebase/notification-module/quiet-hours) for the precedence rules and what happens to a notification that lands in the middle of a DND window.

## Form Behaviour

The preferences page is built with `react-hook-form` + Zod validation.

- **Save** button is **disabled until the form is dirty** — clean forms cannot trigger a redundant save.
- On submit, a `PUT /v1/user/notify/preferences` is sent with the entire object (full-object update, not PATCH).
- On success: a `toast.success` is shown; the form is reset to the new values (`dirty` goes back to `false`).
- On failure: the toast surfaces the server error; the form stays dirty so the user can retry.

Initial values come from `GET /v1/user/notify/preferences`. If no record exists yet for the user, the backend returns platform defaults (every channel `true`, every type `true`, `frequency_preference: IMMEDIATE`, no quiet hours).

## Data Model

`NotificationPreference`:

| Field | Type | Notes |
|-------|------|-------|
| `id` | UUID | Absent until the user saves for the first time |
| `user_id` | UUID | Owning user (server-populated) |
| `email_enabled` | boolean | Default `true` |
| `sms_enabled` | boolean | Default `true` |
| `push_enabled` | boolean | Default `true` |
| `whatsapp_enabled` | boolean | Default `true` |
| `telegram_enabled` | boolean | Default `true` |
| `slack_enabled` | boolean | Default `true` |
| `discord_enabled` | boolean | Default `true` |
| `notification_type_preferences` | `Record<string, boolean>` | Keyed by canonical type value |
| `frequency_preference` | `IMMEDIATE` \| `DAILY` \| `WEEKLY` | Default `IMMEDIATE` |
| `quiet_hours_start` | `HH:MM` \| null | Default null |
| `quiet_hours_end` | `HH:MM` \| null | Default null |
| `updated_at` | ISO timestamp | Server-populated |

## API Reference

| Endpoint | Method | Purpose |
|----------|--------|---------|
| `/v1/user/notify/preferences` | GET | Fetch the current user's preferences (returns defaults if none saved) |
| `/v1/user/notify/preferences` | PUT | Full-object update — body matches the `NotificationPreference` shape |

Both require user authentication. There is no admin-side endpoint for editing another user's preferences — admins who need a user to stop receiving something should deactivate the user or pause the campaign instead.

## How Preferences Interact With Campaigns

Campaign delivery always goes through the preference filter:

```
1. Campaign picks an audience (single user / segment / list)
2. For each recipient, for each channel the campaign targets:
   2a. Is the user's channel toggle enabled?            → if no, skip
   2b. Is the notification type not user-suppressed?    → if no, skip
   2c. Is the notification type on the "always-send"
       transactional allow-list?                        → if yes, bypass preferences
   2d. Is the recipient in a quiet-hours window?        → if yes, defer (see Quiet Hours)
   2e. Is the user's frequency_preference IMMEDIATE?    → if not, enqueue into the digest
3. Passing notifications are persisted and dispatched
```

Preferences are evaluated at dispatch time, not at campaign-creation time, so a user who toggles off a channel mid-campaign stops receiving subsequent sends immediately.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| "I turned off Email but still got one" | Check the type — security/transactional types (welcome, verification, password reset) bypass user preferences by design |
| Changes not saving | Confirm the form is dirty; the **Save** button remains disabled otherwise |
| Push toggle off but push still arriving | Push requires two things: the preference flag **and** a registered device. See [Push Notifications](/docs/knowledgebase/notification-module/push-notifications) to unregister the device as well |
| Frequency set to DAILY but nothing arrives | Digests fire at a server-determined hour; a user opting in mid-day will not see their first digest until the next cycle |
| Quiet hours appear to be ignored | The window is interpreted in the user's timezone; confirm the profile timezone matches where the user actually is |
| Preferences differ across tenants | Preferences are tenant-scoped; the same person in two tenants has two independent records |
