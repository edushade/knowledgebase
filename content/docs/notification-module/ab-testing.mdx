# A/B Testing

A/B testing is an **early-preview** capability on the notification module. The campaign wizard exposes the opt-in toggle and a results-preview modal, and `CampaignSettings` already carries the two persisted fields, but the deeper variant-template, delivery-log, and analytics plumbing is still on the roadmap. This page documents what's wired today, what's stubbed, and what's still to come so admins don't mistake the toggle for a finished feature.

## What's Wired Today

### Wizard Toggle

The campaign wizard's **Schedule** step includes a single A/B test toggle (`<Checkbox checked={abTest} />`). Enabling it sets:

| Field | Written value |
|-------|---------------|
| `settings.ab_test_enabled` | `true` |
| `settings.ab_test_percentage` | `10` (fixed; no slider in the UI today) |

Disabling the toggle clears `ab_test_enabled` back to `false` and leaves `ab_test_percentage` unset.

### Persisted Settings Fields

`CampaignSettings` accepts these two fields on `POST/PUT /v1/admin/notify/campaigns`:

| Field | Type | Notes |
|-------|------|-------|
| `ab_test_enabled` | boolean | Persisted as part of the campaign settings blob |
| `ab_test_percentage` | number | Recorded but not yet consumed by dispatch |

Nothing else about A/B testing is persisted at the moment — there is no second-template reference on the campaign payload.

### Results Modal — Mock

`<ABTestResultsModal />` exists as a standalone component and can be opened from the campaign detail area. It renders a two-variant comparison UI — sent counts, open/click/conversion rates, and a "Winner" badge — but the content is **hardcoded sample data**, not real analytics. Treat it today as a design preview, not a live dashboard.

## What's Not Yet Implemented

The claims below are on the roadmap; none are available in production today. If your team is evaluating A/B testing, plan for these gaps:

| Area | Status |
|------|--------|
| Variant B template selection | Not implemented — the wizard still accepts only a single `template_id` |
| `variant_b_template_id` on the campaign payload | Field does not exist |
| Deterministic hash-based split at dispatch | Not implemented — dispatch treats the campaign as a single-variant send |
| `variant` column on [Delivery Logs](/docs/knowledgebase/notification-module/delivery-logs) | Not present |
| `ab_test` sub-object on [Analytics](/docs/knowledgebase/notification-module/analytics) responses | Not present |
| Statistical-significance computation | Not implemented |
| Winner-promotion action | Not implemented |

Because variant assignment and tagging are not yet in place, enabling the toggle today does not actually split recipients. The campaign still sends a single variant to every eligible user; only the `ab_test_enabled` flag is recorded for future backfill.

## Intended Behaviour (Roadmap)

The sections below describe the target behaviour once the remaining pieces land. They are preserved here as a design reference so the wizard, dispatch worker, and analytics pipeline can grow into a consistent shape.

### Split Allocation

Segment members will be split as follows:

| Group | Share | Receives |
|-------|-------|----------|
| **Control (A)** | `100 − ab_test_percentage` % | Variant A (the existing campaign template) |
| **Test (B)** | `ab_test_percentage` % | Variant B (a second template selected in the wizard) |

Splitting will use a deterministic hash of `user_id` into `[0, 100)` so the same user lands in the same bucket across reruns. `ab_test_percentage` will be clamped to `1`–`50` to keep the test group as a minority slice.

### Dispatch

A/B campaigns will dispatch as a single logical campaign, but each notification will be tagged with its variant:

```
for each recipient in resolved_segment:
    variant = bucket_for(recipient.user_id)
    template = variant == "B" ? variant_b_template : variant_a_template
    dispatch(recipient, template, channels, settings)
```

Delivery logs will carry a `variant` field so analytics can group by `A` vs `B`.

### Results Dashboard

Once per-variant delivery data is available, the campaign analytics page will expose an **A/B Test Results** section when `ab_test_enabled` is `true`. The mock modal described above is the planned shape:

| Metric | Description |
|--------|-------------|
| **Sent** | Notifications dispatched for this variant |
| **Delivery rate** | `delivered / sent` |
| **Open rate** | `opened / delivered` |
| **Click rate** | `clicked / delivered` |
| **Bounce rate** | `bounced / sent` |

Each metric will highlight the winning variant and show absolute + relative deltas. Under-powered tests will display a "More data needed" notice instead of a misleading p-value.

### Interaction With Preferences & Quiet Hours

Variant assignment will happen **before** the preference and quiet-hours filters so a user assigned to B who is suppressed simply receives no notification — they will not be re-bucketed into A. The effective test group can therefore be smaller than `ab_test_percentage` suggests when filtering is heavy.

### Winner Promotion

Planned admin actions once results are reliable:

- **Promote winner** — subsequent reruns use the winning variant for the whole segment.
- **Keep both** — continue splitting indefinitely.
- **Revert** — promote the losing variant (for cases where a test reveals a problem with the control).

## API Reference

Today's supported surface is just the two `CampaignSettings` fields:

```
POST /v1/admin/notify/campaigns
{
  ...,
  "template_id": "<single_template_id>",
  "settings": {
    "ab_test_enabled": true,
    "ab_test_percentage": 10,
    ...
  }
}
```

No variant-B or analytics endpoints are part of the A/B flow yet. Once the roadmap items ship, the campaign payload is expected to grow a second template reference and the campaign analytics endpoint will grow an `ab_test` sub-object.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| Enabled the toggle but every recipient got the same message | Expected today — variant assignment is not yet wired; only the flag is persisted |
| Results modal numbers don't match any real campaign | The modal is a design preview with mock data; it is not connected to analytics yet |
| Can't find a "Variant B template" picker in the wizard | Not implemented today — on the roadmap. The wizard accepts a single `template_id` only |
| Can't see a `variant` field on a delivery log | Not implemented today — the delivery log shape does not carry variant information yet |
| Expected an `ab_test` sub-object on the analytics response | Not implemented today — the [Analytics](/docs/knowledgebase/notification-module/analytics) payload does not include it yet |
