# Analytics

Analytics is the reporting surface for the notification system. It rolls up [Delivery Logs](/docs/knowledgebase/notification-module/delivery-logs) into per-campaign and platform-wide metrics so admins can measure deliverability, engagement, and channel performance.

## Accessing Analytics

| Surface | Route | Purpose |
|---------|-------|---------|
| **Notification Dashboard** | `/admin/notification` | Platform-wide rollups — top-of-funnel view |
| **Campaign analytics** | `/admin/notification/campaigns/analytics/{id}` | Dedicated dashboard for one campaign |
| **Campaign detail** | `/admin/notification/campaigns/{id}` | Inline summary panel |

Required permission: `notification.view`. Exports require `notification.export`.

## Campaign Analytics

### Headline Counters

| Counter | Description |
|---------|-------------|
| `total_contacts` | Recipients resolved at send time |
| `sent_count` | Handed off to a provider |
| `delivered_count` | Confirmed delivery |
| `opened_count` | Opens (email pixel + push delivered + inbox click) |
| `clicked_count` | Link clicks |
| `bounced_count` | Hard bounces |
| `failed_count` | Terminal failures |

### Derived Rates

| Rate | Formula |
|------|---------|
| `delivery_rate` | `delivered_count / sent_count` |
| `open_rate` | `opened_count / delivered_count` |
| `click_rate` | `clicked_count / delivered_count` |
| `bounce_rate` | `bounced_count / sent_count` |
| `failure_rate` | `failed_count / total_contacts` |

All rates are reported as fractions in the API (`0.42`) and rendered as percentages in the UI (`42%`).

### Channel Breakdown

Each rate is also reported per channel via `channel_breakdown`:

| Field | Description |
|-------|-------------|
| `sent` / `delivered` / `opened` / `clicked` / `bounced` / `failed` | Per-channel counters |
| `delivery_rate` / `open_rate` / `click_rate` / `bounce_rate` / `failure_rate` | Per-channel rates |
| `unique_recipients` | Distinct users reached on this channel (useful when multiple retries per user occur) |

Channels where opens or clicks aren't meaningful (SMS, WhatsApp on providers without read receipts) report those rates as `null`, not zero, so the UI can display "N/A" rather than misleading zeros.

### Timeline

A time-series of events for charting:

| Field | Description |
|-------|-------------|
| `interval` | `hour` for campaigns under 72 h, else `day` |
| `data` | Array of `{ timestamp, sent, delivered, opened, clicked, bounced, failed }` |

The UI renders a stacked area chart with each series toggleable; hover reveals exact counts per interval.

### A/B Test Sub-Payload

Campaigns with `ab_test_enabled` include an `ab_test` block — see [A/B Testing](/docs/knowledgebase/notification-module/ab-testing) for the shape.

## Platform-Level Analytics

The notification dashboard (`/admin/notification`) shows cross-campaign rollups over a configurable date range.

### Tiles

| Tile | Contents |
|------|----------|
| **Total notifications** | Count of notifications dispatched in the window |
| **Active campaigns** | Currently `RUNNING` or `SCHEDULED` |
| **Delivery rate** | Weighted across all campaigns |
| **Engagement rate** | `(opened + clicked) / delivered` — combined engagement |
| **Channel mix** | Donut chart of notifications per channel |
| **Top templates** | Templates driving the most traffic |
| **Top segments** | Segments receiving the most traffic |
| **Provider health** | Live health badges from the [Providers](/docs/knowledgebase/notification-module/providers) health endpoint |

### Date Range Controls

The dashboard supports relative ranges (last 24 h / 7 d / 30 d / 90 d) and a custom picker. Every rollup re-queries on change; for large windows the dashboard shows a skeleton while loading.

## API Reference

### Campaign Analytics

| Endpoint | Method | Purpose |
|----------|--------|---------|
| `/v1/admin/notify/campaigns/{id}/analytics` | GET | Full analytics for one campaign |

Returned shape (`CampaignAnalytics`):

| Field | Description |
|-------|-------------|
| `campaign_id` | UUID |
| `total_contacts` | See above |
| `sent_count` / `delivered_count` / `opened_count` / `clicked_count` / `bounced_count` / `failed_count` | Counters |
| `delivery_rate` / `open_rate` / `click_rate` / `bounce_rate` / `failure_rate` | Derived rates |
| `channel_breakdown` | Map keyed by channel name |
| `timeline` | Array of time-bucketed data points |
| `ab_test` | Present when A/B enabled |

### Platform Analytics

| Endpoint | Method | Purpose |
|----------|--------|---------|
| `/v1/admin/notify/analytics/delivery` | GET | Aggregate delivery metrics across campaigns |
| `/v1/admin/notify/analytics/engagement` | GET | Open/click engagement rollups |

Query parameters:

| Param | Description |
|-------|-------------|
| `start_date` / `end_date` | Date range (ISO) |
| `channel` | Optional channel filter |
| `campaign_type` | Optional `TRANSACTIONAL` / `MARKETING` / `ANNOUNCEMENT` |

Additional grouping parameters (e.g. `group_by`) may be supported by the backend; the frontend does not currently pass one on these endpoints.

### Exports

| Endpoint | Method | Purpose |
|----------|--------|---------|
| `/v1/admin/notify/analytics/export` | GET | Export analytics or delivery logs |

Query parameters:

| Param | Description |
|-------|-------------|
| `resource` | `delivery_logs`, `analytics`, `campaign_summary` |
| `campaign_id` | When resource is scoped to a campaign |
| `format` | `csv` / `json` / `xlsx` |
| Plus any filters above | Respected during export |

The response is a blob download with `Content-Disposition: attachment`.

## Refresh Behaviour

The `useCampaignAnalytics` hook fetches on demand — it runs on mount and whenever its React Query key invalidates. There is **no auto-polling interval** today, so live counters on a `RUNNING` campaign only update when the page re-fetches (navigation back, window focus, or an explicit refresh). A fixed-interval live refresh is on the roadmap but not wired yet.

## How Analytics Are Computed

Analytics are **materialised rollups**, not live queries:

```
1. Delivery logs write row-level events in real time.
2. A rollup worker aggregates into minute-grain buckets.
3. Minute-grain aggregates roll up into hour/day partitions on a cadence.
4. API reads hit the pre-computed partitions for speed.
```

This is why extremely fresh analytics (events in the last minute) may briefly lag the raw delivery-log count. For forensic analysis, query delivery logs directly.

## Channel-Specific Notes

| Channel | Opens reliable? | Clicks reliable? | Notes |
|---------|-----------------|------------------|-------|
| **Email** | Yes (pixel) | Yes (link wrap) | Opens inflated by mail-client pre-fetch |
| **Push** | Proxied (a delivered ack counts as an open) | Yes (click action) | Background notifications that go unseen still count as opens |
| **SMS** | No | Only with provider-side shortlink tracking | Most SMS providers don't expose opens |
| **WhatsApp** | Provider-dependent | Provider-dependent | Cloud API reports read receipts if the user has them enabled |
| **Telegram / Slack / Discord** | No | If links are wrapped | Bot frameworks don't generally report opens |

The dashboard clearly labels `N/A` for unsupported metric/channel combinations.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| Counter doesn't match delivery logs | Minute-grain aggregator lag (< 1 min typically); live-refresh or query logs directly |
| Open rate > 100 % | Usually a mis-configured pixel firing repeatedly — open the delivery log drawer to see opens per recipient |
| Click rate > open rate | Some clients fire clicks without loading images (image auto-block) — treat click rate as the more reliable engagement signal |
| Channel breakdown missing a channel | That channel had zero attempts — the campaign may not have targeted it, or providers were unavailable |
| Export hangs for large campaigns | Use CSV (the default) and narrow the date range; JSON/XLSX exports are memory-heavier |
| Timeline chart empty | The campaign sent outside the viewed date range; reset the range |
| Platform dashboard slow | Very long date ranges (>90 d) require rollup partitions; narrow the window to < 30 d for snappy loads |
