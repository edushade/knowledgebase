# Delivery Logs

A **Delivery Log** is a row per notification per channel attempt. One logical notification sent across Email + Push + SMS produces three delivery logs; a retry produces another. Delivery logs are the canonical "what happened to this message" record used for debugging, analytics roll-ups, and audit.

## Accessing Delivery Logs

| Surface | Route | Purpose |
|---------|-------|---------|
| **Campaign detail** | `/admin/notification/campaigns/{id}` → Delivery Logs tab | Logs for one campaign |
| **Analytics dashboard** | `/admin/notification/campaigns/analytics/{id}` | Logs grouped + charted |
| **Direct endpoint** | `GET /v1/admin/notify/campaigns/{id}/delivery-logs` | Paginated API |

Required permission: `notification.view`. Exports require `notification.export`.

There is no cross-campaign "all delivery logs" surface in the admin UI today — logs are always scoped to a campaign to keep the view manageable.

## Delivery Log Shape

`DeliveryLog`:

| Field | Description |
|-------|-------------|
| `id` | UUID of this delivery attempt |
| `notification_id` | Logical notification this attempt belongs to |
| `campaign_id` | Owning campaign (null for non-campaign sends) |
| `contact_id` | Contact record (null if the recipient is a registered user) |
| `user_id` | Recipient user (null for guest/contact-only sends) |
| `channel` | One of the seven [Channels](/docs/knowledgebase/notification-module/channels) |
| `provider` | Specific provider adapter that handled this attempt |
| `status` | Current status — see matrix below |
| `attempt` | Attempt counter starting at 1 |
| `sent_at` | When the provider accepted the message |
| `delivered_at` | Provider-confirmed delivery (or mailbox delivery ack) |
| `opened_at` | First open event (email pixel / push delivered / inbox click) |
| `clicked_at` | First link click |
| `bounced_at` | Hard bounce notification from the provider |
| `error_message` | Provider-returned error text (truncated for UI) |
| `provider_message_id` | Provider's own ID — useful for cross-referencing in the provider console |
| `variant` | `A` or `B` for A/B-tested campaigns (null otherwise) |
| `metadata` | Free-form: provider response headers, provider-specific reason codes, geolocation of open events |

## Delivery Status

| Status | Description | Terminal? |
|--------|-------------|-----------|
| `PENDING` | Queued but not yet attempted | No |
| `SENT` | Provider accepted the message | No |
| `DELIVERED` | Provider confirmed delivery to the recipient surface | No (opens/clicks can still follow) |
| `OPENED` | Recipient opened the notification | No (clicks can still follow) |
| `CLICKED` | Recipient clicked a link | Yes |
| `BOUNCED` | Hard bounce — address/token/endpoint invalid | Yes |
| `FAILED` | Terminal provider rejection after exhausting retries | Yes |

Statuses advance monotonically: once a log is `CLICKED` it will never regress to `SENT`. Each advance stamps the corresponding timestamp column.

## How Retries Appear

Each retry creates a **new log row** with the next `attempt` value and the same `notification_id`:

```
notification_id: A
  log #1: attempt 1, provider X, status FAILED, error "5xx"
  log #2: attempt 2, provider X, status FAILED, error "5xx"
  log #3: attempt 3, provider Y, status SENT → DELIVERED → OPENED
```

Filter the notification by `notification_id` to see the whole retry chain in order.

## Delivery Logs UI

The campaign delivery-logs tab presents a paginated table with:

### Columns

- Recipient (name + email/phone, click-through to user profile if applicable)
- Channel (icon)
- Provider
- Status (colour-coded pill)
- Attempt
- Sent at (relative + absolute on hover)
- Delivered / Opened / Clicked timestamps (as they arrive)
- Error excerpt

### Filters

| Filter | Description |
|--------|-------------|
| **Status** | Any of the delivery statuses |
| **Channel** | One of seven |
| **Provider** | Specific provider ID |
| **Variant** | `A` or `B` for A/B-tested campaigns |
| **Has error** | Show only rows with non-empty `error_message` |
| **Time range** | `sent_after` / `sent_before` |
| **Recipient search** | Fuzzy match on email, phone, name |

### Row Detail Drawer

Clicking a row opens a drawer with the full log: complete error message, provider response headers, geolocation of opens/clicks, and the rendered content actually sent (for debugging template variable issues).

## Exports

The delivery-logs table can be exported to CSV, JSON, or XLSX — filters in the UI apply to the export.

API: `GET /v1/admin/notify/analytics/export` with `resource=delivery_logs&campaign_id={id}&format=csv` (requires `notification.export`).

## API Reference

| Endpoint | Method | Purpose |
|----------|--------|---------|
| `/v1/admin/notify/campaigns/{id}/delivery-logs` | GET | Paginated delivery logs for a campaign |
| `/v1/admin/notify/campaigns/{id}/delivery-logs?notification_id=X` | GET | Narrow to a single logical notification (all retries) |
| `/v1/admin/notify/analytics/export` | GET | Export delivery logs (or analytics) as CSV/JSON/XLSX |

Query parameters:

| Param | Description |
|-------|-------------|
| `status` | Comma-separated status filter |
| `channel` | Single channel filter |
| `provider` | Specific provider ID |
| `variant` | `A` or `B` |
| `has_error` | Boolean |
| `sent_after` / `sent_before` | ISO timestamps |
| `search` | Fuzzy recipient search |
| `page`, `per_page` | Standard pagination |

## Common Log Patterns

### Successful multi-channel send

```
user_id: u1, notification_id: n1
  channel email, provider sendgrid, SENT → DELIVERED → OPENED → CLICKED
  channel push,  provider fcm,      SENT → DELIVERED → OPENED
  channel sms,   provider twilio,   SENT → DELIVERED
```

### Failover after provider outage

```
channel email, provider sendgrid, FAILED "5xx"
channel email, provider ses,      SENT → DELIVERED
```

Two rows for the same notification_id, same channel, different providers — the first row has an error, the second succeeded. Analytics counts one delivery (the second), not two.

### Preference-suppressed fanout

```
user_id: u2, campaign email+sms
  (no logs for SMS — user disabled sms_enabled)
  channel email, provider sendgrid, SENT → DELIVERED
```

Suppressed channels don't produce delivery logs — the absence is the record. Aggregate counters on the campaign reflect this as `total_contacts - sms_suppressed_count` for the SMS lane.

### Bounced after delivery

```
channel email, provider sendgrid, SENT → DELIVERED, then later: BOUNCED (soft/delayed bounce)
```

The log row is updated in place; the `bounced_at` is stamped, and the user's email is added to the tenant suppression list.

## Relationship to Campaign Counters

Campaign counters (`sent_count`, `delivered_count`, etc. — see [Campaigns](/docs/knowledgebase/notification-module/campaigns)) roll up from delivery logs:

| Counter | Computed as |
|---------|-------------|
| `sent_count` | Count of delivery logs with status ≥ `SENT` |
| `delivered_count` | Count of delivery logs with status ≥ `DELIVERED` |
| `opened_count` | Count of delivery logs with a non-null `opened_at` |
| `clicked_count` | Count of delivery logs with a non-null `clicked_at` |
| `bounced_count` | Count of delivery logs with status `BOUNCED` |
| `failed_count` | Count of delivery logs with status `FAILED` (terminal only — retried-then-succeeded chains don't count) |

The counters are eventually consistent — brief drift between the campaign header and the log count during heavy dispatch is normal and resolves within seconds.

## Retention

Delivery logs are retained for the tenant's configured window; the exact default is set at the platform layer rather than hard-coded in the frontend, and can be tuned per tenant by the platform team. After expiry, logs are purged and only the aggregate counters remain on the campaign. For long-term analysis, use the [Analytics](/docs/knowledgebase/notification-module/analytics) export which persists in your own storage.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| No log row for a recipient I expected | Preference or quiet hours suppressed the send — check `/v1/admin/notify/segments/{id}/users` for the user's `last_notification_at` and preference state |
| Log row stuck in `SENT` never advancing to `DELIVERED` | The provider didn't emit a delivery ack (some SMS providers don't) — open rate / click rate will report `null` for this channel |
| Error message is truncated | UI shows an excerpt — full text is in the row-detail drawer |
| Opens outnumber deliveries | Email open pixels can fire from mail-client pre-fetch, inflating opens; treat open rate as directional |
| Clicks without prior open | Some clients inline-expand emails without loading images — clicks can legitimately precede open pixels |
| Same recipient appears twice with status SENT | Retry after a transient failure; `attempt` column differs |
| Bounce arrived days after delivery | Soft bounces can be delayed (forwarders, greylisting) — the log is updated in place |
