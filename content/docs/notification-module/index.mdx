# Notification Module

The **Notification Module** is the platform's messaging backbone — it delivers every transactional alert, announcement, marketing campaign, and system event to learners, instructors, and admins across Email, SMS, Push, WhatsApp, Telegram, Slack, and Discord. It also powers the in-app inbox every signed-in user sees.

## Architecture Overview

The notification system is a standalone microservice (`notification-service`) that sits behind the platform gateway and exposes three logical surface areas — learner, admin, and system — each with its own endpoint prefix.

### Key Components

- **Backend**: Go service with Bun ORM on PostgreSQL, Redis for queueing, and pluggable provider adapters
- **Frontend (Learner)**: Next.js with a bell icon, sheet/popover notification centre, and a Preferences page
- **Frontend (Admin)**: Next.js admin area covering campaigns, templates, segments, providers, webhooks, analytics, and audit logs
- **Web Push**: Firebase Cloud Messaging (FCM) with a Service Worker registered at `/service-worker.js`
- **Multi-Tenancy**: Every notification, preference, template, segment, campaign, provider, and webhook is tenant-scoped

### Endpoint Surfaces

| Prefix | Audience | Auth |
|--------|----------|------|
| `/v1/user/notify/*` | Signed-in learners and instructors | User JWT |
| `/v1/admin/notify/*` | Admins with `notification.*` permissions | User JWT + RBAC |
| `/v1/system/notify/*` | Other microservices emitting events | System token |
| `/v1/public/notify/settings` | Unauthenticated bootstrap (FCM config) | Public |
| `/v1/public/notify/devices` | Guest device registration | Public |

### Notification Channels

EduShade supports seven delivery channels. A single logical notification can fan out to any subset of these, guided by the user's preferences and the campaign's channel list.

| Channel | Value | Typical provider |
|---------|-------|------------------|
| **Email** | `email` | SendGrid, SES, Mailgun, SMTP |
| **SMS** | `sms` | Twilio, AWS SNS |
| **Push** | `push` | Firebase Cloud Messaging |
| **WhatsApp** | `whatsapp` | WhatsApp Cloud API |
| **Telegram** | `telegram` | Telegram Bot API |
| **Slack** | `slack` | Incoming webhook / Bot token |
| **Discord** | `discord` | Incoming webhook |

See [Channels](/docs/knowledgebase/notification-module/channels) for per-channel content fields, limits, and provider options.

### Notification Lifecycle

```
1. Source service emits an event (e.g. enrollment.completed, payment.succeeded)
2. notification-service resolves recipients (single user, segment, or campaign audience)
3. Per-recipient preferences + global quiet hours + channel availability are checked
4. A notification row is persisted (status: QUEUED)
5. Worker dispatches to the selected channels via the priority-ordered provider for each channel
6. Provider callbacks update status: SENDING → SENT → DELIVERED → OPENED / CLICKED
7. Delivery logs, campaign counters, and analytics rollups are updated
8. Webhooks are fired for subscribed events
```

### Notification Statuses

| Status | Description |
|--------|-------------|
| `QUEUED` | Persisted, waiting for a worker to pick it up |
| `SENDING` | Picked up by a worker, handed to a provider |
| `SENT` | Provider accepted the message |
| `DELIVERED` | Provider confirmed delivery to the recipient device/inbox |
| `READ` | Recipient opened the notification (in-app inbox click or email open pixel) |
| `FAILED` | Provider rejected or terminally failed after retries |
| `CANCELLED` | Cancelled before dispatch (campaign paused/cancelled, user unsubscribed mid-flight) |

### Campaign Statuses

| Status | Description |
|--------|-------------|
| `DRAFT` | Being authored; not yet scheduled |
| `SCHEDULED` | Scheduled to start at a future `scheduled_at` |
| `RUNNING` | Actively fanning out to the audience |
| `PAUSED` | Manually paused; can be resumed |
| `COMPLETED` | All recipients processed |
| `CANCELLED` | Cancelled by an admin before completion |
| `FAILED` | Terminal failure (provider outage, segment resolution error, etc.) |

## User Types & Scope

Every notification belongs to **one tenant** and targets **one or more users** within that tenant. Tenant isolation is enforced at the database layer; cross-tenant delivery is impossible by construction.

| Surface | Who can use it |
|---------|----------------|
| **Inbox + Preferences** | Every authenticated learner, instructor, or admin |
| **Push registration** | Every authenticated user (also supports guest device registration) |
| **Campaigns, templates, segments, providers, webhooks, audit logs** | Admins with the relevant `notification.*` permissions |

User type flags (`is_admin`, `is_instructor`, `is_learner`) are independent of notification access — anyone signed in has an inbox. Admin-surface access is gated by [Roles & Permissions](/docs/knowledgebase/auth-module/roles-and-permissions).

## Permissions

The notification group in the platform permission catalog (`auth-service/data/permissions.json`):

| Permission | Grants |
|------------|--------|
| `notification.view` | View campaigns, templates, segments, providers, webhooks, analytics, audit logs |
| `notification.create` | Create campaigns, templates, segments, providers, webhooks |
| `notification.update` | Edit any notification resource; pause/resume campaigns |
| `notification.delete` | Delete campaigns, templates, segments, providers, webhooks |
| `notification.send` | Trigger an immediate send or rerun of a campaign |
| `notification.export` | Export analytics, delivery logs, audit logs as CSV/JSON/XLSX |

See [Roles & Permissions](/docs/knowledgebase/auth-module/roles-and-permissions) for how permissions are assembled into roles.
