# Providers & Integrations

A **Provider** is a concrete external delivery backend for a channel — SendGrid for email, Twilio for SMS, Firebase Cloud Messaging for push, and so on. Multiple providers can be configured per channel with priorities so if one is unhealthy, the next takes over without admin intervention.

## Accessing Providers

1. Sign in as an **Admin** with `notification.view`.
2. Navigate to **Admin → Notification → Settings** (`/admin/notification/settings`).
3. The **Integrations** section lists every provider configured for the tenant.

| Action | Permission |
|--------|------------|
| View providers & health | `notification.view` |
| Add provider | `notification.create` |
| Edit provider | `notification.update` |
| Delete provider | `notification.delete` |
| Test provider | `notification.send` |

## Provider Anatomy

| Field | Description |
|-------|-------------|
| `id` | UUID |
| `provider` | Name of the provider adapter (e.g. `sendgrid`, `smtp`, `twilio`). The full set of supported adapter names is returned by the backend via the channels-lookup endpoint — see **Dynamic Provider Catalogue** below |
| `channel` | The [Channel](/docs/knowledgebase/notification-module/channels) this provider serves |
| `config` | Provider-specific config blob — API key, sender address, webhook URL, etc. |
| `is_active` | On/off switch |
| `priority` | Lower number = higher priority; used for failover |
| `rate_limit` | Per-minute cap enforced inside the dispatch worker |
| `created_at` / `updated_at` | Audit |

## Dynamic Provider Catalogue

The set of provider adapters available to a tenant is **not hard-coded in the frontend**. `<ProviderDialog />` calls `useAvailableChannels()` (`GET /v1/admin/notify/providers/channels`), and the response drives:

- The channel dropdown options.
- The provider dropdown options (filtered by the selected channel).
- The config form for the selected provider — fields are rendered from the backend's `config_fields` descriptor per adapter.

This means introducing a new adapter is a backend-side change; the UI picks it up on the next channels-endpoint response without a frontend release.

### Field Renderers

The dynamic form renders each `config_fields` entry based on its type:

| Field type | Rendered as |
|------------|-------------|
| `string` | Text input |
| `secret` | Password input (masked) |
| `email` | Email input |
| `url` | URL input with validation |
| `enum` | Select dropdown |
| `boolean` | Switch |
| `json` | Code textarea with JSON validation |

### Frontend-Native Validation

For the three most frequently deployed email / SMS adapters, the frontend also ships native Zod schemas (`sendgridConfigSchema`, `smtpConfigSchema`, `twilioConfigSchema` in `schema.ts`) so the create/edit form validates synchronously even before the backend round-trip:

| Adapter | Frontend-native keys |
|---------|----------------------|
| **SendGrid** (email) | `api_key`, `from_email`, `from_name`, optional `reply_to` |
| **SMTP** (email) | `host`, `port`, `username`, `password`, `from_email`, `encryption` (`tls` / `ssl` / `none`) |
| **Twilio** (SMS) | `account_sid`, `auth_token`, `from_number` |

For every other adapter the tenant's backend exposes, config validation is entirely backend-driven via the channels-lookup response.

### Typically Deployed Adapters

The backend commonly exposes the following adapters per channel. The exact list depends on which integrations your deployment has enabled — always trust the channels endpoint over this table:

| Channel | Commonly deployed adapters |
|---------|----------------------------|
| **Email** | SendGrid, SMTP; additional SaaS options (e.g. SES, Mailgun) when the backend enables them |
| **SMS** | Twilio; additional options (e.g. AWS SNS) when the backend enables them |
| **Push** | Firebase Cloud Messaging (FCM) — see [Push Notifications](/docs/knowledgebase/notification-module/push-notifications) |
| **WhatsApp** | WhatsApp Cloud API — business-initiated messages require pre-approved templates |
| **Telegram** | Telegram Bot API — the recipient must have started a chat with the bot |
| **Slack** | Slack incoming webhook |
| **Discord** | Discord incoming webhook |

## Priority-Based Failover

Every provider carries an integer `priority`. When dispatching on a channel:

```
1. Rank providers for the channel by priority ASC (1 first).
2. Walk the list until a healthy, non-rate-limited provider is found.
3. Dispatch via that provider.
4. On retryable failure (5xx, network), try the next provider.
5. On terminal failure (4xx invalid payload), mark the delivery FAILED.
```

Priorities are per-tenant and per-channel — so an email channel can have SendGrid at priority 1 and SES as a priority-2 fallback, while the SMS channel has Twilio alone.

## Rate Limiting

The `rate_limit` field is the per-minute ceiling the worker enforces *before* dispatching. When a provider is saturated, the worker either:

- Defers to the next-priority provider (if one exists and has headroom), or
- Enqueues and retries after a short backoff.

This protects the tenant against provider-side 429s and keeps costs predictable.

## Connection Testing

Every provider has a **Test** action (`<ProviderDialog />`):

1. Fill in the provider config.
2. Click **Test Connection**.
3. The backend attempts a minimal live call — e.g. `GET /v3/user/profile` for SendGrid, `GET /2010-04-01/Accounts` for Twilio.
4. Results: green tick with latency, or the provider's error message inline.

API: `POST /v1/admin/notify/providers/{id}/test` (requires `notification.send`).

A test pass doesn't guarantee deliverability to a specific recipient, but it confirms the credentials and endpoint are reachable.

## Config Validation

Before saving, the config can be validated without touching the provider:

API: `POST /v1/admin/notify/providers/validate`

Body: `{ provider, channel, config }`

Returns:

- Missing-required-field errors
- Format errors (e.g. `webhook_url` must be HTTPS, `from_email` must be a valid email)
- Warnings for soft issues (e.g. using a shared sandbox domain)

## Health Monitoring

The **Integrations** section shows a live health badge per provider:

| State | Meaning |
|-------|---------|
| **Healthy** | Recent successful deliveries; provider responsive |
| **Degraded** | Elevated error rate in the last 15 min |
| **Unhealthy** | Repeated failures; provider auto-skipped in failover |
| **Unknown** | No recent deliveries (e.g. a fresh provider) |

API: `GET /v1/admin/notify/system/providers/health` (requires `notification.view`)

Returns per-provider: state, last success, last failure, success rate in the last hour, current rate-limit usage.

## Adding a Provider

1. Open **Admin → Notification → Settings** → **Integrations** → **Add Provider**.
2. Pick the **Channel** — the provider dropdown filters to adapters for that channel.
3. Pick a **Provider** — the config form renders dynamically.
4. Fill in the required fields.
5. Click **Test Connection** — if it passes, continue.
6. Set **Priority** and **Rate Limit**.
7. Click **Save** — `is_active` defaults to true.

API: `POST /v1/admin/notify/providers` (requires `notification.create`).

## Editing a Provider

Click the provider row to open the same dialog in edit mode. Rotations of API keys, changes to sender addresses, and priority adjustments are all handled here.

API: `PUT /v1/admin/notify/providers/{id}` (requires `notification.update`).

Credential rotations are captured as audit events without leaking the secret itself — the audit diff records `config.api_key: "******" → "******"` but the underlying value is encrypted at rest and never exposed through the admin UI once saved.

## Deleting a Provider

- Hard-delete if no campaign ever used it.
- Soft-delete otherwise — the provider is marked inactive and removed from the failover list, but delivery logs keep referencing the provider ID for audit continuity.

API: `DELETE /v1/admin/notify/providers/{id}` (requires `notification.delete`).

## Troubleshooting

| Issue | Solution |
|-------|----------|
| "No active provider for channel X" at send time | Add a provider for that channel or deselect the channel on the campaign |
| Test passes but real sends fail | Credentials may only have sandbox scope — check the provider console for production-access status |
| Provider stuck "Degraded" | Inspect the health endpoint's recent failures; if transient, state clears after a stable hour |
| Secret accidentally captured in audit log | Secrets are masked automatically; if you find plaintext, report immediately — this is a security bug |
| Rate limit too low | Increase `rate_limit` and re-save; remember this is a per-minute cap enforced *before* dispatch |
| Two providers with priority 1 | The worker picks deterministically by creation order; set distinct priorities to be explicit |
| Deleted provider still attached to historical delivery logs | By design — soft delete preserves the reference for audit; the provider simply can't be used for new dispatch |
