# Segments

A **Segment** is a named audience — the set of users a campaign will reach. EduShade supports two kinds: **dynamic segments** that re-resolve from user attributes every time they're used, and **static segments** that store a fixed list of user IDs.

## Accessing Segments

1. Sign in as an **Admin** with `notification.view`.
2. Navigate to **Admin → Notification → Segments** (`/admin/notification/segments`).

| Action | Permission |
|--------|------------|
| View list & detail | `notification.view` |
| Create segment | `notification.create` |
| Edit segment | `notification.update` |
| Delete segment | `notification.delete` |

## Segment Kinds

| Kind | Value | Use case |
|------|-------|----------|
| **Dynamic** | `DYNAMIC` | "All active learners in Bangladesh who enrolled in the last 30 days" — resolves live every time the segment is used |
| **Static** | `STATIC` | A one-off list (e.g. 500 beta testers) — the `user_ids` array is stored verbatim |

Pick dynamic when the audience is definable by filters; pick static when the audience is ad-hoc or externally-produced (e.g. a CSV upload of recipients).

## The Segment Builder (Dynamic Segments)

Dynamic segments carry a `filters` object consumed by the condition builder — a drag-and-drop UI for composing boolean logic on user attributes.

### Condition Groups

The builder nests AND/OR groups arbitrarily deep:

```
AND
├── status = "active"
├── OR
│   ├── country = "Bangladesh"
│   └── country = "India"
└── created_in_last_days ≤ 30
```

Each leaf node is **field + operator + value**. Both the list of fields *and* the operators allowed on each field are fetched from the backend via the `useConditionFields()` hook — the frontend does not hard-code a canonical operator catalogue, so the exact set depends on what your deployment's condition-service publishes. Commonly returned operators include equality / inequality, numeric and date comparisons (`>`, `>=`, `<`, `<=`), string matching (`CONTAINS`, `STARTS_WITH`, `ENDS_WITH`), set membership (`IN`, `NOT IN`), and null checks — but always trust the live field descriptor over any enumerated list.

### Available Fields

Fields are fetched from `GET /v1/admin/notify/segments/fields`, so new source services can expose new fields without a frontend change. The live descriptor is authoritative; the categories below are the kind of fields typically returned:

| Category | Typical examples |
|----------|------------------|
| **Identity** | `user_id`, `email`, `phone`, `username` |
| **Status** | `status`, `is_admin`, `is_instructor`, `is_learner`, `email_verified`, `phone_verified` |
| **Geography** | `country`, `city`, `timezone`, `locale` |
| **Demographics** | `gender`, `designation`, `age` |
| **Activity** | `created_at`, `last_login_at`, `last_learning_activity_at` |
| **Enrollments** | `enrolled_program_ids`, `enrollment_status`, `progress` |
| **Engagement** | `opened_any_email`, `clicked_any_email`, `profile_complete` |
| **Behavioural** | `last_notification_at`, `notifications_received_in_last_days`, `bounced_recently` |

The builder surfaces each field's allowed operators and offers autocomplete for enum-backed fields (statuses, countries, roles) — both driven by the same descriptor.

### Preview

At any point the admin can click **Preview** to open `<SegmentPreviewModal />`:

- Calls `POST /v1/admin/notify/segments/preview` with the current filter JSON.
- Returns the resolved user count and a sample of up to 50 users.
- Helps catch over- or under-matching filters before saving.

### Size Calculation

A saved segment has a cached `size` that's refreshed:

- On segment save
- When a campaign starts (so counter is accurate at send time)
- On explicit refresh (`GET /v1/admin/notify/segments/{id}/size`)

The cached value is shown in the segment list so admins get a quick sense without re-resolving.

## Static Segments

Static segments store an explicit `user_ids` array. They're useful for:

- Manual lists (e.g. beta programme)
- Externally-generated cohorts (data-science pipeline output)
- Fixed ad-hoc targets ("these 12 instructors")

Static segments have no `filters`, and their `size` equals `user_ids.length`. The editor offers:

- Upload via CSV (`user_id` column, or `email` with server-side lookup)
- Manual add via user search
- Bulk remove

A static segment's membership never changes unless explicitly edited — it will **not** pick up new users matching a conceptual definition.

## Advanced Options

The **Advanced Options Drawer** (`<AdvancedOptionsDrawer />`) exposes segment-level delivery rules that ride along on the segment as an `advanced` object. The frontend `SegmentDoc.advanced` shape today is:

### Frequency Capping (`advanced.frequencyCap`)

Limit how often the same user can be reached through this segment:

| Field | Description |
|-------|-------------|
| `count` | Maximum number of sends allowed within the window |
| `window.n` | Numeric length of the window |
| `window.unit` | `days`, `weeks`, or `months` |

### Deduplication (`advanced.dedupe`)

When the same user could match multiple conditions that would produce duplicate sends, pick the granularity at which to collapse them:

| Value | Meaning |
|-------|---------|
| `user` | One notification per user, even across devices |
| `device` | One notification per device — same user on two devices gets two |

### Cohorts (`advanced.cohorts`)

Scope the segment to a named cohort list (include / exclude) so A/B tests or canary rollouts can address a known slice:

| Field | Description |
|-------|-------------|
| `include` | Cohort IDs that *must* be present |
| `exclude` | Cohort IDs that *must not* be present |

The cohort IDs themselves are produced upstream (e.g. by a data-science pipeline) — the segment drawer consumes them rather than minting them, and advanced deterministic-bucket slicing is a backend concern.

## Overlap Detection

When saving a segment, `<SegmentOverlapDetector />` runs an asynchronous check: if an existing segment has ≥ 80 % of its members in common with the new one, the admin sees a warning and a list of overlapping segments. The warning is informational — the save still proceeds.

Useful for catching accidental duplicates like "Active learners in BD" vs "BD learners who are active".

## Segment List & Card Views

Route: `/admin/notification/segments`.

Two view modes:

- **Table view** (`<SegmentsTable />`) — sortable, filterable, bulk-selectable.
- **Card view** (`<SegmentCard />`) — visual grid showing name, size, type badge, last used.

Filters:

| Filter | Description |
|--------|-------------|
| **Search** | Name, description |
| **Type** | `DYNAMIC` / `STATIC` |
| **Size range** | Minimum / maximum users |
| **Last used** | Campaigns that used the segment within a date range |
| **Tags** | Free-form tag filter |

Bulk actions include delete, duplicate, and export (a segment's `user_ids` can be exported to CSV for offline use).

## Segment Detail

Route: `/admin/notification/segments/{id}`.

Sections:

| Section | Contents |
|---------|----------|
| **Summary** | Name, description, type, size, advanced options snapshot |
| **Filter preview** | For dynamic segments — the condition tree rendered read-only |
| **Members** | Paginated list (`GET /v1/admin/notify/segments/{id}/users`) |
| **Campaigns using this segment** | Related campaigns with their statuses |
| **Audit trail** | Who edited the segment and when |

## Creating a Segment

Route: `/admin/notification/segments/create`.

1. Pick **Dynamic** or **Static**.
2. Fill **Name**, **Description**, **Tags**.
3. **Dynamic**: build the condition tree; hit **Preview** to verify match count.
4. **Static**: upload a CSV or add users by search.
5. Open **Advanced Options** to set `frequencyCap`, `dedupe`, or `cohorts`.
6. **Save** — the backend resolves the initial size and persists.

API: `POST /v1/admin/notify/segments` (requires `notification.create`).

## Editing a Segment

Route: `/admin/notification/segments/{id}/edit`.

Edits re-resolve the segment; campaigns already running against this segment continue with their in-flight contact list — new sends/reruns pick up the new definition.

API: `PUT /v1/admin/notify/segments/{id}` (requires `notification.update`).

## Deleting a Segment

- Soft-delete if any campaign references it; the segment is marked inactive and hidden from the campaign wizard but remains for historical joins.
- Hard-delete if no campaign ever used it.

API: `DELETE /v1/admin/notify/segments/{id}` (requires `notification.delete`).

## Troubleshooting

| Issue | Solution |
|-------|----------|
| Segment size is 0 | Filters are too restrictive; use Preview with fewer conditions and incrementally re-narrow |
| Segment takes seconds to preview | Deep joins (enrollment, progress) are expensive — narrow the date window or add a status prefilter |
| Static segment is missing users after CSV upload | CSV rows with unknown emails are silently dropped; check the post-upload "skipped" summary |
| Cached size disagrees with live count | Cache is refreshed on save and at send time; call `/size` to force a recompute |
| Overlap warning spammy | Threshold is 80 % common membership; the warning is informational — acknowledge and proceed if intended |
| Fields I expect aren't in the builder | The field catalogue is served by `GET /v1/admin/notify/segments/fields` — a new source service needs to register its fields there |
| Cohort include/exclude has no effect | Cohort IDs must match what the upstream pipeline registered for this tenant; a typo silently matches zero users |
