# Scheduling

Every [Campaign](/docs/knowledgebase/notification-module/campaigns) carries a **schedule** — an instruction for *when* the dispatch should start. EduShade supports three schedule types, and recurring schedules use the standard iCalendar `RRULE` grammar for maximum flexibility.

## Schedule Types

| Type | Value | Behaviour |
|------|-------|-----------|
| **Immediate** | `IMMEDIATE` | Campaign begins dispatching as soon as it's sent |
| **Scheduled** | `SCHEDULED` | Campaign begins at `scheduled_at` (stored UTC) |
| **Recurring** | `RECURRING` | Campaign fires repeatedly on the cadence defined by `recurrence_rule` |

The schedule type is picked in step 4 of the campaign wizard and can be changed on any `DRAFT` or `SCHEDULED` campaign.

## Immediate Send

The simplest path:

1. Author the campaign.
2. Click **Send**.
3. Status transitions to `RUNNING` in seconds; the worker starts dispatching.

Use for ad-hoc announcements, urgent alerts, or any time the audience is ready and the content is final.

## Scheduled (One-off) Send

For a send that should happen at a specific future moment:

| Field | Description |
|-------|-------------|
| `scheduled_at` | ISO timestamp in UTC |
| `settings.timezone` | IANA timezone the UI used to compose the time — stored for auditability |

At save time, the campaign enters `SCHEDULED`. A periodic worker wakes up and transitions any `SCHEDULED` campaign whose `scheduled_at <= now()` into `RUNNING`.

Editing `scheduled_at` while `SCHEDULED` is supported — the new time is simply used on the next worker poll.

### Timezone Handling

- The UI displays every timestamp in the admin's browser timezone by default.
- Input fields offer a timezone picker so the admin can author "9 AM Dhaka" explicitly — the UI converts to UTC before sending.
- `settings.timezone` preserves the composition timezone so the detail page can re-render the intended local time even years later.

## Recurring Send

For periodic sends — weekly digests, monthly newsletters, daily reminder rollups — use `RECURRING` with an RRULE.

### RRULE Grammar

EduShade accepts standard iCalendar RRULE strings. A few common examples:

| Intent | RRULE |
|--------|-------|
| Daily at 9 AM | `FREQ=DAILY;BYHOUR=9;BYMINUTE=0;BYSECOND=0` |
| Weekly on Mondays at 8 AM | `FREQ=WEEKLY;BYDAY=MO;BYHOUR=8;BYMINUTE=0` |
| Every weekday at 6 PM | `FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR;BYHOUR=18` |
| First day of every month | `FREQ=MONTHLY;BYMONTHDAY=1` |
| Quarterly | `FREQ=MONTHLY;INTERVAL=3` |
| Every 2 weeks on Friday | `FREQ=WEEKLY;INTERVAL=2;BYDAY=FR` |
| 10 occurrences, then stop | `FREQ=WEEKLY;BYDAY=WE;COUNT=10` |
| Weekly until a specific date | `FREQ=WEEKLY;BYDAY=MO;UNTIL=20261231T000000Z` |

### How Recurring Dispatch Works

```
1. A recurring campaign lives in SCHEDULED between fires.
2. A periodic worker computes the next occurrence from RRULE + last run.
3. When next_occurrence <= now():
   - The campaign transitions to RUNNING for this occurrence
   - The segment is re-resolved (so the audience reflects the current state)
   - Counters update as the occurrence dispatches
4. When the occurrence finishes, the campaign returns to SCHEDULED,
   and next_occurrence is recomputed.
5. If the RRULE has terminated (COUNT or UNTIL exhausted), the campaign
   transitions to COMPLETED.
```

The exact re-evaluation cadence is a backend configuration and is not enforced by the frontend.

### Occurrence History

Each recurring occurrence contributes its delivery logs into the campaign's running total. The detail page's [Delivery Logs](/docs/knowledgebase/notification-module/delivery-logs) and [Analytics](/docs/knowledgebase/notification-module/analytics) surfaces are scoped to the campaign — per-occurrence slicing depends on delivery-log timestamps, not a first-class `occurrence_id` field in the current frontend types.

## Schedule-Related Settings

Further scheduling controls live in `CampaignSettings`:

| Setting | Description |
|---------|-------------|
| `timezone` | IANA zone the RRULE is interpreted in; defaults to the tenant's default timezone |
| `quiet_hours_enabled` | Campaign-level quiet hours — shifts dispatch out of DND windows |
| `quiet_hours_start` / `quiet_hours_end` | `HH:MM` in `timezone` |
| `skip_recent_contacts` | Drop recipients who received *any* campaign in the last N days |
| `skip_recent_days` | N for the skip-recent rule |

See [Quiet Hours](/docs/knowledgebase/notification-module/quiet-hours) for how quiet-hour windows interact with the dispatch loop.

## Lifecycle Transitions

| From → To | Trigger |
|-----------|---------|
| `DRAFT` → `SCHEDULED` | Admin sends a campaign whose `scheduled_at` is in the future |
| `DRAFT` → `RUNNING` | Admin sends with `IMMEDIATE` or a past `scheduled_at` |
| `SCHEDULED` → `RUNNING` | Worker hits `scheduled_at` (or next RRULE occurrence) |
| `RUNNING` → `PAUSED` | Admin clicks **Pause** |
| `PAUSED` → `RUNNING` | Admin clicks **Resume** |
| `RUNNING` → `COMPLETED` | Every recipient processed for the current occurrence |
| Recurring `RUNNING` → `SCHEDULED` | Occurrence finished; more remain |
| Recurring `SCHEDULED` → `COMPLETED` | RRULE terminated |
| Any → `CANCELLED` | Admin clicks **Cancel** |

## Pausing and Resuming

- **Pause** halts new per-recipient handoffs; in-flight provider calls complete.
- **Resume** picks back up from where the dispatch left off — no re-send of already-dispatched recipients.
- Pausing a recurring campaign freezes the current occurrence only; the next occurrence will fire on schedule unless cancelled.

## Backfill & Catch-Up

If a recurring worker is offline across one or more occurrences, missed runs are not auto-blasted on recovery. The **Rerun** action (`POST /v1/admin/notify/campaigns/{id}/rerun`) lets an admin fire a manual occurrence against the current segment membership to cover a gap. Exact backfill policy (time-window, pacing) is set by the dispatch service, not the frontend — consult the dispatch worker's runbook before relying on automatic catch-up.

## API Reference

| Endpoint | Method | Purpose |
|----------|--------|---------|
| `/v1/admin/notify/campaigns/{id}/send` | POST | Apply the schedule — `IMMEDIATE` fires now; `SCHEDULED`/`RECURRING` transition to `SCHEDULED` |
| `/v1/admin/notify/campaigns/{id}/pause` | POST | Halt the current occurrence |
| `/v1/admin/notify/campaigns/{id}/resume` | POST | Resume a paused occurrence |
| `/v1/admin/notify/campaigns/{id}/cancel` | POST | Cancel the current occurrence and (for recurring) stop future occurrences |
| `/v1/admin/notify/campaigns/{id}/rerun` | POST | Trigger a manual occurrence (outside the recurrence schedule) |

All schedule-related transitions are recorded in the [Audit Logs](/docs/knowledgebase/notification-module/audit-logs).

## Troubleshooting

| Issue | Solution |
|-------|----------|
| Scheduled campaign never fires | Confirm `scheduled_at` is in the future at save time; the worker polls periodically so a scheduled time within the poll window may lag briefly |
| RRULE rejected | Validate with a standard iCalendar parser; common errors: missing `FREQ=`, invalid `BYDAY` codes (use `MO`, `TU`, `WE`, `TH`, `FR`, `SA`, `SU`) |
| Recurring campaign fires twice | Usually two workers concurrently processed the same occurrence — duplicate dispatch is a dispatch-worker concern; verify per-recipient delivery logs before assuming double-send |
| Wrong time on recipient devices | `scheduled_at` is UTC; the recipient-local time is driven by their own timezone, not the campaign's |
| Pause didn't stop an email already mid-flight | Correct — in-flight provider calls complete before the worker checks `paused`; subsequent recipients are held |
| Backfill blasted many notifications | Check `skip_recent_contacts` and `skip_recent_days` — set them to avoid slamming users on a worker restart |
| Campaign stuck in `SCHEDULED` past its time | Scheduled worker may be paused or misconfigured; check service health |
