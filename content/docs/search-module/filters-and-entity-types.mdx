# Filters & Entity Types

Every search query runs against one Typesense collection per tenant (`search_{tenantID}`) but callers can narrow the result set with four optional filters. All filters are combined with AND.

## Query Parameters

| Param | Type | Default | Description |
|-------|------|---------|-------------|
| `q` | string | — | The raw query. Sent to Typesense with `query_by = title,description,tags` |
| `entity_type` | string | all | Restrict to one entity type (see table below) |
| `status` | string | `published` | Document status. When omitted, the service defaults to `published` unless `include_drafts=true` is set |
| `language` | string | all | The document's primary language (matches the `language` field, not the localized title/description keys) |
| `include_drafts` | boolean | `false` | Admin use only — disables the default `status:=published` filter |
| `page`, `per_page` | int | `1`, `20` | Pagination. `per_page` is capped at **100** server-side |

These map to Typesense's `filter_by`:

```
tenant_id:={tenantID}
[&& entity_type:={entity_type}]
[&& status:={status | published}]
[&& language:={language}]
```

The `tenant_id` filter is **always** applied — there is no way to opt out.

## Entity Types

The `entity_type` field is both a **facetable** and a **filterable** field on the Typesense schema.

| Value | Description |
|-------|-------------|
| `course` | Individual courses |
| `learning_path` | Ordered learning paths |
| `post` | Blog / announcement posts |
| `page` | Static or landing pages from the website builder |
| `product` | E-commerce products |
| `booking` | Consultation / meeting plans |
| `event` | Live events |
| `cohort` | Cohort offerings |
| `bundle` | Bundles of courses or products |

> The schema also tolerates additional types (e.g. `meeting_plan`) routed by individual source services. If you're introducing a new entity type, the search schema does not need to change — add the mapping in `search-service/models/mappers.go` and publish events with the new `entity_type`.

## Status

The `status` field tracks document lifecycle and is **facetable**.

| Value | Meaning |
|-------|---------|
| `draft` | In-progress document; never returned to public callers |
| `published` | Live, visible to everyone |
| `archived` | Retired — retained in the index but hidden by the default filter |

### Default Behaviour

- **Public search** (`/api/v1/public/search`): defaults to `status:=published`. Passing `include_drafts=true` is accepted by the handler but the public endpoint still applies `status:=published` unless an explicit `status` is provided — in practice, only admin callers with a known status value should override.
- **Admin search** (`/api/v1/admin/search`): same handler, but authenticated. Admins use `include_drafts=true` to see draft documents alongside published ones. See [Admin Search](/docs/knowledgebase/search-module/admin-search).

### Override Logic

The server builds the filter in this order (`search-service/services/search_service.go::Search`):

```
1. filters += "tenant_id:={tenantID}"
2. if entity_type is set    → filters += "entity_type:={entity_type}"
3. if status is set          → filters += "status:={status}"
   else if !include_drafts   → filters += "status:=published"
   else                      → no status filter (all statuses returned)
4. if language is set        → filters += "language:={language}"
```

So an admin can see **all statuses** across drafts and archives by sending `include_drafts=true` with **no explicit `status`**.

## Language

The `language` field on the search document is distinct from the localized `title` / `description` maps. It represents the document's **primary language** — useful for multi-language catalogues where a course is authored in Arabic and should only appear for Arabic visitors.

- Facetable — see [Facets](/docs/knowledgebase/search-module/facets) for counts.
- Filterable with `language=en`, `language=ar`, etc.
- Not tied to locale fallback: the query will return zero results if the document has no `language` or a different one than the filter value.

To show a title in multiple languages regardless of the `language` filter, rely on the **localized `title` map** instead — see [Localization](/docs/knowledgebase/search-module/localization).

## Pagination

| Behaviour | Value |
|-----------|-------|
| Default page size | `20` |
| Max page size | `100` (hard-capped by the handler) |
| Default page | `1` |
| Zero/negative values | Coerced to defaults |

Response includes a `pagination` object: `total`, `current_page`, `total_pages`, `per_page`.

## Frontend Defaults

The `SearchResults` component passes `entityType`, `status`, and `language` through as optional props. When it is mounted from the search bar, none of them are set — the call therefore defaults to "all entity types, published, all languages".

A caller page (e.g. a dedicated "Courses" search) can pin a single entity type by passing `<SearchResults entityType="course" />`.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| Draft documents leak into public results | Don't override `status` on the public endpoint. The default `status:=published` filter is only skipped when an **explicit** `status` is provided |
| Empty results for a query that works without filters | Each filter narrows by AND. Drop filters one at a time to identify the offending one (often `language` or `status`) |
| Admin sees no drafts even with `include_drafts=true` | Make sure no `status` is explicitly set — setting both overrides the include-drafts bypass |
| `entity_type` returns zero rows for a new type | Confirm the source service is publishing `search.document.created` events with that exact `entity_type` — see [Indexing Pipeline](/docs/knowledgebase/search-module/indexing-pipeline) |
| Cross-tenant leakage | Not possible — `tenant_id` is always part of the filter and is resolved from the authenticated context, not the request body |
