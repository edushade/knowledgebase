# Click Tracking

Click tracking ties a search result the user actually opened back to the [search history](/docs/knowledgebase/search-module/search-history) row that produced it. That link powers [Trending Results](/docs/knowledgebase/search-module/trending#trending-results) and feeds click-through signals into analytics.

The write is a single POST from the client after a result is opened. It updates the `clicked_result_id` column on the existing history row — no separate click-events table.

## Endpoint

- **Public:** `POST /api/v1/public/search/click`
- **Admin:** `POST /api/v1/admin/search/click` (authenticated)
- **Handler:** `search-service/api/handlers/search_history_handler.go::TrackClick`
- **Service:** `search-service/services/search_history_service.go::TrackClick`

### Request Body

```
{
  "history_id": "3f5c...",
  "result_id":  "course_abc"
}
```

| Field | Type | Description |
|-------|------|-------------|
| `history_id` | UUID | The `metadata.history_id` returned from the search response that produced the click |
| `result_id` | string | The document ID clicked — `{entity_type}_{uuid}` (e.g. `course_7b4e...`) |

### Response

```
{
  "success": true,
  "message": "Click tracked successfully"
}
```

## What It Does

Runs a single update scoped to the caller:

```sql
UPDATE search_history
SET clicked_result_id = :result_id
WHERE id = :history_id
  AND tenant_id = :tenant_id
  AND (user_id = :user_id OR session_id = :session_id)
```

Ownership is enforced in the WHERE clause. A click on somebody else's history row returns `search history not found or access denied`.

> Only one click per history row is stored — if the user clicks a second result from the same search, the newer `result_id` overwrites the previous one. This is intentional: for trending purposes the "terminal result" matters most.

## When The Client Calls It

The `SearchResultItem` component wires this automatically. On a result click:

1. Read `history_id` from the most recent search response's `metadata`.
2. Fire `apiClient.trackSearchClick({ history_id, result_id })`. The call is fire-and-forget — errors are swallowed so failed tracking never blocks navigation.
3. Navigate to the result's URL (see the routing table in [Search Results](/docs/knowledgebase/search-module/search-results#routing)).

If the search response omitted `history_id` (e.g. the history write failed), the client skips the call.

## Why On History, Not Separate Events

The system deliberately **does not** keep a `search_clicks` table. Reasoning:

- Every click already has a known antecedent row (the history entry) — a separate table would duplicate tenant/user/session/query fields.
- Trending results queries need to join clicks back to queries anyway; keeping them co-located on `search_history` turns that join into a single scan.
- Retention is unified — when `search_history` rows age out at 90 days, their click records age out with them.

The trade-off is the "only-last-click" rule above. If per-click fidelity ever becomes necessary, the column would be promoted to its own table at that point.

## Downstream Consumers

| Consumer | How it uses clicks |
|----------|---------------------|
| [Trending Results](/docs/knowledgebase/search-module/trending#trending-results) | Aggregates `clicked_result_id` counts per-document across two windows to rank by growth |
| [Search Analytics](/docs/knowledgebase/search-module/search-analytics) | Not currently aggregated into the analytics table — clicks live only on the history rows |
| Admin dashboards | Can join `search_history` on `clicked_result_id` for click-through rate breakdowns |

## Parameters & Limits

| Parameter | Value |
|-----------|-------|
| Request method | `POST` |
| Rate limit | Same as the rest of the search-service (see [Filters & Entity Types](/docs/knowledgebase/search-module/filters-and-entity-types)) |
| Idempotency | A repeated POST is a no-op re-UPDATE of the same row |

## Troubleshooting

| Issue | Solution |
|-------|----------|
| `search history not found or access denied` on every click | The `history_id` belongs to a different user/session. Usually happens when the user logs in between searching and clicking — the scoping flipped from session to user. Re-search before clicking |
| Trending Results is empty despite heavy traffic | No one clicked. Views, scrolls, and hovers are not tracked. Only `POST /click` populates the signal |
| Click goes through but column stays `NULL` | The client silently dropped the call (fire-and-forget). Check the browser Network tab; typical causes are a race where `history_id` wasn't yet hydrated, or a 4xx auth error being swallowed |
| Wrong result_id format | The service doesn't validate format — it just stores the string. Always send the full document ID (`{entity_type}_{uuid}`) exactly as it appeared in the search response, otherwise the trending ID filter won't match |
