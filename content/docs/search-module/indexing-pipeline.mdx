# Indexing Pipeline

The search service does not own content — every indexed document is a **mirror** of something owned by another service (Course, CMS, Product, Booking, Event, etc.). The mirror is kept in sync by an **event-driven pub/sub pipeline**: owning services publish lifecycle events, the search service subscribes, maps the payload into a unified [SearchDocument](#document-shape), and upserts or deletes it in Typesense.

No polling, no direct DB joins, no service-to-service HTTP. Every change flows through three topics.

## High-Level Flow

```
┌─────────────────┐   publish    ┌─────────────┐   subscribe    ┌──────────────────┐
│ Owning service  │ ───────────► │   Pub/Sub   │ ─────────────► │ search-service   │
│ (course, post…) │              │   broker    │                │ subscriber       │
└─────────────────┘              └─────────────┘                └────────┬─────────┘
                                                                          │ map + upsert
                                                                          ▼
                                                                 ┌──────────────────┐
                                                                 │    Typesense     │
                                                                 │ search_{tenant}  │
                                                                 └──────────────────┘
```

## Topics

The subscriber listens on three topics. Every message carries a JSON payload and metadata headers (`tenant_id`, `entity_type`, `entity_id`).

| Topic | Handler | What It Does |
|-------|---------|--------------|
| `search.document.created` | `handleDocumentCreated` | Map the entity payload into a `SearchDocument` and upsert to Typesense |
| `search.document.updated` | `handleDocumentUpdated` | Identical to `created` — Typesense upsert is idempotent, so update and create share code |
| `search.document.deleted` | `handleDocumentDeleted` | Delete the document by composite ID (`{entity_type}_{entity_id}`) |

Subscribers are registered at service start by `services/subscriber_service.go::StartSubscribers` and run as three background goroutines until the process context is cancelled.

### Retry Policy

Messages are processed by `pubsub.ProcessMessagesWithRetry` with `pubsub.DefaultRetryConfig()`. The checker marks the following errors as **non-retryable** so they don't block the queue forever:

- `invalid entity type`
- `invalid payload`

Everything else (transient DB / Typesense / network errors) is retried. The exact retry count, backoff, and dead-letter behaviour come from the `edushade-common/pkg/pubsub` defaults.

## Per-Tenant Collections

Each tenant has its own Typesense collection: `search_{tenantID}` (collision-safe, simple tenant isolation). The prefix is configurable:

```yaml
typesense:
  collection_prefix: "search"   # "" → defaults to "search"
```

`TypesenseClient.GetCollectionName(tenantID)` builds the name. Callers **always** pass `tenantID` as a string — the routes / handlers layer validates that it's a UUID before it reaches the service.

> One collection per tenant means tenant isolation is structural, not just a filter. A misconfigured query can't leak another tenant's documents because they live in a different collection. The `tenant_id` filter on top is defence-in-depth.

### Collection Lifecycle

- `EnsureCollection(ctx, tenantID)` — creates the collection on demand. Called automatically before every index write; idempotent (409 Conflict → success).
- `RecreateCollection(ctx, tenantID)` — deletes + re-creates. Use for **schema migrations** and **backfills** only; it wipes the tenant's index.

## Document Shape

Every entity type maps into the same document shape, defined by `models/search_document.go::SearchDocument`:

| Field | Type | Facet / Sort | Notes |
|-------|------|---------------|-------|
| `id` | string | — | Composite: `{entity_type}_{entity_id}` |
| `tenant_id` | string | facet | UUID as string |
| `entity_type` | string | facet | `course`, `learning_path`, `post`, `page`, `product`, `meeting_plan`, `event`, `cohort`, `bundle` |
| `entity_id` | string | — | Source entity's UUID |
| `title` | object (map) | — | Localized: `locale → content`; required |
| `description` | object (map), optional | — | Localized: `locale → content` |
| `slug` | string, optional | — | URL slug (non-localized; the routing table composes locale + slug) |
| `thumbnail` | string, optional | — | Image URL |
| `status` | string | facet | `draft`, `published`, `archived` |
| `published_at` | int64, optional | sort | Unix timestamp; falls back to `created_at` in the mapper |
| `tags` | string[], optional | facet | Used for both retrieval and potential future faceting |
| `language` | string, optional | facet | Primary language code — powers the `language` filter |
| `metadata` | object, optional | — | Entity-specific extra fields (price, level, duration, etc.) |
| `created_at` | int64 | sort | Unix timestamp; default sort field |
| `updated_at` | int64 | sort | Unix timestamp |

`EnableNestedFields: true` is set on the schema so Typesense indexes inside the localized `title` / `description` maps (that's what powers per-locale highlights — see [Localization](/docs/knowledgebase/search-module/localization)).

### Why Unix Timestamps

Typesense sorts numerically. `int64` Unix timestamps sort correctly and round-trip through Typesense's float64 JSON without precision loss for any plausible date. The `UnmarshalJSON` helper accepts `float64`, `int64`, or `int` because Typesense may return any of them.

## Entity Mappers

Every supported entity type has a dedicated mapper in `models/mappers.go`. `MapEntityByType` is the single entry point:

| `entity_type` | Mapper |
|---------------|--------|
| `course` | `MapCourse` |
| `learning_path` | `MapLearningPath` |
| `post` | `MapPost` |
| `page` | `MapPage` |
| `product` | `MapProduct` |
| `meeting_plan` | `MapMeetingPlan` |
| `event` | `MapEvent` |
| `cohort` | `MapCohort` |
| `bundle` | `MapBundle` |
| anything else | `mapEntityGeneric` fallback |

Each mapper:

1. Extracts the entity's primary fields (ID, title, description, status, slug, thumbnail, tags, language, published_at).
2. Normalises `title` and `description` into a `map[string]string` (localized). If the source is a plain string, the helper `stringToEnLocale` wraps it under the `"en"` key.
3. Packs any entity-specific extras (e.g. course level, product price) into `metadata`.
4. Ensures `published_at` is set — falling back to `created_at`, or `0` if neither is present (see `EnsurePublishedAt`).

> The generic fallback (`mapEntityGeneric`) is permissive but not ideal — it only picks up `id`, `title`/`name`, and generic fields. Adding a new entity type means writing a proper mapper in `mappers.go` and extending the `MapEntityByType` switch.

## Write Paths

### Single Index

`IndexService.IndexDocument(ctx, tenantID, doc)`:

1. Ensure the per-tenant collection exists.
2. Compute the composite `id = {entity_type}_{entity_id}`.
3. Typesense `Documents.Upsert(doc)`.

### Batch Index

`IndexService.IndexDocuments(ctx, tenantID, docs)`:

- Imports with `action = "upsert"`, `batch_size = 100`.
- Used for backfills and migrations (called from tooling, not from subscribers).
- Failures are logged per document; the batch does not abort on partial failure.

### Delete

`IndexService.DeleteDocument(ctx, tenantID, entityType, entityID)`:

- Deletes by composite ID.
- `404 Not Found` is swallowed — deleting an already-gone document is a no-op.

`IndexService.DeleteDocumentsByType(ctx, tenantID, entityType)` is available for mass-delete operations (used by admin tooling, not subscribers).

## Identity: Composite ID

The document `id` is always `{entity_type}_{entity_id}`. This matters because:

- Click tracking refers to results by exactly this string (see [Click Tracking](/docs/knowledgebase/search-module/click-tracking)).
- Trending Results hydrates by a Typesense `id` filter with the same composite (see [Trending](/docs/knowledgebase/search-module/trending)).
- Entity IDs are not globally unique across tables (two different services could legally mint the same UUID); prefixing with `entity_type` makes the search-service namespace collision-free.

## Cold Start / Backfill

On first deployment, or when onboarding a new tenant, the index is empty. Three options to populate it:

1. **Passive** — every edit in the owning services eventually publishes a `search.document.updated`, which re-upserts the document. Fine for low-traffic content.
2. **Active backfill** — owning service iterates its rows and publishes `search.document.created` for each. The search service upserts as normal. This is the recommended path for full populations.
3. **Recreate + backfill** — call `RecreateCollection(tenantID)` to wipe and rebuild the Typesense collection before the backfill. Only necessary after a schema change.

There is currently no HTTP endpoint on the search service to trigger these; they are admin / ops operations run from the owning services' CLIs.

## Failure Modes & Observability

| Failure | What Happens | Where to Look |
|---------|--------------|---------------|
| Unknown `entity_type` | Subscriber calls `mapEntityGeneric` — document is partial but still indexed | search-service logs — `failed to map entity to search document` is a hard skip |
| Typesense 401 | `EnsureCollection` returns a wrapped auth error | check `typesense.api_key` in config — must be an **admin** key, not search-only |
| Typesense 409 on create | Collection already exists — treated as success | No action needed |
| Tenant ID missing from message | `handleDocumentCreated` returns an error; message goes back to retry | Owning service must emit `tenant_id` in metadata *or* payload |
| Retry loop on non-transient error | The checker's `WithNonRetryableErrors` list stops the loop | Add new non-retryable error substrings here if a hot loop appears |

## Parameters & Limits

| Parameter | Value |
|-----------|-------|
| Topics | `search.document.created`, `search.document.updated`, `search.document.deleted` |
| Collection naming | `search_{tenantID}` (prefix configurable) |
| Batch size (import) | `100` |
| Default sort field | `created_at` |
| Non-retryable substrings | `invalid entity type`, `invalid payload` |

## Troubleshooting

| Issue | Solution |
|-------|----------|
| Edit to a course doesn't show up in search | Confirm the course service emitted `search.document.updated`. Check search-service logs for the matching message. Pub/sub consumer lag can also delay it by seconds |
| Deleted course still shows up | Either the delete event wasn't published, or the subscriber failed and retried out. Re-run a delete from the owning service to republish |
| Search returns archived/draft items to the public | Check the `status` filter logic on the search request — public calls default to `status:=published` unless `include_drafts=true` is set by an admin call. See [Admin Search](/docs/knowledgebase/search-module/admin-search) |
| Backfill took hours and some docs are missing | Typesense returns per-doc errors on batch import — check the logs for `Document indexing failed`. Often the cause is a malformed `title` map (empty after extraction) |
| Different tenants see each other's content | Should be impossible — collections are per-tenant. If it happens, check `GetCollectionName` and the `tenant_id` filter. Both apply |
| `RecreateCollection` run by accident | The tenant's index is gone until a backfill. The owning services are the source of truth; trigger a full re-publish |
