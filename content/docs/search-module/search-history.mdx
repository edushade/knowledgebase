# Search History

Every submitted search is recorded in the `search_history` table, scoped to the **tenant** and to either a **user** (when authenticated) or a **session** (for anonymous visitors). The history powers the "Recent" section of the search bar, feeds the analytics aggregator, and anchors click tracking.

Entries written inside a short **deduplication window** update an existing row instead of inserting a new one, so repeated searches don't flood the table.

## Data Model

`search_history` row shape (from `search-service/models/search_history.go`):

| Column | Type | Notes |
|--------|------|-------|
| `id` | UUID | Primary key |
| `tenant_id` | UUID | Always scoped |
| `user_id` | UUID, nullable | Set when the caller is authenticated |
| `session_id` | string, nullable | Set when the caller is anonymous |
| `query` | string | The exact query string as submitted |
| `filters` | JSONB, nullable | Copy of the filters applied on the request |
| `result_count` | int, nullable | Number of hits Typesense returned |
| `clicked_result_id` | string, nullable | Populated later via [Click Tracking](/docs/knowledgebase/search-module/click-tracking) |
| `created_at` | timestamptz | Refreshed to `now()` on dedupe hits |

### Anonymous Session ID

For anonymous callers, the handler derives a stable session ID:

```
sessionID = hex( sha256(ip + ":" + userAgent) )[:16]
```

Same browser + same IP → same session ID. This is intentionally coarse: it means history follows a device, not a cookie.

> The hash is truncated to 16 bytes (32 hex chars). Different User-Agent strings produce different IDs, so browser upgrades or UA spoofing will fork history.

## Writing History

History is **written automatically** by the `/search` and `/search/facets` handlers after a successful query — the client does **not** need to POST anything itself.

### Dedupe Rule

Defined in `SearchHistoryService.CreateHistory`. A new entry is **merged into an existing row** when all of the following match within the last **30 minutes**:

1. Same `tenant_id`.
2. Same `user_id` (authenticated) *or* same `session_id` (anonymous).
3. Exact `query` string match (case-sensitive, whitespace-sensitive).
4. Equivalent `filters` map (keys + values must match; the map is compared value-by-value).

When all four match, the existing row's `created_at` is reset to now and `result_count` is overwritten with the new total. Otherwise a fresh row is inserted.

> Comparing `filters` value-by-value means a change in entity type, language, or status override breaks the dedupe and writes a new row. This keeps "same query, different filter" distinct in history.

### History ID Returned

When the `/search` handler successfully writes or refreshes a history row, it surfaces the ID in the response:

```
metadata: {
  history_id: "3f5c..."
}
```

The client persists this ID for the subsequent [Click Tracking](/docs/knowledgebase/search-module/click-tracking) call — click events reference the history row they belong to.

## Reading History

- **Public:** `GET /api/v1/public/search/history`
- **Admin:** `GET /api/v1/admin/search/history` (authenticated)
- **Handler:** `search-service/api/handlers/search_history_handler.go::GetHistory`
- **Service:** `search-service/services/search_history_service.go::GetHistory`

### Query Parameters

| Param | Type | Default | Description |
|-------|------|---------|-------------|
| `page` | int | `1` | 1-indexed page number |
| `per_page` | int | `20` | Items per page. Clamped to `[1, 100]` |

### Response

```
{
  "data": [
    {
      "id": "3f5c...",
      "user_id": "...",
      "query": "figma basics",
      "filters": { "entity_type": "course" },
      "result_count": 12,
      "clicked_result_id": "course_abc",
      "created_at": "2026-04-22T09:31:00Z"
    }
  ],
  "pagination": { "page": 1, "per_page": 20, "total": 87, "total_pages": 5 }
}
```

Entries are ordered `created_at DESC` — newest first. Tenant and user/session scoping is applied in SQL; callers cannot see other users' history.

### Scope Resolution

The handler picks the scope per call:

1. If the request has a valid auth context → `user_id = current_user_id`.
2. Else → `session_id = generateSessionID(clientIP, userAgent)`.
3. If neither is available → returns an empty page.

## Deleting History

### Single Entry

- `DELETE /api/v1/public/search/history/:id`
- `DELETE /api/v1/admin/search/history/:id`

The service enforces ownership: the `DELETE` runs with `user_id = current` or `session_id = current` as an extra predicate. If the row doesn't belong to the caller, the delete affects zero rows and the handler returns `search history not found or access denied`.

### All Entries

- `DELETE /api/v1/public/search/history`
- `DELETE /api/v1/admin/search/history`

Removes every row for the current `(tenant_id, user_id | session_id)` tuple. There is no soft-delete — rows are hard-deleted from the table.

## Retention

Rows older than the configured retention window are removed by the analytics aggregator at midnight. See [Search Analytics](/docs/knowledgebase/search-module/search-analytics#retention-cleanup).

| Parameter | Value |
|-----------|-------|
| Retention window | `90 days` (configurable via `search_features.history_retention_days`) |
| Cleanup trigger | First aggregator tick after midnight UTC (hour `0`, minute `< 5`) |

## Frontend Integration

The [Search Bar](/docs/knowledgebase/search-module/search-bar) renders a **Recent** section when the input is empty:

- Calls `apiClient.getSearchHistory({ page: 1, per_page: 5 })` on mount and on focus.
- Renders each entry as a clickable row; clicking one re-runs the query.
- Shows an inline "X" per row that calls `deleteSearchHistoryEntry(id)` and optimistically removes the row.
- Shows a footer "Clear all" link that calls `clearSearchHistory()` and empties the list.

A dedicated `SearchHistoryList` component (used on the account / profile surface) renders the full paginated view with the same endpoint.

## Parameters & Limits

| Parameter | Value |
|-----------|-------|
| Dedup window | `30 minutes` |
| Default `per_page` | `20` |
| Max `per_page` | `100` (hard-capped) |
| Session ID hash | `sha256(ip + ":" + ua)[:16]` |
| Retention | `90 days` (configurable) |

## Troubleshooting

| Issue | Solution |
|-------|----------|
| Same query appears twice back-to-back | Filters differed (e.g. language override); dedupe treats those as distinct. Compare the `filters` map across the two rows |
| Anonymous history disappears after switching networks | Session ID is derived from IP + User-Agent. Changing network → new IP → new session. Expected behaviour — log in to persist |
| `history_id` missing from search response | The write failed silently (usually a DB timeout) or the tenant ID didn't parse as UUID. Check search-service logs |
| "Clear all" doesn't delete a row seen in the UI | The row probably belongs to a different session (e.g. cached from a previous User-Agent). Confirm the scope by fetching history fresh |
| Old entries never age out | The analytics aggregator only runs cleanup between `00:00` and `00:05` UTC. Confirm the aggregator is running and the clock is correct |
| `per_page=500` returns only 100 | Expected — capped at 100 in the service layer |
