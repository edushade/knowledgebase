# Search Analytics

The analytics layer turns raw `search_history` rows into a compact, daily-grained aggregate in the `search_analytics` table. Every "popularity-ranked" feature in the search module reads from this aggregate:

- [Popular Searches](/docs/knowledgebase/search-module/popular-searches) — top queries by sum.
- [Did You Mean](/docs/knowledgebase/search-module/did-you-mean) — candidate pool.
- [Related Searches](/docs/knowledgebase/search-module/related-searches) — top queries excluding the current one.
- [Trending Searches](/docs/knowledgebase/search-module/trending) — two-window growth ratio.

The aggregation is done by a background job, not inline on write. This keeps the search path O(1) and lets the rest of the module treat `search_analytics` as a cheap lookup table.

## Data Model

`search_analytics` row (from `search-service/models/search_analytics.go`):

| Column | Type | Notes |
|--------|------|-------|
| `id` | UUID | Primary key |
| `tenant_id` | UUID | Always scoped |
| `query` | string | Exact query string as seen in history |
| `date` | date | UTC calendar day |
| `search_count` | int | Total searches that day for `(tenant, query)` |
| `unique_users` | int | `COUNT(DISTINCT user_id)` where `user_id IS NOT NULL` |
| `unique_sessions` | int | `COUNT(DISTINCT session_id)` where `session_id IS NOT NULL` |
| `avg_result_count` | decimal(10,2), nullable | `AVG(result_count)` that day |
| `created_at`, `updated_at` | timestamptz | Standard audit columns |

Primary uniqueness is `(tenant_id, query, date)` — the aggregator upserts on that tuple.

## The Aggregator Job

- **Job:** `search-service/jobs/analytics_aggregator.go::AnalyticsAggregatorJob`
- **Service:** `search-service/services/search_analytics_service.go::AggregateHistory`
- **Cadence:** every `search_features.analytics_aggregation_interval` (default `1h`).
- **Cleanup slot:** triggered on any tick that fires between `00:00` and `00:05` UTC. Skipped (not made up) if the service is down during that window.

### What Each Tick Does

1. `SELECT DISTINCT tenant_id FROM search_history` — one pass to list tenants.
2. For each tenant, re-aggregate two days: **yesterday** and **today** (UTC).
3. For each date, run:
   ```sql
   SELECT
     query,
     COUNT(*) AS search_count,
     COUNT(DISTINCT user_id)    FILTER (WHERE user_id IS NOT NULL)    AS unique_users,
     COUNT(DISTINCT session_id) FILTER (WHERE session_id IS NOT NULL) AS unique_sessions,
     AVG(result_count)                                                 AS avg_result_count
   FROM search_history
   WHERE tenant_id = :tenant
     AND DATE(created_at) = :date
   GROUP BY query;
   ```
4. For each resulting row, upsert into `search_analytics` with:
   ```sql
   ON CONFLICT (tenant_id, query, date) DO UPDATE
     SET search_count    = EXCLUDED.search_count,
         unique_users    = EXCLUDED.unique_users,
         unique_sessions = EXCLUDED.unique_sessions,
         avg_result_count = EXCLUDED.avg_result_count,
         updated_at      = EXCLUDED.updated_at;
   ```

Because each tick fully **replaces** the values for yesterday + today, the aggregate is always correct up to the most recent tick. Historical days (before yesterday) are written once and then left alone — they don't need re-aggregation because their underlying history rows are sealed.

> The job runs immediately on service start and then every interval. If the service was offline for a few hours, the first restart tick will reconstruct yesterday + today from history, so short outages don't create gaps.

## Retention Cleanup

`CleanupOldHistory` deletes old rows from `search_history`:

```
cutoff = now() - HistoryRetentionDays
DELETE FROM search_history WHERE created_at < cutoff
```

It runs inline with the aggregator tick, but only when `now().Hour == 0 && now().Minute < 5` UTC. In practice this means cleanup happens on **the first tick of each day that falls inside the 00:00–00:05 UTC window**. If the service is down during that window, cleanup is simply skipped until the next day — missed runs are never made up. At the default aggregation interval (`1h`), exactly one tick lands in that window per day; at shorter intervals multiple ticks may qualify, but the extra deletes are no-ops once the first one succeeds.

| Parameter | Value |
|-----------|-------|
| Retention window | `90 days` (configurable via `search_features.history_retention_days`) |
| Trigger | Any aggregator tick where `now().Hour == 0 && now().Minute < 5` UTC |

Only `search_history` is cleaned up — `search_analytics` rows are **not** removed. The per-day aggregate is compact enough that it can stay indefinitely, which lets long-tail popular/trending computations look back further than the raw history window.

## What Is Aggregated

| Field in history | Field in analytics | Notes |
|------------------|---------------------|-------|
| `query` (exact string) | `query` | No trimming or case folding — matches history byte-for-byte |
| `user_id` | `unique_users` | Nullable rows excluded from the `DISTINCT` count |
| `session_id` | `unique_sessions` | Same |
| `result_count` | `avg_result_count` | Null-safe — SQL `AVG` ignores nulls |
| `clicked_result_id` | — | Not aggregated here. See [Click Tracking](/docs/knowledgebase/search-module/click-tracking) |

Clicks are intentionally **not** copied into `search_analytics`. Trending Results reads clicks directly from `search_history`, so the click signal stays responsive to real-time events without waiting for the next aggregation tick.

## Timezones

All dates are bucketed by **UTC calendar day** (via `DATE(created_at)` in Postgres, which uses the column's timezone — `timestamptz` stored as UTC). A tenant operating in a non-UTC region will see its "day" boundaries shifted. If day-of-week analytics matter for a tenant, the dashboard should re-bucket in the client.

## Frontend Exposure

There is no public "give me my analytics" endpoint. The table is read internally by:

| Reader | Endpoint |
|--------|----------|
| `SearchSuggestionsService.GetPopularSearches` | `GET /search/suggestions` |
| `SearchSuggestionsService.GetRelatedSearches` | Inline in `/search` metadata |
| `QuerySuggestionService.GetSuggestion` | Inline in `/search` metadata |
| `TrendingService.GetTrendingSearches` | `GET /search/trending` |

To build admin dashboards on top of `search_analytics`, query the table directly from the analytics DB layer — it is not currently exposed via HTTP.

## Cold Start Behaviour

On a fresh deployment, `search_analytics` is empty. Until the first aggregator tick runs (within one interval, default `1h`), every feature that depends on it returns empty:

- Popular Searches: `{ suggestions: [] }`.
- Did You Mean: `metadata.did_you_mean` omitted.
- Related Searches: `metadata.related_searches` omitted.
- Trending Searches: `{ searches: [] }`.

Trending Results is the **exception** — it reads clicks directly from `search_history`, so it starts working as soon as the first click is recorded.

## Parameters & Limits

| Parameter | Value |
|-----------|-------|
| Aggregation interval | `1h` (configurable via `search_features.analytics_aggregation_interval`) |
| Days re-aggregated per tick | `2` (yesterday + today) |
| Retention window | `90 days` (configurable) |
| Cleanup window | `00:00`–`00:05` UTC daily |
| Aggregation grain | Per `(tenant_id, query, date)` |

## Troubleshooting

| Issue | Solution |
|-------|----------|
| Analytics-derived features return empty despite traffic | The aggregator hasn't run yet. Wait one interval (default `1h`) or restart the service to trigger an immediate run |
| Today's counts look wrong mid-day | Expected — today's row is rewritten each interval as more searches come in. Compare the `updated_at` timestamp to confirm the last tick |
| Two rows differ only by casing (`"ui"` vs `"UI"`) | Aggregator groups by exact `query` bytes. Normalise casing in the client before submitting if you want case-folded analytics |
| `unique_users` is far lower than `search_count` | Most searches are anonymous — they're counted in `unique_sessions` instead. Both together approximate distinct searchers |
| Old history rows survive past 90 days | Cleanup only runs between `00:00`–`00:05` UTC. Confirm the aggregator is running, the clock is correct, and `HistoryRetentionDays` isn't `0` (which disables the default and falls back to `90`) |
| Historical analytics days show `0` counts | The aggregator only recomputes yesterday + today. If history for an older day was backfilled manually, re-run the service after resetting its internal clock, or write a one-shot aggregate job for that specific date |
