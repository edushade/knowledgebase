# Search Integration

The search module is a shared service; consumers mount it in different ways depending on context. This page maps each consumer surface to the endpoints it calls, the components it renders, and any surface-specific quirks.

Think of it as the "who calls search and how" directory.

## Public Website (Website Builder)

The public site runs on the **website-builder-v2** app. Search is mounted inside header and hero blocks that merchants compose via the block builder.

### Header Blocks: `search_bar` Action Type

Two Taibah templates expose search as an opt-in action:

- `admin/blocks/templates/taibah/blocks/header-block-01/TaibahHeaderBlock01Component.tsx`
- `admin/blocks/templates/taibah/blocks/header-block-02/TaibahHeaderBlock02Component.tsx`

The block schema lets the merchant add a navigation action of type `search_bar`; the component then renders the [Search Bar](/docs/knowledgebase/search-module/search-bar) in place of a link or locale switcher.

```ts
// field-schema.ts
{ value: "search_bar", label: "Search Bar" }
```

```tsx
case 'search_bar':
  return <SearchBar ... />;
```

This is how every public site ends up with a header search without the merchant writing code. The underlying `SearchBar` is the Command-palette component described in [Search Bar](/docs/knowledgebase/search-module/search-bar); no new calls or endpoints are introduced by the integration — the header block is purely a mounting point.

### Hero Block

`admin/blocks/templates/taibah/blocks/hero-block-03/TaibahHeroBlock03Component.tsx` mounts the same `SearchBar` component in the hero region. Used on landing pages that want search as the primary CTA.

### Search Results Route

A dedicated `/search` route on the public site renders [Search Results](/docs/knowledgebase/search-module/search-results) with its full pagination, filters, did-you-mean, related-searches, and trending-fallback behaviour. Navigating to this route is what the search bar does on "Enter" or "See all results".

## API Client

All public-site search is funnelled through one client: `website-builder-v2/src/lib/api/client.ts`. The methods:

| Method | Endpoint | Notes |
|--------|----------|-------|
| `apiClient.search(params, isAdmin)` | `/search` | Main full-text search |
| `apiClient.searchWithFacets(params, isAdmin)` | `/search/facets` | Same + facet counts |
| `apiClient.getAutocomplete(params, isAdmin)` | `/search/autocomplete` | Prefix matching |
| `apiClient.getSearchHistory(params, isAdmin)` | `/search/history` | Recent searches |
| `apiClient.deleteSearchHistoryEntry(id, isAdmin)` | `DELETE /search/history/:id` | Remove one row |
| `apiClient.clearSearchHistory(isAdmin)` | `DELETE /search/history` | Wipe current user/session |
| `apiClient.trackSearchClick(body, isAdmin)` | `POST /search/click` | Click tracking |
| `apiClient.getSearchSuggestions(params, isAdmin)` | `/search/suggestions` | Popular queries |
| `apiClient.getTrendingSearches(params, isAdmin)` | `/search/trending` | Trending queries |
| `apiClient.getTrendingResults(params, isAdmin)` | `/search/trending/results` | Trending documents |

The `isAdmin` boolean flips the base path between `/public/search/*` and `/admin/search/*`. See [Admin Search](/docs/knowledgebase/search-module/admin-search#frontend-integration) for the authenticated variant.

Types live in `website-builder-v2/src/lib/api/types.ts` (`SearchDocument`, `SearchHit`, `SearchResponse`, `SearchFacetsResponse`, `AutocompleteResponse`, `TrendingSearch`, `TrendingResult`, `SearchHistoryResponse`, etc.).

## Learner App

The learner-facing Next.js app (`frontend/`) has an **AI-flavoured search modal** at `src/components/learner/search-modal.tsx`.

> **Status: stub.** The modal is wired into the UI but does not yet call the search-service. Its `searchResults` array is hardcoded and the "AI mode" simulates a response with `setTimeout`. Nothing from this module is affected by the search-service state.

When this is promoted past the stub:

1. Replace the hardcoded `SearchResult[]` with a call to `apiClient.search({ q, per_page: 10 }, false)`.
2. Replace the simulated AI response with whatever LLM orchestration is chosen.
3. Wire `apiClient.trackSearchClick` on result selection so AI-surfaced results feed [Trending Results](/docs/knowledgebase/search-module/trending#trending-results).

Until then, treat this modal as **unrelated to the search service** — the two live on different surfaces and share no state.

## Admin Console

The admin app uses search in two different places, for two different purposes:

### 1. Tenant Content Search

Same `apiClient.*` methods, passed `isAdmin=true`, against `/admin/search/*`. Used when an admin is searching their own tenant's catalogue (courses, products, posts, etc.) to find something to edit or preview. The `include_drafts=true` query param is typical here — see [Admin Search](/docs/knowledgebase/search-module/admin-search#draft--status-visibility).

### 2. Admin User-List Filters

A separate component, `frontend/src/components/admin/user/filters/search-filters.tsx`, drives the admin user-list search-by-name/email filter. This is **not** the search module — it queries the user service directly via its own list endpoint. The name collision is unfortunate; the component existed before the search module.

> The admin DataTable components also expose a `hideSearchBar` prop (table-local filtering). That is also unrelated to the search module — it's column-level client-side filtering.

## End-to-End Flow

Stitching together the public website journey:

```
User lands on the storefront
 │
 ▼
Header block renders SearchBar (mounted via search_bar action type)
 │  user types "figma"
 ▼
SearchBar debounces 300ms, calls /autocomplete → renders suggestions
 │  user presses Enter
 ▼
Navigate to /search?q=figma
 │
 ▼
SearchResults mounts, calls /search → renders hits
 │  user clicks a course
 ▼
SearchResultItem calls /click { history_id, result_id }
 │  then navigates to /{locale}/courses/{slug}
 ▼
Click lands in search_history.clicked_result_id → aggregated into trending
```

## Integration Checklist

When adding a new surface that needs search:

- [ ] Import `SearchBar` if you just need an inline search input, or build against `apiClient.search` directly for a custom UI.
- [ ] Decide public vs admin — `isAdmin` must match the surface's auth context.
- [ ] If you render results yourself, honour `metadata.history_id` and call `trackSearchClick` so analytics stays correct.
- [ ] If you show empty states, pull in `getTrendingResults` (zero-hit recovery) and `getTrendingSearches` (empty-input inspiration).
- [ ] If the surface has its own locale, make sure the UI falls back through `preferred → en → first` on `title`/`description`. See [Localization](/docs/knowledgebase/search-module/localization#frontend-locale-resolution).
- [ ] If drafts must stay hidden, do **not** expose `include_drafts` as a query param on the new surface — the service honours it on public routes too, relying on the client to not pass it.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| Search works on storefront but not inside a specific merchant template | The merchant template hasn't added the `search_bar` action. Open the header block editor and add it, or pick a template that ships with it by default |
| AI search modal in learner app returns the same 4 results every time | Expected — the modal is a stub. The list is hardcoded. Wait for the real integration before treating it as broken |
| Admin user-list search behaves differently from content search | They're different systems. `admin/user/filters/search-filters.tsx` talks to the user service, not the search service. Look for filter bugs on the user service side |
| `isAdmin` flag is set but calls still hit `/public/search/*` | The client reads `isAdmin` at call time per method. Ensure the value is threaded through the component tree — a stale closure is the usual culprit |
| Two templates render two SearchBars side by side | The merchant probably added the `search_bar` action twice. Edit the header block configuration to deduplicate |
| Click tracking missing from a custom integration | The component likely navigates before awaiting the click POST. `trackSearchClick` is fire-and-forget, but the client-side navigation must not tear down the network context too early — use `keepalive` if targeting a new tab |
