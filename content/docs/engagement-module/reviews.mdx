# Reviews

Reviews let learners leave a star rating (1–5) and a written body about a course, quiz, event, cohort, or learning path. Reviews power the average rating you see on course cards and the satisfaction dashboard admins use to track quality over time. A public read endpoint exists so unauthenticated visitors on marketing pages can see the same reviews enrolled learners see.

## Quick Facts

| Attribute | Value |
|-----------|-------|
| Entity types supported | `course`, `quiz`, `event`, `cohort`, `learning_path` |
| Rating range | Integer `1`–`5` |
| Body length | 1–10,000 characters |
| Delete mode | Soft delete (sets `deleted_at`) |
| Admin endpoint prefix | `/api/v1/admin/reviews` |
| User endpoint prefix | `/api/v1/user/reviews` |
| Public endpoint prefix | `/api/v1/public/reviews` |
| System endpoint prefix | `/api/v1/system/reviews` |
| Required admin permissions | `review.list`, `review.view`, `review.create`, `review.update`, `review.delete` |

## Data Model

A review row (`reviews` table):

| Field | Type | Description |
|-------|------|-------------|
| `id` | UUID | Primary key |
| `tenant_id` | UUID | Tenant scope |
| `entity_type` | string | `course`, `quiz`, `event`, `cohort`, `learning_path` |
| `entity_id` | UUID | Specific entity being reviewed |
| `body` | text | Review body (1–10,000) |
| `rating` | int | 1 (poor) to 5 (excellent) |
| `created_at` | timestamp | Set on insert |
| `updated_at` | timestamp | Updated on every PUT |
| `created_by` | UUID | Reviewer |
| `updated_by` | UUID | Last editor |
| `deleted_at` | timestamp \| null | Soft delete marker |

> **Note:** The backend does **not** enforce "one review per user per entity" today. Two distinct rows with the same `entity_id` and `created_by` are allowed. If your product requires uniqueness, the frontend should either pre-check for an existing review before submitting or upgrade the constraint at the database level.

## User-Facing Workflows

### Submitting a Review

1. The learner navigates to a course, quiz, event, cohort, or learning path they are enrolled in.
2. They click **Write a Review** and fill in a 1–5 star rating plus a body.
3. The frontend calls `POST /api/v1/user/reviews` with `{ entity_type, entity_id, body, rating }`.
4. The service verifies enrollment and inserts the row with `created_by` and timestamps.
5. The response includes the creator's profile (name and avatar) for immediate rendering.

> **Validation:** `rating` must be an integer 1–5. Strings, floats, 0, or 6 are rejected. `body` must be 1–10,000 characters.

### Listing Your Reviews and Reviews of Enrolled Entities

1. `GET /api/v1/user/reviews` returns reviews attached to entities the learner is enrolled in.
2. Filters include `entity_type`, `entity_id`, `rating`, `created_by`, and `search` (case-insensitive match on body).
3. Default sort is `created_at DESC`.

### Editing Your Own Review

1. The learner clicks **Edit** on their review.
2. The frontend calls `PUT /api/v1/user/reviews/{review_id}` with any subset of `{ body, rating }`.
3. The service verifies ownership and enrollment, updates the provided fields, and refreshes `updated_at`/`updated_by`.

### Deleting Your Own Review

1. The learner clicks **Delete** and confirms.
2. The frontend calls `DELETE /api/v1/user/reviews/{review_id}`.
3. The service verifies ownership + enrollment and sets `deleted_at = now()`.

## Admin-Facing Workflows

Admin tools live at `/admin/communication/review` in the frontend and expose list, edit, delete, bulk export, bulk delete, and analytics.

### Review List (`GET /api/v1/admin/reviews`)

Requires `review.list`. Supports the same filters as the user list, plus filtering by `rating`, `created_by`, and date ranges. Results include the creator profile (loaded from auth-service) and the linked entity (course / quiz / etc.).

### Creating & Editing as Admin

- `POST /api/v1/admin/reviews` (requires `review.create`) creates a review on any entity without enrollment check.
- `PUT /api/v1/admin/reviews/{id}` (requires `review.update`) edits any review.
- `DELETE /api/v1/admin/reviews/{id}` (requires `review.delete`) soft-deletes any review.

### Bulk Export (`GET /api/v1/admin/reviews/bulk/export`)

Requires `review.list`. Streams matching reviews as CSV.

### Bulk Delete (`DELETE /api/v1/admin/reviews/bulk/delete`)

Requires `review.delete`. Accepts only a fixed body — it is an ID-list operation, not a filter-based mass delete:

```json
{ "review_ids": ["<uuid>", "<uuid>", ...] }
```

The response returns the number of rows soft-deleted.

## Analytics

The admin analytics surface is built on top of three analytic endpoints. All are gated by `review.view`.

### Batch Average Ratings

`POST /api/v1/admin/reviews/average-ratings`

Accepts a batch of `{ entity_type, entity_id }` pairs and returns `{ average_rating, total_reviews }` for each. This is the backbone of the "rating on every course card" pattern — the admin dashboard issues one request for all visible entities.

Request:

```json
{
  "entities": [
    { "entity_type": "course", "entity_id": "course-1" },
    { "entity_type": "course", "entity_id": "course-2" }
  ]
}
```

Response:

```json
{
  "ratings": [
    { "entity_type": "course", "entity_id": "course-1", "average_rating": 4.2, "total_reviews": 50 },
    { "entity_type": "course", "entity_id": "course-2", "average_rating": 4.7, "total_reviews": 18 }
  ]
}
```

### Course Average Rating with Growth

`GET /api/v1/admin/reviews/course-entities/average-rating`

Returns the average rating of courses in the tenant for a given period, along with the previous period's average and the growth percentage. Typically rendered as the "Average Course Rating" card on the analytics dashboard.

### Average Satisfaction

`GET /api/v1/admin/reviews/average-satisfaction?start_date=&end_date=`

Aggregates reviews across `course`, `cohort`, and `learning_path` entity types in the date range and returns:

| Field | Description |
|-------|-------------|
| `average_satisfaction` | Mean rating in the window, scaled to a 0–100 percentage (`avg_rating ÷ 5 × 100`) |
| `previous_average_satisfaction` | **Previous calendar month's** satisfaction percentage — `start_date` and `end_date` are **ignored** for this field; the comparison window is always the prior full calendar month |
| `satisfaction_growth` | Percent change between the **current calendar month** and the **previous calendar month** (also independent of `start_date`/`end_date`) |
| `total_reviews` | Count in the requested window |
| `previous_reviews` | Count in the previous calendar month (not the prior window) |

> **Caveat:** Despite taking `start_date` and `end_date`, the "previous" comparison values are pinned to calendar months, not the prior window of equal length. The same caveat applies to `rating_growth` on `/course-entities/average-rating`.

### Monthly Satisfaction (System)

`POST /api/v1/system/reviews/monthly-satisfaction`

Used by other microservices to pull the monthly satisfaction time-series for a batch of entities. Requires a system API token — not exposed to admins or users directly.

## Rating Distribution (Review Stats)

The `calculateReviewStats()` helper inside the service computes a full distribution for any list of reviews:

```json
{
  "average_rating": 4.2,
  "total_reviews": 50,
  "rating_counts":     { "1": 2,  "2": 3,  "3": 5,  "4": 20, "5": 20 },
  "rating_percentages":{ "1": 4.0,"2": 6.0,"3": 10.0,"4": 40.0,"5": 40.0 }
}
```

This shape is used anywhere the UI renders a star-distribution histogram.

## Public Reviews

`GET /api/v1/public/reviews/{entity_type}/{entity_id}`

Unauthenticated at the user-identity level — no JWT required. The request still resolves through `TenantMiddleware`, so a tenant context (typically a tenant header or host-derived tenant ID) must be present. Used on marketing and course-landing pages where the viewer may not be signed in.

The response is **not** a bare list — it wraps the paginated reviews with the same distribution stats returned by `calculateReviewStats()`:

```json
{
  "data": [
    {
      "average_rating": 4.2,
      "total_reviews": 50,
      "rating_counts":     { "1": 2,  "2": 3,  "3": 5,  "4": 20, "5": 20 },
      "rating_percentages":{ "1": 4.0,"2": 6.0,"3": 10.0,"4": 40.0,"5": 40.0 },
      "reviews": [ /* review objects */ ]
    }
  ],
  "pagination": { /* standard pagination fields */ }
}
```

Standard pagination query params (`page`, `per_page`, `sort_by`, `sort_dir`) are supported.

> **Security:** The public endpoint intentionally bypasses enrollment and RBAC checks. Do not expose `body` content that must be private via this endpoint — every soft-deleted review is excluded, but otherwise the response is fully public. Treat reviews as public content by default.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| "rating must be between 1 and 5" (400) | `rating` must be an integer 1–5 — 0, 6, decimals, or strings are rejected |
| "you are not enrolled in this program" (403) | Learner is not enrolled in the entity. Admins bypass this via the admin endpoints |
| "you can only update your own reviews" / "you can only delete your own reviews" (403) | Only the author can edit/delete via the user endpoint. Use admin endpoints with `review.update`/`review.delete` for moderation |
| Duplicate reviews by the same user | The backend does not enforce uniqueness. Check for an existing review on the frontend before allowing "Write a Review" |
| `average_rating` appears as `0` for a new course | Expected when `total_reviews` is 0. The analytics endpoints return a zero value rather than null for ease of rendering |
| Soft-deleted review still returned in public endpoint | It is not — the public endpoint filters by `deleted_at IS NULL`. If you see otherwise, the row may not actually be soft-deleted; re-check `deleted_at` in the database |
