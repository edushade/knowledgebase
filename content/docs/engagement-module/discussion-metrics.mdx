# Discussion Metrics

Discussion Metrics is a lightweight analytics layer that aggregates live data for a single discussion on demand. It combines unique viewer counts, reaction summaries, and a split of comments vs replies into one compact response. It also exposes an idempotent "record a view" endpoint that the frontend calls the first time a user opens a discussion.

## Quick Facts

| Attribute | Value |
|-----------|-------|
| Aggregate target | One discussion at a time |
| Unique-viewer counting | `COUNT(DISTINCT user_id)` on `discussion_views` |
| Reactions aggregation | Grouped by `type` across all reactions on the discussion |
| Comment split | `comments_count` = `parent_id IS NULL`; `replies_count` = `parent_id IS NOT NULL` |
| Endpoint prefix | `/api/v1/admin/discussions/{discussion_id}` |
| Required permissions | `engagement.metrics.read`, `engagement.view.create` |

## Data Model

The feature reads from three engagement tables and one helper table:

| Source | Read as |
|--------|---------|
| `discussions` | Confirms the discussion exists and is not soft-deleted |
| `discussion_views` | Source of `views_count` via `COUNT(DISTINCT user_id)` |
| `reactions` | Source of `reactions.total`, `reactions.counts[]`, and `reactions.user_reaction` |
| `comments` | Source of `comments_count`, `replies_count`, and `total_comments` |

### The `discussion_views` Table

| Field | Type | Description |
|-------|------|-------------|
| `id` | UUID | Primary key |
| `tenant_id` | UUID | Tenant scope |
| `discussion_id` | UUID | FK to `discussions` |
| `user_id` | UUID | Who viewed the discussion |
| `viewed_at` | timestamp | When the view was recorded |
| `ip_address` | string | Client IP at the time of recording |
| `user_agent` | string | Client user-agent string |

One row per user per discussion — the first call from a given user inserts; every subsequent call is a silent no-op.

## Response Shape

`GET /api/v1/admin/discussions/{discussion_id}/metrics` returns:

```json
{
  "discussion_id": "uuid",
  "views_count": 42,
  "reactions": {
    "total": 15,
    "counts": [
      { "type": "like",  "count": 8 },
      { "type": "love",  "count": 5 },
      { "type": "angry", "count": 2 }
    ],
    "user_reaction": "like"
  },
  "replies_count": 3,
  "comments_count": 5,
  "total_comments": 8,
  "last_updated": "2025-04-22T10:30:00Z"
}
```

| Field | Description |
|-------|-------------|
| `views_count` | Unique viewers — each user counted once regardless of how often they open the discussion |
| `reactions.total` | Sum of all reaction counts |
| `reactions.counts[]` | Array of `{ type, count }`, one entry per reaction type present |
| `reactions.user_reaction` | The current user's reaction type, or `null` if they have not reacted |
| `comments_count` | Root comments (`parent_id IS NULL`) |
| `replies_count` | Replies (`parent_id IS NOT NULL`) |
| `total_comments` | `comments_count + replies_count` — included for convenience |
| `last_updated` | Server time at which the metrics response was generated (literally `time.Now()` in the service). It is **not** derived from `discussions` or `comments` timestamps |

## Recording a View

`POST /api/v1/admin/discussions/{discussion_id}/view`

The endpoint takes **no request body**. Every field is derived from the request context:

- `discussion_id` — from the URL path parameter.
- `user_id` — from the JWT (`middlewares.GetUserID`).
- `tenant_id` — from the JWT.
- `ip_address` — from `c.ClientIP()`.
- `user_agent` — from the `User-Agent` header.

Response:

```json
{
  "message": "Discussion view recorded successfully",
  "data": { "success": true }
}
```

> **Note:** A `DiscussionViewRequest` DTO exists in the codebase but is currently unused by the handler — do not send a body; it is ignored.

### Behaviour

1. The service loads the discussion and rejects if it is soft-deleted.
2. It checks whether a `discussion_views` row already exists for the `(tenant_id, discussion_id, user_id)` tuple.
3. If yes → returns success without inserting (idempotent).
4. If no → inserts a new row with `viewed_at = now()`, capturing `ip_address` and `user_agent` from the request.

> **Note:** View recording is idempotent *per user*. A single user can open the same discussion 50 times in a day — only one row is stored, so `views_count` is a **unique viewer count**, not a raw view count. If you need raw view counts, that is a separate analytic the engagement-service does not emit today.

## API Reference

| Method | Path | Purpose | Permission |
|--------|------|---------|------------|
| `GET` | `/api/v1/admin/discussions/{discussion_id}/metrics` | Fetch aggregated metrics | `engagement.metrics.read` |
| `POST` | `/api/v1/admin/discussions/{discussion_id}/view` | Record a unique view | `engagement.view.create` |

Both endpoints require authentication. Although the paths live under `/admin/`, both permissions can be granted to learner roles if the tenant wants dashboard widgets to display metrics on the user surface. In particular, **learner roles need `engagement.view.create`** for view tracking to fire from the user-facing UI — there is no user-prefix alternative route.

## Workflow Example

```
1. Learner opens discussion d1 → frontend calls POST /admin/discussions/d1/view
   → discussion_views insert (first time for this user)
2. Admin opens the discussion moderation page → frontend calls GET /admin/discussions/d1/metrics
   → service returns { views_count: 17, reactions: {...}, comments_count: 4, replies_count: 9 }
3. Another learner reacts with "love" → POST /v1/reactions/discussion/d1 { "type": "love" }
4. Admin refetches metrics → views_count unchanged, reactions.total +1, counts.love +1
5. A comment is posted on d1 → POST /v1/user/comments with entity_type=discussion, entity_id=d1
6. Admin refetches metrics → total_comments +1, comments_count +1 (or replies_count +1 if parent_id was set)
```

## Aggregation Details

| Metric | SQL path |
|--------|----------|
| `views_count` | `SELECT COUNT(DISTINCT user_id) FROM discussion_views WHERE tenant_id = ? AND discussion_id = ?` |
| `reactions.counts` | `SELECT type, COUNT(*) FROM reactions WHERE tenant_id = ? AND entity_type = 'discussion' AND entity_id = ? GROUP BY type` |
| `reactions.user_reaction` | `SELECT type FROM reactions WHERE tenant_id = ? AND entity_type = 'discussion' AND entity_id = ? AND user_id = ?` |
| `comments_count` | `SELECT COUNT(*) FILTER (WHERE parent_id IS NULL) FROM comments WHERE tenant_id = ? AND entity_type = 'discussion' AND entity_id = ? AND deleted_at IS NULL` |
| `replies_count` | `SELECT COUNT(*) FILTER (WHERE parent_id IS NOT NULL) FROM comments WHERE tenant_id = ? AND entity_type = 'discussion' AND entity_id = ? AND deleted_at IS NULL` |

> **Tip:** The counts are computed on read — there is no materialised view. If you observe slow aggregation on high-volume discussions, add covering indexes on `(tenant_id, entity_type, entity_id)` for `comments` and `reactions`. They are the canonical access pattern.

## Events Emitted

**Neither endpoint emits events today.** `GET .../metrics` is a pure query, and the view-recording handler does not publish `AuditEvent` or `ActivityEvent`. A view is inserted silently.

If you need a "viewed a discussion" signal in the audit or activity feeds, it will have to be added to the handler — it is not there today.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| "discussion not found" (404) | The ID does not exist or the discussion is soft-deleted. Deleted discussions are excluded from both metrics and view recording |
| `views_count` is much lower than I expect | Unique viewers only. If you need raw views, build a separate counter; this endpoint intentionally counts distinct users |
| `views_count` does not increment on refresh | Correct — view recording is idempotent per user. Each user is counted exactly once |
| `total_comments` does not match `comments_count + replies_count` | They must match by construction. If they don't, a soft-deleted comment is being counted somewhere — re-check `deleted_at IS NULL` in your query |
| `last_updated` appears to be "now" on every request | Expected — `last_updated` is the server time when the response was generated, not derived from the underlying data. It is not useful for change detection on this endpoint |
| Reaction summary inside metrics differs from the standalone reactions endpoint | Both queries read from the same table. A discrepancy usually means a caller is passing a different tenant context — check the JWT's tenant claim |
