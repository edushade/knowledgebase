# Engagement Module

The **Engagement Module** is the platform's social-learning fabric. It lets learners and instructors start discussions, post threaded comments, react with emoji, and leave star-rated reviews on any course, quiz, event, cohort, learning path, lesson, or assignment. It also aggregates every interaction into per-discussion metrics and platform-wide satisfaction analytics.

## What This Module Covers

| Feature | Description |
|---------|-------------|
| [Discussions](/docs/knowledgebase/engagement-module/discussions) | Forum-style topics scoped to a course, quiz, event, cohort, or learning path — with public/private visibility |
| [Comments](/docs/knowledgebase/engagement-module/comments) | Infinitely-nestable threaded comments on any engagement entity, with cursor pagination and strategy-based filters |
| [Reactions](/docs/knowledgebase/engagement-module/reactions) | Seven emoji reactions (`like`, `dislike`, `haha`, `love`, `angry`, `sad`, `support`) — one per user per entity, idempotent replace |
| [Reviews](/docs/knowledgebase/engagement-module/reviews) | 1-to-5 star reviews with text body — plus admin analytics for average rating, monthly satisfaction, and rating distribution |
| [Discussion Metrics](/docs/knowledgebase/engagement-module/discussion-metrics) | Per-discussion aggregates: unique view count, reaction summary, and comment vs reply counts |

## Architecture Overview

The engagement system is a standalone microservice (`engagement-service`) that exposes three surface areas — admin, user, and public — each gated differently.

### Key Components

- **Backend**: Go (Gin framework) with Bun ORM on PostgreSQL
- **Frontend**: Next.js with React, using dedicated `lib/comment/*` and `lib/engagement/*` hooks and server actions
- **Event Pipeline**: `EntityEventPublisher` emits `AuditEvent` (creates/updates/deletes) and `ActivityEvent` (user-facing activity feed entries) via pub-sub
- **Multi-Tenancy**: Every discussion, comment, reaction, and review is scoped by `tenant_id`. Cross-tenant reads are impossible by construction.
- **Cross-Service Data**: Pulls user profiles from auth-service, enrollment state from learning-service, and quiz state from quiz-service through shared `UserAssociationService`, `EnrollmentAssociationService`, and `EntityAssociationService` helpers.

### Endpoint Surfaces

| Prefix | Audience | Auth |
|--------|----------|------|
| `/api/v1/admin/*` | Admins and instructors with `discussion.*`, `comment.*`, `review.*` permissions | User JWT + RBAC |
| `/api/v1/user/*` | Signed-in learners — scoped automatically to entities the user is enrolled in | User JWT + enrollment check |
| `/api/v1/reactions/*` | Any signed-in user — applies across all engagement entities | User JWT + `reaction.*` |
| `/api/v1/public/reviews/*` | Unauthenticated visitors | Public (read-only) |
| `/api/v1/system/reviews/*` | Other microservices aggregating satisfaction data | System token |

### Supported Entity Types

Every engagement feature operates on an **entity reference** — a pair of `entity_type` + `entity_id`. The table below shows which types each feature is intended for. Enforcement varies:

- **Discussions** and **Comments** validate `entity_type` via their DTOs.
- **Reviews** validate only the string length of `entity_type`; the satisfaction analytics are restricted to `course`, `cohort`, `learning_path` at the SQL level.
- **Reactions** do **not** validate `entity_type` on set/get at all — the handler accepts any string from the URL path. The `ReactionFilter` DTO (used only for list-style calls) restricts the list to `course, discussion, lesson, assignment, quiz, comment`, but the write endpoints bypass that filter. Treat the "Valid For" column as guidance, not enforcement.

| Entity Type | Valid For | Notes |
|-------------|-----------|-------|
| `course` | Discussions, Comments, Reactions, Reviews | Learning-service courses |
| `quiz` | Discussions, Comments, Reactions, Reviews | Quiz-service quizzes |
| `event` | Discussions, Comments, Reactions, Reviews | Live / recorded events |
| `cohort` | Discussions, Comments, Reactions, Reviews | Time-boxed learner groups |
| `learning_path` | Discussions, Comments, Reactions, Reviews | Multi-course programs |
| `lesson` | Comments, Reactions | Individual lesson inside a course |
| `assignment` | Comments, Reactions | Individual assignment inside a course |
| `discussion` | Comments, Reactions | A comment on another discussion |
| `comment` | Reactions | Reactions attached to a comment |

|------|-------|----------------|

## How Engagement Works (High-Level Flow)

```
1. A learner opens a course, quiz, event, cohort, or learning path
2. engagement-service.ListDiscussions filters to programs the learner is enrolled in
3. The learner creates a discussion (or a comment on an existing one) → row persisted with tenant_id + created_by
4. The learner reacts to the discussion/comment → replace-or-insert into reactions (one per user per entity)
5. Another learner views the discussion → discussion_views is inserted (idempotent per user) for the unique viewer count
6. An admin opens Discussion Metrics → views, reactions by type, and comment/reply counts are aggregated live
7. Every mutation publishes an AuditEvent; user-visible actions also emit an ActivityEvent for activity feeds
8. Admin analytics roll up reviews across date ranges into average satisfaction and monthly trends
```

## Permissions

The engagement group in the platform permission catalog:

| Permission | Grants |
|------------|--------|
| `discussion.list` | List discussions (admin table) |
| `discussion.view` | View a single discussion |
| `discussion.create` | Create a discussion (admin surface) |
| `discussion.update` | Edit any discussion |
| `discussion.delete` | Soft-delete any discussion and run bulk delete |
| `comment.list` | List comments (admin table) |
| `comment.view` | View a single comment |
| `comment.create` | Create a comment (admin surface) |
| `comment.update` | Edit any comment |
| `comment.delete` | Soft-delete any comment and run bulk delete |
| `reaction.set` | Add or change a reaction on any entity |
| `reaction.delete` | Remove a reaction |
| `review.list` | List reviews (admin table) |
| `review.view` | View a review, including analytics and bulk export |
| `review.create` | Create a review on behalf of anyone (admin surface) |
| `review.update` | Edit any review |
| `review.delete` | Soft-delete any review and run bulk delete |
| `engagement.metrics.read` | Read aggregated discussion metrics |
| `engagement.view.create` | Record a discussion view |

User-surface endpoints (`/api/v1/user/*`) do **not** require engagement permissions. Instead they check that the user is enrolled in the entity they are trying to read or write. See [Roles & Permissions](/docs/knowledgebase/auth-module/roles-and-permissions) for how permissions are assembled into roles.

## Enrollment Gating

Every user-surface endpoint calls `EnrollmentAssociationService.CheckUserEnrollment(tenantID, userID, entityType, entityID)` before doing any read or write. If the user is not enrolled in the target entity, the service returns `403 Forbidden` with the message `you are not enrolled in this program`.

> **Note:** Enrollment gating is applied even on reads. A learner can only see discussions, comments, and reviews attached to programs they are enrolled in. This is enforced server-side — it is not a frontend filter.

Admin-surface endpoints skip the enrollment check and use RBAC permissions instead.

## Soft Deletes

Discussions, comments, and reviews all use **soft deletes** — a `deleted_at` timestamp is set instead of removing the row. Queries filter `WHERE deleted_at IS NULL`, so deleted rows disappear from every listing, including bulk export.

- Replies to a deleted comment **remain visible** (no cascade).
- Reactions and `discussion_views` rows are **hard-deleted** — there is no `deleted_at` on those tables.

## Getting Started

If you're a **new learner**, start with:
1. [Discussions](/docs/knowledgebase/engagement-module/discussions) — Start a topic or join one scoped to your program
2. [Comments](/docs/knowledgebase/engagement-module/comments) — Reply to a discussion or thread a conversation
3. [Reactions](/docs/knowledgebase/engagement-module/reactions) — React to a post with one of seven emoji
4. [Reviews](/docs/knowledgebase/engagement-module/reviews) — Leave a 1-to-5 star review on a completed course

If you're an **administrator**, also read:
1. [Discussions](/docs/knowledgebase/engagement-module/discussions) — Moderate, bulk-export, or bulk-delete discussions
2. [Comments](/docs/knowledgebase/engagement-module/comments) — Moderate threads and inspect reply trees
3. [Reviews](/docs/knowledgebase/engagement-module/reviews) — Run average-rating and monthly-satisfaction analytics
4. [Discussion Metrics](/docs/knowledgebase/engagement-module/discussion-metrics) — Inspect views, reactions, and comment counts per discussion

If you're an **engineer integrating engagement data**, also read:
1. [Reactions](/docs/knowledgebase/engagement-module/reactions) — How the idempotent replace-and-aggregate flow works
2. [Reviews](/docs/knowledgebase/engagement-module/reviews) — Batch average-rating and monthly-satisfaction system endpoints
3. [Discussion Metrics](/docs/knowledgebase/engagement-module/discussion-metrics) — Server-side aggregation for discussion analytics
