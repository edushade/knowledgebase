# Website Builder Integration

The `website-builder-v2` app (Vite + React + TanStack Router) uses the same `@softimist/filemanager` package as the main frontend, with its own thin wrapper in `website-builder-v2/src/components/filemanager/`. Every block that shows an image, every form that collects an attachment, goes through that wrapper.

## The Wrapper

- **Path:** `website-builder-v2/src/components/filemanager/file-manager-dialog.tsx`
- **Upload endpoint:** `POST /api/v1/admin/files/upload`
- **Auth:** JWT via `getAuthToken()` (reads `es_auth_access_token` from localStorage)
- **Asset base URL:** from `VITE_ASSET_BASE_URL` in dev, falls back to `apiBaseUrl` on localhost

The wrapper injects app-specific `Image` and `VideoPlayer` components for previews, so that image thumbnails inside the picker render using the builder's own design system.

> The builder only uses the **admin** upload path — there is no learner flow in the builder.

## Where the Dialog Opens

The `FileManagerDialog` is mounted at three places in the builder:

| Location | File | Use |
|----------|------|-----|
| Block config forms (dynamic) | `src/components/admin/blocks/templates/DynamicFormRenderer.tsx` | Image fields on any block template |
| Public form fields | `src/components/shared/FormFieldsRenderer.tsx` | File attachments on user-facing forms |
| Rich text / media fields inside blocks | Inside `DynamicFormRenderer` (embedded editor) | Media in WYSIWYG fields |

None of these are URL-driven — the dialog is a modal that opens from a button or dropzone on the page editor.

## Block Image Fields

When a block schema defines an `image` or `gallery` field, the builder renders the picker in **dropzone mode**:

```tsx
<FileManagerDialog
  mode="dropzone"
  acceptedTypes={['image/*']}
  multiple={false}
  onSelect={(files) => {
    const file = files[0];
    form.setValue(field.name, file.url || file.path);
  }}
/>
```

- **Strict image-only filter:** the dropzone passes `acceptedTypes={['image/*']}` so non-image files are rejected before upload.
- **Single file:** block image fields are single-file by default. Gallery blocks use the same component with `multiple={true}` and store an array of URLs.
- **Stored value:** the block config stores the file's `url` (or `path`) — **not** the `file_id`. This keeps the block JSON self-contained for serialization and lets the renderer emit the `<img src>` without an extra DB lookup. The URL itself still resolves through the filemanager service (`/v1/files/preview-id/{file_id}` → 30-min presigned redirect to S3), so blocks do **not** keep working if the filemanager service is down. They break if the underlying file is deleted, since the bucket key behind the URL no longer exists.

### Common Image-Using Blocks

| Block | Field | Notes |
|-------|-------|-------|
| `image` | `src` | Single image with caption |
| `gallery` | `images[]` | Array of image URLs — multi-select picker |
| `hero` | `backgroundImage` | Hero banner background |
| `background` | `image` | Section background image |
| Custom tenant templates (`templates/taibah/blocks/*`) | Varies | Background, icons, decoration images |

## Form Attachments

User-facing public forms (contact forms, webinar signup, etc.) can include file-upload fields. `FormFieldsRenderer.tsx` defines a dedicated `FileFieldRenderer` component that mounts `FileManagerDialog` and stores the picked **file IDs** on the form (deliberately different from blocks, which store URLs):

```tsx
<FileManagerDialog
  multiple
  trigger={{ label: 'Add Files', placeholder: 'Select files to attach' }}
  onSelect={(files) => {
    const currentIds = (form.watch(field.name) as string[]) || [];
    const newIds = files
      .filter((f) => !currentIds.includes(f.id))
      .map((f) => f.id);
    form.setValue(field.name, [...currentIds, ...newIds], { shouldValidate: true });
  }}
  acceptedTypes={['*/*']}
/>
```

Why IDs (not URLs) for forms? Form submissions are persisted as records that the receiving service may want to display, re-issue download URLs for, or attach via the [Attachments](/docs/knowledgebase/filemanager-module/attachments) table. Storing the ID keeps that future use open. Blocks, by contrast, render directly from the URL so they don't need a server round-trip at render time.

Because this is an admin-side builder, the files uploaded here end up in the admin's file library just like any other upload — end-user-side form submissions to this surface would need a different flow.

## URL Handling

The builder stores absolute file URLs (or paths) in block configs. The resolution at render time is:

| Environment | `assetBaseUrl` | Resulting `<img src>` |
|-------------|----------------|------------------------|
| Production (tenant domain) | Empty string | `/v1/files/preview-id/{file_id}` — resolved by the browser relative to the tenant domain |
| Dev (localhost) | `apiBaseUrl` | `http://localhost:<port>/v1/files/preview-id/{file_id}` |

The re-exported `getFileUrl()` helper applies the prefix so callers don't have to branch on environment.

### Storing URL vs File ID

Blocks currently store **URLs** in config, not file IDs. This has two consequences:

- **Pro:** Block JSON is self-contained and renders without a backend call.
- **Con:** Renaming, moving, or deleting the underlying file silently breaks the block. A future migration could switch blocks to store file IDs and resolve at render time — today they do not.

## Accepted MIME Types & Stored Value by Context

| Context | Types | Enforcement | Stored as |
|---------|-------|-------------|-----------|
| Block image field | `image/*` | Picker-side (strict) | URL |
| Block gallery field | `image/*` | Picker-side (strict) | URL[] |
| Form attachment field | `*/*` (any) | Backend tenant size cap only | file_id[] |
| Rich text editor media | `image/*`, `audio/*`, `video/*` | Picker-side | URL embedded in `<img>`/`<audio>`/`<video>` tag |

The backend tenant upload cap (`media.max_upload_file_size`) applies to all of the above.

## Tenant & Role Access

The builder does not perform explicit role checks before opening the picker — it relies on:

1. **Route-level auth:** the page editor route (`/admin/_admin/website/pages/$pageId`) is only accessible to authenticated admins (TanStack Router guards).
2. **API-level RBAC:** the backend `/v1/admin/files/*` endpoints enforce `file.view`, `file.upload`, etc. — see [Roles & Permissions](/docs/knowledgebase/filemanager-module/roles-and-permissions).

If a user reaches the editor but lacks `file.upload`, the picker will open but uploads will `403`. The UI surfaces this as a toast.

## Tenant Scoping

Every request carries the user's JWT, which contains `tenant_id`. All file list/preview/upload responses are scoped to that tenant automatically. Cross-tenant file picking is not possible from the builder.

## Route Schema

| Route | Purpose |
|-------|---------|
| `/admin/_admin/website/pages` | Page list |
| `/admin/_admin/website/pages/new` | New page (builder) |
| `/admin/_admin/website/pages/$pageId` | Edit page (builder) |

The file manager is always embedded in a dialog — there is no dedicated `/website/media` or similar route.

## Rich Text Media Inside Blocks

The builder embeds the shared `@softimist/tiptap` rich-text editor inside long-text block fields. The editor's `fileManagerAdd` flag wires up a custom trigger button that opens `FileManagerDialog`. Selected media is inserted as `<img>`, `<audio>`, or `<video>` tags using the injected `getFileUrl(file.id)` helper.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| Image picker doesn't respect `image/*` filter | Ensure `acceptedTypes` is an array (`['image/*']`) and not a string |
| Block image broken after rename | Blocks store URLs that may embed the old path — but since `bucket_key` is immutable, this is only an issue if you stored a path-form URL. ID-form URLs survive renames |
| Block image broken after delete | Expected — the underlying file no longer exists. Surface a placeholder in the renderer and re-upload |
| Dev server can't load preview URLs | Set `VITE_ASSET_BASE_URL` (or leave unset for localhost fallback to `apiBaseUrl`) |
| Upload fails with 403 | The current admin lacks `file.upload`. See [Roles & Permissions](/docs/knowledgebase/filemanager-module/roles-and-permissions) |
| Large upload fails in builder | The builder uses the same Uppy path — confirm the tenant's `max_upload_file_size` is high enough and that the multipart flow is engaged for files > 16 MiB |
| Multi-tenant preview leak | Cannot happen — tenant is resolved from the JWT, not the URL. Cross-tenant IDs 404 |
| "Select an image" button does nothing | Check browser console for missing `getAuthToken` or stale refresh token — log out and back in |
