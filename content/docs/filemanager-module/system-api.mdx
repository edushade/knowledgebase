# System API

The `/v1/system/files/*` surface exposes a small set of endpoints designed for **inter-service calls** — other backend services that need to upload, check, or clean up files on behalf of the platform. It is gated by the `SystemAPIAuthMiddleware` which validates the shared system API token configured in `config.yaml` under `system_api.auth_token`.

No user can reach these endpoints directly. They are called by, for example, the migration service when moving files from a legacy source into EduShade, or by a tenant-lifecycle worker when a tenant is purged.

## Endpoints

| Method | Path | Handler | Purpose |
|--------|------|---------|---------|
| `POST` | `/v1/system/files/directories/ensure` | `EnsureDir` | Atomically create a nested folder path (idempotent) |
| `DELETE` | `/v1/system/files/tenant` | `DeleteTenantFiles` | Delete every S3 object for a tenant, by prefix |
| `POST` | `/v1/system/files/check` | `CheckFilesExist` | Batch-check which file IDs already exist |
| `POST` | `/v1/system/files/upload` | `UploadFile` | Single-file upload, accepts a deterministic `file_id` |
| `POST` | `/v1/system/files/upload/s3/multipart` | `StartS3Multipart` | Initiate a multipart upload (non-Uppy variant) |
| `GET` | `/v1/system/files/upload/s3/multipart/{upload_id}/{part_number}` | `GetS3MultipartURL` | Presign a part (query via JSON body) |
| `POST` | `/v1/system/files/upload/s3/multipart/{upload_id}/complete` | `CompleteS3Multipart` | Complete a multipart upload |
| `DELETE` | `/v1/system/files/upload/s3/multipart/{upload_id}` | `AbortS3Multipart` | Abort a multipart upload |

## Authentication

- **Middleware:** `SystemAPIAuthMiddleware(cfg)`
- **Header:** service-to-service JWT issued at deploy time, configured in `config.yaml` under `system_api.auth_token`
- **Tenant context:** resolved from request headers/domain the same way user calls are

The system-api token is **not** a user JWT — it is a fixed credential shared only between trusted backend services. Rotate it on any compromise or team-member exit, and never expose it to browsers.

## Ensure a Directory Path

Create a whole folder tree in one call, reusing existing folders where they exist.

- **Endpoint:** `POST /v1/system/files/directories/ensure`
- **Body:**
  ```json
  { "path": ["lesson-assets", "images", "covers"] }
  ```
- **Response:**
  ```json
  {
    "success": true,
    "message": "Directory ensured",
    "data": { "dir_id": "0190d4a3-....." }
  }
  ```

The response's `dir_id` is the **leaf folder's** UUID — in the example above, the UUID of `/lesson-assets/images/covers`.

Rules:
- `path` must be a non-empty array of folder names.
- Existing segments are reused; missing ones are created in order under the current tenant's root.
- Collisions with existing **file** rows of the same name in the same parent cause the call to fail — use different segment names.

This endpoint is how services like the migration service prepare a folder structure before bulk-uploading files into it.

## Batch Check File Existence

Ask which file IDs from a candidate list already exist in this tenant.

- **Endpoint:** `POST /v1/system/files/check`
- **Body:**
  ```json
  { "file_ids": ["0190d1e5-....", "0190d1e6-....", "0190d1e7-...."] }
  ```
- **Response:**
  ```json
  {
    "success": true,
    "data": {
      "existing_ids": ["0190d1e5-....", "0190d1e7-...."]
    }
  }
  ```

The response lists only the IDs that **already exist** in the tenant's `media` table (not soft-deleted). The migration service uses this to skip re-uploading files that were already processed in a prior run — combined with the `file_id` parameter on upload, it makes migrations fully idempotent.

## Delete All Tenant Files

Remove every object under a tenant's prefix in object storage.

- **Endpoint:** `DELETE /v1/system/files/tenant`
- **Auth:** `SystemAPIAuthMiddleware`
- **Tenant:** derived from request context — you are deleting **the calling context's tenant**, not an arbitrary one
- **Response:**
  ```json
  { "success": true, "message": "Tenant files deleted from storage" }
  ```

**What it does:**

1. Derives `tenantID` from the request.
2. Calls `DeleteByPrefix("{tenantID}/")` on the S3 client — this is a batch `DeleteObjects` sweep under the tenant's prefix.
3. Returns success once the S3 call completes.

**What it does NOT do:**

- It does not delete `media` DB rows. The DB records remain (with `deleted_at IS NULL`) — you must clean them up separately.
- It does not delete `attachments` rows. See [Attachments](/docs/knowledgebase/filemanager-module/attachments#deletion-behaviour) for the coordinated-cleanup pattern.

This endpoint is intended to be called as **part** of a tenant-offboarding pipeline — usually after the tenant-service has marked the tenant as purged and before DB rows are removed.

> **Irreversible:** every file byte is gone after this call. Run it from your offboarding pipeline with appropriate approvals.

## System Upload Variant

The system-side `POST /v1/system/files/upload` is the same handler as the admin and user versions, but crucially **accepts the `file_id` form field**:

```
POST /v1/system/files/upload
Content-Type: multipart/form-data

file: <binary>
file_id: 0190d1e5-....     # optional — deterministic UUID
dir_id:  0190cf2c-....     # optional — target folder
```

If `file_id` is set and already exists in the tenant, the existing record is returned (`200 OK`) and the upload is **skipped**. This preserves the one-to-one mapping between source system IDs and EduShade file IDs during migrations.

The tenant size cap is still enforced the same way as on the admin path — the system API does not bypass tenant settings.

## System Multipart Variant

The four system multipart endpoints (`StartS3Multipart`, `GetS3MultipartURL`, `CompleteS3Multipart`, `AbortS3Multipart`) are a slightly different shape from the Uppy flow:

| Difference | Uppy flow | System flow |
|------------|-----------|-------------|
| Initiate body | `{ filename, type, metadata: {dir_id, size} }` | Full `types.Media` struct (name, size, mime_type, ext, etc.) |
| Part URL response | `{ "url": "..." }` | Wrapped in the standard response envelope |
| Complete body | `{ "parts": [{ ETag, PartNumber }] }` | `types.MultipartCompleteReq` with `media` + `parts` fields |

Use the system variant from backend services that don't want to pretend to be Uppy. Both flows eventually end up at the same `fileSvc.S3Multipart*` service methods, so the final `media` row looks identical.

## Events Emitted

Most system-side operations emit activity and audit events just like user-triggered ones. The actor is the service's **system user ID** (derived from the system JWT), and the event `module = "filemanager"`. This ensures every change — human or machine — is traceable in the audit log.

| Endpoint | Activity event | Audit event |
|----------|---------------|-------------|
| `POST /upload` (XHR) | `file.uploaded` | `created` / `file` |
| `POST /upload/s3/multipart` (initiate) | `file.multipart_started` | `created` / `multipart_upload` |
| `POST /upload/s3/multipart/{id}/complete` | `file.multipart_completed` | `created` / `file` |
| `DELETE /upload/s3/multipart/{id}` (abort) | `file.multipart_aborted` | `deleted` / `multipart_upload` |
| `POST /directories/ensure` | `directory.created` (per new segment) | `created` / `directory` |
| `POST /check` | — (read-only, no events) | — |
| `DELETE /tenant` | — (system-only sweep, no events) | — |

**Why the silence on `/check` and `DELETE /tenant`?** `POST /check` is a read-only existence probe — there's nothing to audit. `DELETE /tenant` runs as part of a tenant-offboarding pipeline that the tenant-service already audits at a higher level; emitting per-object events would add millions of low-value rows. If you need a record, log the call from your offboarding pipeline instead.

## When to Use Each Endpoint

| Use case | Endpoint |
|----------|----------|
| Migrating from a legacy CMS | `POST /check` → filter → `POST /upload` (with `file_id`) |
| Preparing a folder tree for a new course | `POST /directories/ensure` |
| Offboarding a tenant | `DELETE /tenant` (after tenant-service has marked the tenant as purged) |
| Server-to-server upload of a generated artefact (e.g. a quiz PDF) | `POST /upload` |
| Large server-to-server artefact upload | System multipart variant |

## Troubleshooting

| Issue | Solution |
|-------|----------|
| 401 Unauthorized | `system_api.auth_token` mismatch — both services must share the same token |
| "'path' must contain at least one folder name" | `path` array is empty — send at least one segment |
| Ensure fails mid-tree | A collision with an existing file name. Choose a different segment, or inspect the tenant's root |
| `POST /check` returns fewer IDs than expected | Some IDs are soft-deleted — the query filters `deleted_at IS NULL`. Use a DB query directly if you need "ever existed" semantics |
| `DELETE /tenant` appears to return but objects remain | The batch DeleteObjects API paginates; the service handles pagination but very large tenants can take minutes. Verify by listing the prefix afterward |
| Deterministic `file_id` rejected | The value must be a valid UUID string — any format. Retry with a fresh UUID if a collision exists in another tenant (very unlikely with UUID v7) |
| Multi-tenant bleed on `DELETE /tenant` | Cannot happen — the tenant is derived from the caller's context, and the prefix is `{tenantID}/` |
