# Attachments

Files in the `media` table are stand-alone records. To associate a file with an entity elsewhere in the platform (a lesson, a notice, an assignment submission, a product image), the system uses the **`attachments`** join table. Attachment rows are owned by the service that produces them — the file manager just provides the schema.

## The `attachments` Table

| Column | Type | Description |
|--------|------|-------------|
| `id` | UUID | Primary key |
| `tenant_id` | UUID | Tenant that owns the link |
| `file_id` | UUID | The file being attached (row in `media`) |
| `entity_type` | `VARCHAR(50)` | What kind of entity (e.g. `lesson`, `notice`, `assignment_submission`, `product`) |
| `entity_id` | UUID | The specific entity row |
| `created_at`, `updated_at` | timestamps | Auto-maintained |

Indexes exist on `(tenant_id)`, `(tenant_id, entity_type)`, `(tenant_id, entity_id)`, and `(tenant_id, file_id)` for the common query patterns.

A **unique index** on `(tenant_id, entity_type, entity_id, file_id)` prevents double-linking the same file to the same entity twice — one attachment row per file/entity pair.

## Attachment Lifecycle

Attachment rows are **managed by the consuming service**, not by the file manager itself. The file manager does not expose any REST endpoints that read or write the `attachments` table directly. Each service that needs attachments (learning-service, misc-service for notices, ecommerce-service for products, etc.) owns its own write path.

### Typical Flow

```
1. User uploads a file    → POST /v1/user/files/upload         → file_id returned
2. User submits the form  → POST /v1/learning/assignments/...  → body includes attachment_ids: [file_id, ...]
3. Consuming service      → INSERT INTO attachments (tenant_id, file_id, entity_type, entity_id) VALUES ...
```

### Why the File Manager Doesn't Own Writes

Every consuming service has its own business rules: a lesson attachment might be required on publish, a notice attachment might need a size cap different from other attachments, a product image has a maximum count. Pushing those rules through a generic filemanager endpoint would either bloat the API or weaken validation. The split keeps both sides simple.

## Entity Types in Use

These are the `entity_type` values known to appear in practice:

| Entity type | Owner service | Use |
|-------------|---------------|-----|
| `lesson` | learning-service | Lesson attachments (PDFs, supplementary files) |
| `assignment_submission` | learning-service | Files a learner attaches when submitting an assignment |
| `notice` | misc-service | Attachments on published notices |
| `product` | ecommerce-service | Product gallery images |
| `profile_avatar` | auth-service (conceptually) | User avatar (often stored as a URL on the user row instead) |
| `course_thumbnail` | learning-service | Course cover image |
| `event_media` | misc-service | Event / webinar media (joining instructions, banners) |

This list is not exhaustive — any service can define new `entity_type` values. Because the column is a plain `VARCHAR(50)` there is no enforced enum.

## Reading Attachments

Consuming services read attachments by querying the join table and then resolving each `file_id` through the file manager:

```sql
SELECT file_id
FROM   attachments
WHERE  tenant_id = $1
AND    entity_type = 'lesson'
AND    entity_id = $2;
```

The returned `file_id`s are then used with the preview endpoints (see [File Preview & Download](/docs/knowledgebase/filemanager-module/file-preview)) — either `/v1/files/preview-id/{file_id}` (public) or `/v1/admin/files/preview-id/{file_id}` (admin-scoped).

## Writing Attachments

When a consuming service creates the link, it typically does so in the same transaction as the entity it is linking to. For example, on notice creation:

```sql
BEGIN;
  INSERT INTO notices (id, tenant_id, title, body, ...) VALUES (...);
  INSERT INTO attachments (tenant_id, file_id, entity_type, entity_id)
  SELECT $1, unnest($2::uuid[]), 'notice', $3;
COMMIT;
```

The unique index ensures duplicate `file_id` entries in the same payload are rejected; services should dedupe before insertion to avoid transaction aborts.

## Deletion Behaviour

| Action | Effect on `media` | Effect on `attachments` |
|--------|-------------------|-------------------------|
| Delete a file via `/v1/admin/files/{id}` | Soft-delete (`deleted_at` set), S3 object hard-deleted | **Not cascaded** — attachment rows are not automatically cleaned up |
| Delete an entity (lesson, notice, etc.) | No direct effect | Consuming service typically deletes its own attachment rows |
| Delete tenant via system API | All tenant files removed from S3 | Attachment rows remain in DB until the tenant cleanup script runs |

Because the file manager does not know about entity lifecycles, **it is the consuming service's responsibility** to clean up its attachment rows when an entity is deleted, and to tolerate dangling attachment rows whose `file_id` points at a soft-deleted media row (preview will return `404`).

## File Reuse

A single file can be attached to many entities — the unique constraint is `(tenant_id, entity_type, entity_id, file_id)`, not `(tenant_id, file_id)`. This is deliberate: the same image can cover a lesson, show up in a notice, and be displayed on a product, all without duplicating the upload.

When such a file is deleted, **every** attachment row for it becomes dangling. Consumers should tolerate this and show a placeholder / empty state.

## Frontend Patterns

The Edushade frontend uses two patterns to collect attachments:

| Pattern | Where | Mechanism |
|---------|-------|-----------|
| **Picker** | Admin forms (course builder, notice, product gallery) | `FileManagerDialog` opens the library, user selects existing files, `file_id`s are submitted with the form |
| **Upload-and-attach** | Learner submissions | `FileUploadDialog` uploads fresh files to `/v1/user/files/upload`, then the returned `file_id`s are submitted with the assignment |

Both patterns end up with the same final shape: a JSON array of `attachment_ids` (or equivalently-named) in the form body. See [Frontend Integration](/docs/knowledgebase/filemanager-module/frontend-integration) for the component details.

## Rich Text Content

Rich-text fields (notice body, lesson description) do **not** use the `attachments` table. Media inserted into a rich-text editor is embedded as `<img>` / `<audio>` / `<video>` tags whose `src` points at `/v1/files/preview-id/{file_id}` or a preview-path URL. The file is still a regular `media` row; it just isn't linked through `attachments`.

This means deleting a file that was pasted into a rich-text body leaves a broken image / 404 in the rendered HTML. Consumers should warn admins before deleting files that might be referenced this way — a cross-service search for the file's ID in rendered HTML is the only reliable way to detect it.

## Multi-Tenancy

The `tenant_id` column on `attachments` ensures a file from tenant A can never be linked to an entity in tenant B, even by a buggy service. Every query that reads or writes attachments must filter on `tenant_id`.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| Attachment points at a missing file | The file was soft-deleted (or hard-deleted from storage). Show a placeholder in the UI and, if appropriate, delete the attachment row |
| Duplicate-key error on insert | A `(tenant_id, entity_type, entity_id, file_id)` row already exists — the user is re-attaching a file. Dedupe on the client or use `ON CONFLICT DO NOTHING` |
| Attachments not cleaned up after entity delete | Consuming services must explicitly `DELETE FROM attachments WHERE entity_type = ... AND entity_id = ...` — the file manager does not do this automatically |
| File visible but can't be previewed | `tenant_id` mismatch between the attachment row and the request's tenant context. Check for cross-tenant data introduced by a buggy migration |
| Rich-text image broken after file delete | The file was referenced by URL, not through `attachments`. Re-upload the file and update the HTML body, or add a fallback image |
| Need attachments CRUD endpoints in filemanager | Not in scope — add endpoints in the consuming service instead. The file manager deliberately stays schema-only for attachments |
