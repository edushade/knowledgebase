# Learner Uploads

Learners upload files (assignment attachments, submission proofs, profile docs) through a dedicated surface at `/v1/user/files/*`. This surface has the same upload mechanics as the admin surface — XHR upload, Uppy multipart, presigned PUT — but a different **authentication model**, a different **size limit**, and an **ownership check** on delete.

## Endpoint Map

| Method | Path | Purpose |
|--------|------|---------|
| `POST` | `/v1/user/files/upload` | Single-file XHR upload |
| `GET` | `/v1/user/files/upload/s3/params` | Presigned PUT URL for Uppy AwsS3 plugin |
| `POST` | `/v1/user/files/upload/s3/multipart` | Initiate Uppy multipart upload |
| `GET` | `/v1/user/files/upload/s3/multipart/{upload_id}` | List parts (always returns `[]`) |
| `GET` | `/v1/user/files/upload/s3/multipart/{upload_id}/{part_number}` | Sign a part |
| `POST` | `/v1/user/files/upload/s3/multipart/{upload_id}/complete` | Complete multipart upload |
| `DELETE` | `/v1/user/files/upload/s3/multipart/{upload_id}` | Abort multipart upload |
| `DELETE` | `/v1/user/files/{file_id}` | Delete own file (ownership-checked) |

All routes require `AuthMiddleware` but have **no RBAC checks**. Any authenticated user — learner, instructor, or admin — can call them.

## Why a Separate Surface?

The admin `file.upload` permission is scoped to staff who build content. Learners do not have that permission by default, but they still need to attach files to assignment submissions. The `/user/files/` routes:

- Skip the `file.upload` RBAC middleware
- Apply a **learner-specific size cap** when configured
- Enforce **ownership on delete** so learners cannot delete each other's files

The service detects learner-surface calls by checking whether the request's `c.FullPath()` starts with `/api/v1/user/` (see [File Upload → Learner Route Detection](/docs/knowledgebase/filemanager-module/file-upload#learner-route-detection)).

## Size Limit

If the tenant has `TenantSettings.Media.MaxUploadFileSizeForLearner` set to a non-zero value, that is the cap used on `/user/files/*` uploads. Otherwise the cap falls back to `Media.MaxUploadFileSize` — the same cap admins face.

```
learner_cap = settings.Media.MaxUploadFileSizeForLearner > 0
            ? MaxUploadFileSizeForLearner
            : MaxUploadFileSize
```

On violation the server returns `400` with `"File size exceeds the allowed limit of {N} MB. Please upload a smaller file."`.

## Uploading a File

### XHR Upload (Typical Flow)

```
POST /v1/user/files/upload
Content-Type: multipart/form-data

file: <binary>
dir_id: <optional UUID — typically omitted, files live in root>
```

The response is identical to the admin version — a 200 with the new `Media` object. Files uploaded through this route are stored with `created_by = <learner-user-id>`, which drives the ownership check on delete.

### Uppy Multipart (Large Files)

Large files (e.g. video recordings, long PDFs) use the same four-step Uppy flow as admins — see [Multipart Upload](/docs/knowledgebase/filemanager-module/multipart-upload). Every endpoint there has a `/user/files/*` equivalent.

## Target Folder

Learners typically upload to the **root** (`dir_id` omitted). The filesystem hierarchy is primarily an admin/instructor organisation tool; learner files can be left at the root and tracked via the `attachments` table (see [Attachments](/docs/knowledgebase/filemanager-module/attachments)).

If a learner-facing UI does want to scope uploads to a folder, it can pass `dir_id` — but the folder must already exist in the tenant (learners do **not** have `file.create` and therefore cannot create folders).

## Deleting Your Own File

- **Endpoint:** `DELETE /v1/user/files/{file_id}`
- **Auth:** `AuthMiddleware` only

### Ownership Check

The handler first asks `userFlagsProvider.GetFlags(tenantID, userID)` whether the caller is a **learner-only** user:

```go
IsLearnerOnly() = IsLearner && !IsAdmin && !IsInstructor
```

| Caller type | Behaviour |
|-------------|-----------|
| **Learner-only** | `UserDeleteFile` service method — checks `file.created_by == userID`. If not, returns `403 Forbidden` with `"You can only delete files you uploaded."` |
| **Admin or instructor** | Falls through to `DeleteFile` — same as the admin endpoint, no ownership check |

So a learner who happens to also have `is_instructor = true` can delete any file via this endpoint, even though it's under `/user/`. The route exists primarily for learner self-service.

### Error Cases

| Condition | Status | Message |
|-----------|--------|---------|
| Invalid UUID | `400` | "Invalid file ID format. Please provide a valid UUID." |
| File not found | `404` | "File not found." |
| Learner deleting someone else's file | `403` | "You can only delete files you uploaded." |
| Storage / DB failure | `500` | "Failed to delete file. Please try again later." |

### Events Emitted

Learner delete emits a learner-flavoured activity event:

| Event | Fields |
|-------|--------|
| **Activity** | `action = "file.deleted"`, title `"Deleted own file"`, metadata `{file_id}` |

The admin-equivalent emits `action = "media.deleted"` with title `"Deleted media item"` and **both** activity + audit. The learner path here emits activity only — if you need an audit trail for learner deletes, extend the handler.

## No Browse, No Rename

Learners **cannot** list, rename, preview-via-admin, or otherwise browse the file manager through the `/user/files/` surface. There is no `GET /v1/user/files` endpoint. If a learner UI needs to show a file, it uses the file's ID (from their attachment list) and the **public** preview route `/v1/files/preview-id/{file_id}` — see [File Preview & Download](/docs/knowledgebase/filemanager-module/file-preview).

## How Learner Files Are Linked to Submissions

A typical assignment submission flow:

1. Learner opens the assignment detail page (`/dashboard/assignments/{id}`).
2. Clicks **Add File** — a `FileUploadDialog` opens.
3. The dialog uploads each file to `POST /v1/user/files/upload` and collects the resulting `file_id`s.
4. On **Submit**, the frontend calls the learning service's submit endpoint with `{ attachment_ids: [...] }`.
5. The learning service inserts rows in the `attachments` table linking each `file_id` to the submission entity.

Files are not deleted when the submission is deleted — they remain in the learner's `media` records. See [Attachments](/docs/knowledgebase/filemanager-module/attachments) for lifecycle details.

## Orphan Cleanup

If the dialog uploads a file but the submission is cancelled, the frontend calls `DELETE /v1/user/files/{file_id}` to clean up. This is best-effort — if the tab crashes before cleanup, the file lingers in storage. Over time these accumulate; a periodic sweep comparing `media` rows with no corresponding `attachments` row can reclaim space.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| "File size exceeds the allowed limit of X MB" | Tenant has a learner-specific cap — ask an admin to raise `media.max_upload_file_size_for_learner` |
| 403 "You can only delete files you uploaded" | You are trying to delete another user's file via the learner route. Ask an admin — they can delete via `/v1/admin/files/{item_id}` with `file.delete` |
| 401 Unauthorized | Session expired — refresh the auth token and retry. See the [auth module](/docs/knowledgebase/auth-module/login#automatic-token-refresh) for refresh behaviour |
| Upload hangs during impersonation | The frontend blocks write operations while in **read-only impersonation mode**. Switch to **masquerade** or exit impersonation — see the [auth user-impersonation docs](/docs/knowledgebase/auth-module/user-impersonation) |
| Uploaded file doesn't show in submission | The frontend keeps `file_id`s in component state and sends them on submit. If the page reloaded, the file was uploaded but never linked — it becomes an orphan |
| Learner wants to rename their own file | Not supported on `/user/` surface. There is no rename endpoint for learners; ask an admin to rename via `PATCH /v1/admin/files/{item_id}` |
