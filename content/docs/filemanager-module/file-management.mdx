# File Management

Once a file or folder exists in the media table, admins (and — for their own uploads — learners) can rename or delete it. The service uses a **soft-delete in the database, hard-delete in object storage** model, which affects how recovery works.

## Rename

Both files and folders are renamed through the same endpoint. The service dispatches on the row's `type` column.

- **Endpoint:** `PATCH /v1/admin/files/{item_id}`
- **Auth:** `AuthMiddleware` + `file.update`
- **Body:** `{ "name": "new-name.ext" }`
- **Response:** `"Item renamed successfully"`

### Rename Behaviour

| Target type | What happens |
|-------------|-------------|
| **File** | `name` is updated. `full_path` is recomputed by the `trg_set_directory_path` trigger. The S3 `bucket_key` is **not** changed (it's based on ID + date, not name) |
| **Folder** | `name` is updated. `full_path` is recomputed, and the `trg_update_descendants` trigger cascades through every child file and folder in the same transaction |

Because the S3 object's bucket key is stable, renaming a file is a pure metadata change — there is no copy/move in object storage, and existing presigned URLs keep working.

### Name Uniqueness

Renaming into an existing name inside the same folder violates the `UNIQUE (tenant_id, parent_id, name)` constraint and returns **500 Internal Server Error**. The frontend should pre-check or catch this and surface a friendly message.

### Events

- **Activity:** `action = "media.renamed"`, title `"Renamed media item to: {new_name}"`, metadata `{item_id, new_name}`
- **Audit:** `action = "updated"`, `resource_type = "media"`, `after_value = {name}`

## Delete (Admin)

Admins and instructors delete through the RBAC-gated admin route:

- **Endpoint:** `DELETE /v1/admin/files/{item_id}`
- **Auth:** `AuthMiddleware` + `file.delete`
- **Response:** `"Item deleted successfully"`

This path soft-deletes the DB row and hard-deletes the S3 object (when `item_id` is a file).

### Delete (User — Own Files)

Learners delete their own uploads through the user route:

- **Endpoint:** `DELETE /v1/user/files/{file_id}`
- **Auth:** `AuthMiddleware` only

See [Learner Uploads → Deleting Your Own File](/docs/knowledgebase/filemanager-module/learner-uploads#deleting-your-own-file) for the ownership-check behaviour.

## Soft Delete vs Hard Delete

The service splits deletion across the two layers:

| Layer | Behaviour on delete |
|-------|---------------------|
| **Database (`media` row)** | Soft delete — `deleted_at = now()`, `deleted_by = <user>`. Row remains in the table for audit/recovery |
| **Object storage (S3)** | Hard delete — `DeleteObject` is called after the DB soft-delete succeeds |

The DB row stays so that `deleted_by`, `deleted_at`, and historical queries work. The S3 object is gone immediately — there is **no trash/restore** for the bytes themselves.

> **Restore is metadata-only.** Clearing `deleted_at` on a row makes it visible again, but the `bucket_key` no longer points at any object. Restoring a "deleted" file requires re-uploading the content.

## What Happens on File Delete

```
1. Load media row by ID (tenant-scoped)
2. Begin soft-delete (UPDATE media SET deleted_at = now(), deleted_by = <user>)
3. If soft-delete fails → return error, S3 object is untouched
4. Call S3 DeleteObject(bucket_key)
5. If S3 call fails → log warning, but return success (the DB row already says deleted)
```

Step 5 is deliberate: once the DB says the file is deleted, the user sees it as gone. An orphaned S3 object is tolerated — it is cheaper to leave it than to re-surface a file the user thought was gone. Orphan cleanup is manual (see [System API](/docs/knowledgebase/filemanager-module/system-api#delete-all-tenant-files) or an `aws s3` sweep).

## Deleting a Folder

Folders are soft-deleted through the same `DELETE /v1/admin/files/{item_id}` endpoint. The service uses `mediaSvc.DeleteMedia` which updates the folder row only.

> **Note:** the FK `parent_id → media(id)` is `ON DELETE CASCADE DEFERRABLE INITIALLY DEFERRED`, but application code uses a soft delete (just sets `deleted_at`), which does **not** trigger the cascade. As of this writing, deleting a folder in the application does not automatically soft-delete its children; the children remain visible unless they are independently deleted. If you need folder-recursive deletion, delete the children first or add explicit cascade logic.

## Empty Response Body

Both delete and rename responses return only a message — no data payload. The response envelope shape:

```json
{
  "success": true,
  "message": "Item deleted successfully"
}
```

Clients should update local state optimistically based on the HTTP status.

## Ordering Guarantees

- Activity and audit events are emitted in `go` routines after the response. The caller receives `200 OK` before the events are published. If the event bus is temporarily down, the delete still succeeds.
- Rename and delete are single-row operations and complete within the HTTP response.

## Events Emitted on Delete

| Event | Fields |
|-------|--------|
| **Activity** | `action = "media.deleted"`, title `"Deleted media item"`, metadata `{item_id}` |
| **Audit** | `action = "deleted"`, `resource_type = "media"`, `resource_id = {item_id}` |

User-initiated learner deletes emit `action = "file.deleted"` with `title = "Deleted own file"` instead — see [Learner Uploads](/docs/knowledgebase/filemanager-module/learner-uploads).

## Recovery / Undelete

There is no API endpoint for undelete. To recover a soft-deleted **DB record** (metadata only), run a manual SQL `UPDATE media SET deleted_at = NULL, deleted_by = NULL WHERE id = ...;`. To recover the **file bytes**, you must re-upload — the S3 object has been hard-deleted.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| `500` on rename | Most often a `UNIQUE (tenant_id, parent_id, name)` collision — pick a different name |
| File deleted but still visible | Cache or stale list — the list endpoint filters `deleted_at IS NULL`. Force-reload |
| File deleted but S3 still shows the object | Orphan — step 5 of delete can fail silently. Re-delete via the admin route or clean up in S3 directly |
| Deleted folder still shows children | Folder soft-delete does not cascade to children. Delete the children first, or run an SQL batch |
| Want to recover a "deleted" file | DB-only restore (clear `deleted_at`) works for metadata. The bytes are gone — you must re-upload |
| Can't delete someone else's file via `/user/files/` | Intentional — learners can only delete files they uploaded. Use the admin route with `file.delete` |
| 403 on delete | Your role is missing `file.delete` (admin path) — see [Roles & Permissions](/docs/knowledgebase/filemanager-module/roles-and-permissions) |
