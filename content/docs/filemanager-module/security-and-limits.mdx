# Security & Limits

The file manager layers several protections — multi-tenant isolation at every query, tenant-configurable upload limits, short-lived presigned URLs, audit trails on every write, and strict CORS for direct-to-S3 uploads.

## Multi-Tenant Isolation

Every read, write, and list query filters on `tenant_id`. The tenant is derived by `TenantMiddleware` from:

- The `X-Tenant-ID` header (explicit), or
- The request domain / subdomain (SaaS resolution per `config.yaml → tenant.saas_domains`)

| Guarantee | How it's enforced |
|-----------|-------------------|
| File list is tenant-scoped | `WHERE tenant_id = <ctx>` on every `GetDirContents` call |
| Folder tree is tenant-scoped | Same |
| File preview by ID is tenant-scoped | `GetFileByID(tenantID, fileID)` — foreign IDs return `404` |
| File preview by path is tenant-scoped | `GetFileByPath(tenantID, filepath)` — same |
| Bucket keys are tenant-prefixed | `{tenantID}/{date}/{file_id}{ext}` layout |
| Tenant deletion | `DeleteByPrefix({tenantID}/)` — never touches other prefixes |
| Attachments are tenant-scoped | Every row has `tenant_id`, every query filters on it |
| Unique constraints are tenant-scoped | `UNIQUE (tenant_id, parent_id, name)` |

Even if a malicious client guesses a file ID from another tenant, the lookup returns `404` before any redirect is issued.

## Upload Limits

Upload size is controlled by the tenant-service settings table, not by the file manager's static config:

| Setting | Applies to | Default if unset |
|---------|-----------|------------------|
| `Media.MaxUploadFileSize` | Admin + system uploads, and all routes where the learner-specific cap is 0 | No cap (any size, within storage limits) |
| `Media.MaxUploadFileSizeForLearner` | `/v1/user/files/*` routes only, if > 0 | Falls back to `MaxUploadFileSize` |

The file manager calls `TenantProvider.GetTenantSettings` on every upload to pick up the current tenant's values — there's no service restart required when an admin changes a cap.

### Enforcement Points

| Path | Where it checks |
|------|-----------------|
| XHR upload (`POST /upload`) | Before copying the multipart file — size from `c.FormFile("file").Size` |
| Uppy multipart initiate | Only if `metadata.size` is provided in the JSON body |
| Uppy presigned PUT | Only if `metadata.size` is provided in the query |
| Uppy complete | **Not re-checked** — trust the initiate check |

Malicious clients that omit `metadata.size` can bypass the Uppy-path cap. If strict enforcement is needed, add a post-complete size check in the service method.

## Presigned URL Lifetimes

Short lifetimes are the primary defense against leaked URLs:

| Use | Lifetime |
|-----|----------|
| **Download** (`GET /files/preview-*` redirects) | 30 minutes |
| **Upload — presigned PUT** (Uppy `/upload/s3/params`) | 10 minutes |
| **Upload — multipart part** (`/upload/s3/multipart/:id/:n`) | 10 seconds |

A leaked download URL stops working after 30 minutes. Leaked upload URLs expire within the same window as an interactive browser session.

## Presigned URL Caching

The file manager caches generated download URLs in-process for **5 minutes**, keyed by `bucket_key`:

| Property | Value |
|----------|-------|
| Backend | `go-cache` (in-memory) |
| TTL | 5 minutes |
| Cleanup interval | 10 minutes |
| Scope | Per service instance (not shared) |

**Implication:** if a file is deleted and immediately re-uploaded with a new bucket key within 5 minutes, the first few preview calls may still return the old URL. The URL itself 404s after the S3 delete, so clients will retry and get the new one — but if you need immediate-consistency, restart the service or set the cache TTL to `0`.

## Soft Delete

Files and folders use a soft-delete pattern:

| Layer | Delete behaviour |
|-------|-----------------|
| DB | `UPDATE media SET deleted_at = now(), deleted_by = <user>` |
| Storage | `DeleteObject(bucket_key)` — hard delete |

See [File Management → Soft Delete vs Hard Delete](/docs/knowledgebase/filemanager-module/file-management#soft-delete-vs-hard-delete) for the full table. Soft-deleted rows are invisible to `GET /v1/admin/files` and the preview endpoints.

## Rate Limiting

The service's `config.yaml` defines the global and per-user rate limits:

| Scope | Limit (default) |
|-------|-----------------|
| Global | 1000 requests / minute |
| Per user | 100 requests / minute |
| Per tenant | 1000 requests / minute |

Upload, browse, preview, and delete all share this budget. Unlike the auth service, the file manager does not currently define per-endpoint rate limits, but the infrastructure is present in the config block.

When a rate limit is exceeded, the API returns `429 Too Many Requests` with a standard error envelope.

## Ownership Checks (Learner Surface)

`DELETE /v1/user/files/{file_id}` applies an **ownership check** for learner-only users: the target file's `created_by` must equal the caller's `user_id`, or the response is `403 Forbidden`. Admins and instructors bypass the check. See [Learner Uploads → Ownership Check](/docs/knowledgebase/filemanager-module/learner-uploads#ownership-check).

## Security Headers

Global security headers are configured in `config.yaml → security`:

| Header | Config key | Default |
|--------|-----------|---------|
| `Content-Security-Policy` | `security.csp.policy` | `default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline';` |
| `Strict-Transport-Security` | `security.hsts.*` | `max-age=31536000; includeSubDomains` |

These are applied by the common middleware stack shared across services.

## CORS

CORS is configured in `config.yaml → cors` and defaults to:

```yaml
allowed_origins:
  - "http://localhost:*"
  - "https://edushade.com"
  - "https://*.edushade.com"
  - "https://*.taibahacademy.com"
allowed_methods: [GET, POST, PUT, DELETE, OPTIONS]
allowed_headers: [Content-Type, Authorization, X-Requested-With, X-API-Key]
exposed_headers: [X-Total-Count, X-Page-Count]
allow_credentials: true
```

> **S3 / MinIO CORS is separate.** Direct-to-S3 uploads (presigned PUT, multipart parts) require the **bucket's** CORS policy to allow the frontend origin for `PUT`, and to `ExposeHeaders: ["ETag"]` — see [Storage Backends → CORS](/docs/knowledgebase/filemanager-module/storage-backends#cors).

## Request ID Tracking

Every request is tagged with a unique **Request ID** by the OTEL middleware. The ID is included in error responses and all log lines, allowing frontend errors to be correlated with backend traces.

## Password / Credential Security

The file manager does not store passwords. It uses:

- **JWT (access tokens)** for user auth — validated by `AuthMiddleware`, issued by the auth service.
- **System API token** for inter-service calls — validated by `SystemAPIAuthMiddleware`, configured in `config.yaml → system_api.auth_token`.

See the [auth module](/docs/knowledgebase/auth-module/login) for the overall token lifecycle and refresh behaviour.

## Best Practices for Operators

1. Use **IAM instance roles** in production rather than static S3 credentials.
2. Set **tenant-level upload caps** appropriately — some tenants need larger caps (video-heavy), most should cap around 50–200 MB.
3. Run **lifecycle rules** on the bucket: expire incomplete multipart uploads after 7 days.
4. Review **audit events** periodically — especially `file.deleted` / `media.deleted` to catch accidental mass deletes.
5. **Rotate the system API token** on team changes. Treat it like a root credential.
6. Never expose the **private bucket** directly — always go through the service's presigned URLs.

## Best Practices for Users

1. Don't share presigned download URLs — they expire in 30 minutes, but a leaked URL is still exposure.
2. Delete test / unused uploads to avoid accumulating orphans.
3. Use folders to keep the library navigable — flat roots with 10K+ files slow down the UI.
4. Learners: remove files you accidentally uploaded from your submission — the frontend will clean them up server-side.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| Upload succeeds but file invisible to other tenants | Intentional — files are tenant-scoped |
| Presigned URL works then stops | 30-minute window expired — re-hit the preview endpoint for a fresh URL |
| 429 Too Many Requests | Rate limit hit — wait a minute and retry. Consider caching on the client |
| Tenant-level cap ignored on Uppy multipart | `metadata.size` was not provided during initiate — pass it or enforce at complete |
| "Forbidden: system API" | Shared token mismatch between services — check `system_api.auth_token` |
| CORS blocks PUT to S3 | Bucket CORS policy doesn't include the origin or doesn't expose `ETag`. See [Storage Backends → CORS](/docs/knowledgebase/filemanager-module/storage-backends#cors) |
| Leaked URL concerns | Revoking a specific presigned URL is not possible. Delete and re-upload the file to change its bucket key, or wait for the URL to expire |
| Want per-endpoint rate limits | Extend `config.yaml → rate_limit.per_endpoint` — the infrastructure is present, it just isn't used by the file manager handlers today |
