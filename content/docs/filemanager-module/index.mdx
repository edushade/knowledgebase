# File Manager Module

The **File Manager Module** is the centralised media and document management system of the EduShade platform. It handles everything from file uploads and folder trees to presigned S3 downloads, RBAC, attachments, and integrations with the learner dashboard, admin console, and website builder.

## Architecture Overview

The file manager is a standalone microservice (`filemanager`) that other backend services, the Next.js admin/learner frontend, and the website-builder-v2 app all talk to.

### Key Components

- **Backend**: Go (Gin framework) with Bun ORM on PostgreSQL
- **Storage**: S3-compatible object storage (AWS S3 or MinIO) via the AWS SDK v2
- **Frontend**: Wrapped with `@softimist/filemanager` for the React UI (file browser, pickers, dropzones)
- **Multi-Tenancy**: Every file, folder, and bucket key is scoped to a tenant — no cross-tenant access is possible
- **Events**: Every write emits both an **activity event** (for user-visible logs) and an **audit event** (for compliance trails)

### Service Surfaces

The service exposes four route groups, each with a different authentication model:

| Surface | Prefix | Auth | Purpose |
|---------|--------|------|---------|
| **Admin** | `/api/v1/admin/files` | `AuthMiddleware` + RBAC | Full file-manager for admins and instructors |
| **Public** | `/api/v1/files` | None | Direct file preview / download by ID or path |
| **User** | `/api/v1/user/files` | `AuthMiddleware` | Learner upload surface (assignments, submissions) |
| **System** | `/api/v1/system/files` | `SystemAPIAuthMiddleware` | Inter-service calls (migrations, tenant cleanup, batch checks) |

### Data Model

The file manager uses a **single unified `media` table** for both files and folders, discriminated by a `type` column (`file` or `folder`). Folder hierarchy is self-referential via `parent_id`, and the `full_path` column is auto-computed by PostgreSQL triggers.

| Column | Description |
|--------|-------------|
| `id` | UUID primary key (generated) |
| `tenant_id` | Tenant that owns the item |
| `parent_id` | Parent folder ID — `NULL` means root |
| `name` | Display name (file or folder) |
| `full_path` | Auto-computed path, e.g. `/lesson-assets/images/cover.jpg` |
| `type` | `"file"` or `"folder"` |
| `mime_type` | Content-Type (empty string for folders) |
| `bucket_key` | S3 object key — `{tenantID}/{YYYY-MM-DD}/{fileID}{ext}` |
| `size_in_bytes` | File size (0 for folders) |
| `metadata` | `JSONB` — flexible per-item metadata |
| `created_at`, `updated_at` | Timestamps (auto-maintained) |
| `deleted_at` | Soft-delete marker (`NULL` when active) |
| `created_by`, `updated_by`, `deleted_by` | Actor user IDs (audit trail) |

A separate `attachments` table links files to entities elsewhere in the platform — see [Attachments](/docs/knowledgebase/filemanager-module/attachments).

> **Uniqueness:** `UNIQUE (tenant_id, parent_id, name)` — no two items can share a name inside the same folder, per tenant. Uploading or renaming into a collision returns `409 Conflict`.

## How File Upload Works (High-Level Flow)

```
1. Frontend requests upload permission (optional pre-check)
2. Small file (<= configured threshold) → POST /upload (multipart/form-data)
   OR
   Large file → Uppy multipart flow:
     a. POST /upload/s3/multipart  → initiate, DB row created, uploadId returned
     b. GET  /upload/s3/multipart/:upload_id/:part_number?key=...  → signed PUT per part
     c. POST /upload/s3/multipart/:upload_id/complete?key=...       → assemble parts
3. File record is now active in the media table
4. Activity + audit events are emitted (file.uploaded, created)
5. Frontend receives the file ID and can render / link it immediately
```
