# Roles & Permissions

Every admin route on the file manager is gated by a single permission check through the shared RBAC middleware `middlewares.Can(permission, pp)`. Five permissions cover the entire admin surface. Learner routes (`/v1/user/files/*`) and public preview routes (`/v1/files/preview-*`) have no RBAC — auth alone (or no auth, for public) is enough.

## Permission Set

| Permission | Grants |
|------------|--------|
| `file.view` | List directory contents, preview files by ID or path on the admin surface |
| `file.create` | Create folders (root and nested) |
| `file.upload` | Upload files (XHR, presigned PUT, and the full Uppy multipart flow) |
| `file.update` | Rename files and folders |
| `file.delete` | Delete files and folders via the admin route |

All five belong to the `file` resource group. Naming follows the platform convention: `<resource>.<action>` in lowercase (see the auth-module [roles-and-permissions](/docs/knowledgebase/auth-module/roles-and-permissions) doc for the overall RBAC model).

## Route → Permission Map

| Route | Permission |
|-------|-----------|
| `GET /v1/admin/files` | `file.view` |
| `POST /v1/admin/files/directories` | `file.create` |
| `DELETE /v1/admin/files/{item_id}` | `file.delete` |
| `PATCH /v1/admin/files/{item_id}` | `file.update` |
| `POST /v1/admin/files/upload` | `file.upload` |
| `GET /v1/admin/files/upload/s3/params` | `file.upload` |
| `POST /v1/admin/files/upload/s3/multipart` | `file.upload` |
| `GET /v1/admin/files/upload/s3/multipart/{upload_id}` | `file.upload` |
| `GET /v1/admin/files/upload/s3/multipart/{upload_id}/{part_number}` | `file.upload` |
| `POST /v1/admin/files/upload/s3/multipart/{upload_id}/complete` | `file.upload` |
| `DELETE /v1/admin/files/upload/s3/multipart/{upload_id}` | `file.upload` |
| `GET`/`HEAD` `/v1/admin/files/preview-id/{file_id}` | `file.view` |
| `GET`/`HEAD` `/v1/admin/files/preview-path/*filepath` | `file.view` |

Missing a permission returns `403 Forbidden` with the standard RBAC error shape.

## Surfaces Without RBAC

| Surface | Auth |
|---------|------|
| `/v1/user/files/*` | `AuthMiddleware` only — any authenticated user |
| `/v1/files/preview-*` | None — public (but tenant-scoped by middleware) |
| `/v1/system/files/*` | `SystemAPIAuthMiddleware` — inter-service calls |

The learner surface deliberately skips `file.upload` because most learners don't have it. Ownership on delete is enforced in code instead (see [Learner Uploads → Ownership Check](/docs/knowledgebase/filemanager-module/learner-uploads#ownership-check)).

## Suggested Role Assignments

There are no hard-coded "file manager admin" or similar roles — tenants compose their own from the base permissions. Typical mappings are:

| Role | Typical file permissions |
|------|--------------------------|
| **Super Admin** | All five: `file.view`, `file.create`, `file.upload`, `file.update`, `file.delete` |
| **Content Manager / Instructor** | `file.view`, `file.create`, `file.upload`, `file.update` — no delete so content is curated through a formal workflow |
| **Reviewer / Marketing** | `file.view`, `file.upload` — upload assets but cannot delete or reorganise |
| **Auditor** | `file.view` only |
| **Learner** | *(none)* — uses the `/user/files/` surface which doesn't check RBAC |

Create and assign these via the auth-service's role management UI (see the [auth module roles-and-permissions](/docs/knowledgebase/auth-module/roles-and-permissions) doc).

## How the Check Works

Each admin route is registered with `middlewares.Can("file.xxx", pp)` where `pp` is the shared `rbac.PermissionProvider` (a DB-backed, subscriber-cached provider initialised in `main.go`). The middleware:

1. Extracts the `permissions` array from the caller's JWT.
2. If the required permission is present, the request proceeds.
3. Otherwise returns `403 Forbidden` immediately.

The permission cache is invalidated by the auth-service when role assignments change, so updates propagate within seconds.

## User Flags vs Permissions

As with the rest of the platform, **flags** (`is_admin`, `is_instructor`, `is_learner`) and **permissions** are separate axes:

- **Flags** decide which area of the platform the user can enter (`/admin` vs `/dashboard`).
- **Permissions** decide what the user can do once inside.

A user could theoretically have `is_learner = true` **and** hold `file.upload` — in that case the admin surface works for them. In practice the default role ladder tracks flags closely, but the two are not coupled.

The `/v1/user/files/{file_id}` delete handler is the one place the file manager reads a flag — it asks `userFlagsProvider.GetFlags` to determine whether the caller is `IsLearnerOnly()` (only `is_learner` is set, none of admin/instructor). Learners-only trigger the ownership check; everyone else falls through to the standard delete.

## Permission Denied Responses

All permission checks return the standard forbidden envelope:

```json
{
  "success": false,
  "message": "Forbidden",
  "error": {
    "code": "FORBIDDEN",
    "details": "Missing required permission: file.upload"
  }
}
```

The frontend surfaces this as a toast and, where appropriate, disables the triggering button.

## Multi-Tenancy

Permissions are scoped per tenant — holding `file.upload` in tenant A gives no access in tenant B. The `tenant_id` is extracted from the JWT and used as the lookup key for both permission resolution and every database query.

## Event Visibility

Audit events (see [Audit & Events](/docs/knowledgebase/filemanager-module/audit-and-events)) are available to any user with `audit.view` in the audit-service. They contain the actor's `user_id`, `tenant_id`, and the target `resource_id` — so role grants are fully traceable.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| 403 on `POST /v1/admin/files/upload` | Your role lacks `file.upload`. Ask a super admin to grant it |
| 403 on `DELETE /v1/admin/files/{id}` | Missing `file.delete`. Alternatively, if this is your own file, use `DELETE /v1/user/files/{id}` |
| Admin UI button does nothing | The frontend may be hiding the button because your role lacks the permission. Check the network tab for a 403 |
| Role grants aren't picked up | Permission cache can lag — log out and back in, or wait for the subscriber to propagate the change |
| Can't find the right permission | All file manager permissions are `file.<action>`. They are listed in the auth service's permission catalog |
| Instructor wants read-only access to folders | Grant `file.view` only. Do not grant `file.create` or `file.upload` |
| Learner needs to delete teammate's file | Not supported — ownership is individual. An admin with `file.delete` must do it via the admin route |
