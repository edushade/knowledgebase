# Category Tree & Hierarchy

Categories in EduShade form a **tree** — every category can optionally have a parent, and children are automatically nested under their parent for display, filtering, and navigation. This page explains how the hierarchy is stored, how to query it, and how the public tree endpoint is used by tenant-facing pages.

## How the Hierarchy Is Stored

Each category row stores three pieces of state that together describe its position in the tree:

| Column | Purpose |
|--------|---------|
| `parent_id` | UUID of the parent category, or `NULL` for root categories |
| `level` | Integer depth. Root categories have `level = 0`; their children `level = 1`; grandchildren `level = 2`; and so on |
| `path` | Materialized path string, e.g. `/<root-uuid>/<child-uuid>/<grandchild-uuid>/` |

Storing a materialized path lets the service answer **descendant queries** — "give me everything under this category, at any depth" — with a single indexed `LIKE` query (`path LIKE '<parent-path>%'`), avoiding recursive SQL.

### Invariants the Backend Enforces

- `level` and `path` are **never trusted from the client** — the service recomputes them from the current `parent_id`.
- When `parent_id` changes, the service walks down the subtree and rewrites every descendant's `path` prefix and shifts their `level` by the same delta, all in one transaction.
- A category cannot be its own ancestor (cycle prevention).
- **Single** delete rejects parents that still have non-deleted children — see [Categories](/docs/knowledgebase/misc-module/categories#children-must-be-empty). **Bulk** delete does not enforce this rule (see [Bulk Operations](/docs/knowledgebase/misc-module/bulk-operations#behavior)).
- The DB also declares `FOREIGN KEY (parent_id) REFERENCES categories(id) ON DELETE CASCADE`. This only fires on a **physical** `DELETE` — soft-deletes (the API path) set `deleted_at` and leave the row in place, so descendants still point at the soft-deleted parent and you can resurrect the parent without losing its subtree. A DBA doing a manual `DELETE FROM categories` would wipe the entire subtree at once.

## Admin Tree API

The admin-facing tree endpoint returns the **entire tenant taxonomy** as nested objects. Children are included in a `children` array on each parent.

- **Endpoint:** `GET /api/v1/admin/categories/tree`
- **Permission:** `category.list`
- **Query params:**

| Param | Description |
|-------|-------------|
| `search` | If set, the endpoint returns a **flat list** of categories whose name matches the search — nesting is bypassed so the caller can show search results without tree context |

### Response Shape (nested)

Without `search`, the response nests children under each parent:

```json
[
  {
    "id": "…",
    "name": "Technology",
    "slug": "technology",
    "parent_id": null,
    "level": 0,
    "path": "/.../",
    "status": "published",
    "children": [
      {
        "id": "…",
        "name": "Web Development",
        "parent_id": "…",
        "level": 1,
        "children": [ ... ]
      }
    ]
  }
]
```

### Response Shape (flat, with `search`)

With `search=react`, the same endpoint returns a plain array of matches, regardless of their position in the tree. Each item still carries its `parent_id`, `level`, and `path` so the UI can still render breadcrumbs. Every item also comes back with `"children": []` — the service explicitly empties the children array on every search result even if a match has descendants, since callers are meant to render search hits as flat cards, not as a partial tree.

## Public Category Tree API

The public tree is the **unauthenticated** endpoint that tenant-facing websites use to render category menus and listings.

- **Endpoint:** `GET /api/v1/public/categories/tree`
- **Permission:** none (public route, but tenant-scoped via the standard tenant middleware)
- **Returns:** only categories with `status = "published"` — drafts and archived categories are excluded
- **Query params:**

| Param | Description |
|-------|-------------|
| `search` | Flat search behavior, same as the admin tree |

Use this endpoint to power the **category navigation** on the public site, course catalog filters, and anywhere learners pick a category.

> This is the only public endpoint in the misc service for categories. There is no public endpoint for individual categories or for tags.

## Querying Parts of the Tree

Beyond the full-tree endpoint, you can navigate a subtree via the standard list filters:

| Goal | How |
|------|-----|
| All root categories | `GET /admin/categories?parent_id=<null-uuid-marker>` or simply omit and filter by `level=0` |
| Direct children of a category | `GET /admin/categories?parent_id={category_id}` |
| Categories at a specific depth | `GET /admin/categories?level=2` |
| All descendants of a category | Combine the `path` with a `LIKE` query at the service layer; the HTTP API exposes this via the tree endpoint |

The service exposes helpers for each case internally:

| Method | Purpose |
|--------|---------|
| `GetRootCategories` | All roots for a tenant |
| `GetCategoryChildren` | Direct children of a given category |
| `GetCategoryDescendants` | All descendants via `path LIKE '...%'` |
| `GetCategoryWithChildren` | Fetch a single category with its immediate children preloaded |

These are used under the hood by the tree and list endpoints and by other services that integrate directly against the misc DB.

## Moving a Category to a New Parent

To move a subtree, update the category's `parent_id`:

```
PUT /api/v1/admin/categories/{category_id}
{
  "parent_id": "<new-parent-id-or-null>"
}
```

What happens in the same transaction:

1. The old and new parent are resolved.
2. The category's `level` is recomputed (`new_parent.level + 1`, or `0` if root).
3. The category's `path` is rewritten as `<new_parent.path><category_id>/`.
4. Every descendant's `path` has its old prefix replaced with the new one, and `level` is shifted by the same delta.
5. `updated_at` and `updated_by` are bumped on the moved category (descendants' rows are untouched apart from `path`/`level`).
6. `EntityUpdated` and `AuditEvent` events are published.

The admin UI's parent selector will not let you pick one of your own descendants (that would create a cycle); the backend also rejects the request.

## Order Within a Parent

Within a single parent, the display order of siblings is controlled by `order_index` (ascending). Two categories with the same `order_index` fall back to `created_at ASC` for a stable sort.

Set `order_index` on create or via the edit form — there is no separate reorder API; it's just a numeric field you bump up or down.

## Rendering the Tree on the Frontend

- The admin **Categories list** (`/admin/categories`) is a flat table, not a tree — use the **Parent** column to see structure and the **Parent** filter to drill in.
- The **Create/Edit** forms use a tree-style parent selector so you can pick any category as the new parent.
- Any tenant-facing surface (catalog filters, navigation menus) should consume the public tree endpoint once on page load and traverse the `children` arrays client-side.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| New category appears at the wrong depth | `level` is computed from `parent_id` — double-check you sent the right parent ID |
| Public tree is missing a category | Verify its `status` is `published` (not `draft` or `archived`) and it isn't soft-deleted |
| Changed a parent and children are in the wrong place | The server cascades `path` and `level` atomically; reload the list — stale frontend cache is the usual culprit |
| Tree endpoint is slow | Categories use `idx_categories_path`, `idx_categories_parent_id`, and `idx_categories_level` — if queries are slow on a specific tenant, confirm those indexes are present on that environment's DB |
| Can't move a category under another | The API rejects cycles (moving A under one of A's own descendants). Move the target subtree first, then move A |
