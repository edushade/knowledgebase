# Misc Module

The **Misc Module** (backed by the `misc-service` microservice) is the EduShade platform's home for **cross-cutting taxonomy and reference data**. It owns the primitives other services use to classify, label, and locate content: **categories**, **tags**, **polymorphic associations**, and shared **geo data** (countries, states, cities).

Every learning product, course, event, post, or user in EduShade can be organized with the categories and tags defined here — making this module the backbone of navigation, filtering, search, and discovery across the platform.

## What This Module Covers

| Feature | Description |
|---------|-------------|
| [Categories](/docs/knowledgebase/misc-module/categories) | Create, update, delete, and manage hierarchical categories |
| [Category Tree](/docs/knowledgebase/misc-module/category-tree) | Hierarchical parent-child structure, level tracking, materialized paths, public tree API |
| [Category Associations](/docs/knowledgebase/misc-module/category-associations) | Attach categories to any entity (course, event, etc.) with polymorphic links |
| [Tags](/docs/knowledgebase/misc-module/tags) | Flat, lightweight labels — create, update, delete, filter by slug |
| [Tag Associations](/docs/knowledgebase/misc-module/tag-associations) | Attach tags to any supported entity type across the platform |
| [Bulk Operations](/docs/knowledgebase/misc-module/bulk-operations) | CSV export and bulk delete for categories |
| [Geo Data](/docs/knowledgebase/misc-module/geo-data) | Public reference data for countries, states, and cities |

## Architecture Overview

The misc module is a standalone Go microservice (`misc-service`) that exposes three independent feature areas behind a single REST API. Frontend admins manage categories and tags through dedicated pages in the admin dashboard; other backend services consume the data via published entity events and polymorphic association queries.

### Key Components

- **Backend**: Go (Gin framework) with Bun ORM on PostgreSQL
- **Frontend**: Next.js admin pages at `/admin/categories` and `/admin/tags`
- **Multi-Tenancy**: Every category, tag, and association is scoped to a `tenant_id`
- **Pub/Sub**: Entity events (`EntityCreated`, `EntityUpdated`, `EntityDeleted`) and `AuditEvent` published for downstream consumers
- **RBAC**: All admin endpoints guarded by granular permissions (`category.*`, `tag.*`)
- **Soft Deletes**: Categories and tags use `deleted_at` — nothing is physically destroyed by default

### Feature Areas

EduShade's misc-service combines three conceptually separate feature areas:

| Area | Purpose | Multi-tenant | Public API |
|------|---------|-------------|------------|
| **Categories** | Hierarchical classification | Yes (per tenant) | `GET /public/categories/tree` (published only) |
| **Tags** | Flat labels | Yes (per tenant) | No — admin only |
| **Geo** | Reference data for countries / states / cities | No (global) | Yes — fully public |

> Geo is intentionally global — every tenant shares the same country/state/city dataset. Categories and tags are always tenant-scoped.

## Categories vs Tags — When to Use Which

Categories and tags look similar but are used differently:

| Property | Categories | Tags |
|----------|-----------|------|
| **Structure** | Hierarchical (parent → children) | Flat |
| **Navigation** | Shown in menus, filters, public tree | Rarely navigational |
| **Cardinality** | A few per entity | Many per entity |
| **Visibility** | Has a **public** tree endpoint | Admin-only |
| **Fields** | `name`, `description`, `slug`, `parent_id`, `level`, `path`, `icon`, `color`, `thumbnail`, `order_index`, `status` | `title`, `slug`, `description`, `color`, `status` |
| **Use case** | "Programming → Web Development → React" | "#beginner", "#new", "#featured" |

## Entity Types That Can Be Categorized / Tagged

Both categories and tags can be attached to **any entity** — the association tables are polymorphic (`entity_type` + `entity_id`). In practice, the platform currently uses them for:

| Entity Type | Categories | Tags |
|-------------|-----------|------|
| `course` | ✅ | ✅ |
| `event` | ✅ | ✅ |
| `product` | — | ✅ |
| `learning_path` | — | ✅ |
| `bundle` | — | ✅ |
| `lesson` | — | ✅ |
| `assignment` | — | ✅ |
| `cohort` | — | ✅ |
| `user` | — | ✅ |
| `post` | — | ✅ |
| `article` | — | ✅ |

> The backend doesn't enforce the entity type — any service can create an association by passing its own `entity_type` string. The list above reflects what tag stats currently count and what the admin UI expects.

## Content Lifecycle

Both categories and tags share the same three-state lifecycle:

| Status | Visible in admin? | Visible in public APIs? | Description |
|--------|------------------|------------------------|-------------|
| `draft` | Yes | No | Work in progress, not shown to learners |
| `published` | Yes | Yes | Live and visible |
| `archived` | Yes | No | Retired but retained for historical data |

Status is **required on create** for both categories and tags — the create DTOs reject missing values with `400 Bad Request`. The database column defaults (`draft` for tags, `published` for categories) only matter for rows inserted outside the validated API path. In practice: pick a status explicitly in every create request.

Soft deletion (`deleted_at`) is a separate concern from status — deleted records disappear from all queries, but a status change keeps the record in the table.

## Events & Audit

All mutating actions publish events through the platform pub/sub layer:

| Event | Categories | Tags |
|-------|-----------|------|
| `EntityCreated` / `EntityUpdated` / `EntityDeleted` | ✅ (CRUD of the category itself) | — |
| `AuditEvent` (create/update/delete/bulk CRUD of the record) | ✅ | ✅ |
| `AuditEvent` on association attach / detach | ✅ | ✅ |

Every mutation is tagged with `module = "misc"`. `resource_type` varies by surface:

| Action | `resource_type` |
|--------|-----------------|
| Category CRUD (create/update/delete/bulk_deleted) | `"category"` |
| Category association attach / detach | `"category_association"` |
| Tag CRUD | `"tag"` |
| Tag association attach / detach | `"tag_association"` |

The distinction matters for audit-log filters — a "tag" audit row is about a tag record, not about tagging an entity.

See [Audit Module](/docs/knowledgebase/audit-module) for how `AuditEvent` records flow into the platform audit log. Associations **only** emit `AuditEvent` — they never emit `EntityCreated`/`EntityUpdated`/`EntityDeleted`.

## Getting Started

If you're an **administrator** setting up taxonomy for a new tenant:

1. Plan your hierarchy — start from [Category Tree](/docs/knowledgebase/misc-module/category-tree) to understand how parent-child relationships and paths work
2. Create your root categories at `/admin/categories/create` — see [Categories](/docs/knowledgebase/misc-module/categories)
3. Attach categories to your content via [Category Associations](/docs/knowledgebase/misc-module/category-associations)
4. Add tags for lightweight labeling at `/admin/tags` — see [Tags](/docs/knowledgebase/misc-module/tags)
5. Use [Bulk Operations](/docs/knowledgebase/misc-module/bulk-operations) to export current taxonomy or clear out old data

If you're a **developer** integrating with misc-service from another backend:

1. Read [Category Associations](/docs/knowledgebase/misc-module/category-associations) and [Tag Associations](/docs/knowledgebase/misc-module/tag-associations) to see how to link your entities
2. Subscribe to the category entity events (`category.created`, `category.updated`, `category.deleted`) if your service caches category metadata
3. Use [Geo Data](/docs/knowledgebase/misc-module/geo-data) as a drop-in source for country/state/city selectors — no auth required
